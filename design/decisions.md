# Implementation decisions

Points the documentation left open or contradictory, and how the compiler resolves them. Each entry says where the question came from. When a decision changes what a user writes, the documentation is updated to match.

## Programs and the command line

- **Arguments of a standalone file**: the top level of a standalone file or script sees an implicit `arguments: Array(String)` holding only the user arguments: index `0` is the first one, as for an exported entry function (modules page). The guides' `arguments.get(1)` becomes `get(0)`. Everything after the file in `fa run file.fa a b` goes to the program; a `--` right after the file is accepted and dropped. (advanced brief D4, D5)
- **`fa run`** compiles the file for `bun` and runs it; the compile-time interpreter is only used at compile time. Bun is a dependency of the toolchain (`PATH` or `~/.bun/bin`). (advanced brief D6, D35)
- **`fa build` output**: `fa build <file.fa | package> --target=<target> [--output=<directory>]`; the default directory is `build/<target>/`. `native` writes an executable, `wasm` a `.wasm` file and a JavaScript loader, `bun`/`node`/`web` a `.js` module. (benchmarks)

## Standard library

- **Parsing a number** is `Integer.parse(text)` (`throws ParseError`), as on the type conversion page. `Integer.fromString` in the guides was stale and is renamed. (benchmarks)

## Proofs

- **Index proofs**: a loop `for i in a..b` proves `a <= i < b`; with `b` being `array.length` (or `array.length - k`) and `a >= 0` provable, `array[i]` (and `array[i + k]` within bounds) needs no check. A `while i < array.length` guard proves the same inside the loop body until `i` or the array is mutated. (benchmarks)

## Native and WebAssembly

- **Binding**: inkwell on LLVM 18, linked dynamically to `libLLVM.so` during development (`FA_LLVM_LINK=static` for release builds of the compiler). (LLVM proof of concept, see `design/llvm-backend-plan.md`)
- **Runtime**: the core runtime (output, exit, stops, allocation) is LLVM IR generated by the compiler into each module, only for what the program uses. Larger parts (Unicode tables, float formatting) are written in Fa, or in C compiled by clang 18 to bitcode when Fa can't express them yet.
- **WebAssembly target**: `wasm32-unknown-unknown` with a few imports (`fa.write`, `fa.exit`, …) provided by a generated JavaScript loader; not WASI.
- **Float to integer conversion** (`Integer(x)` on a `Float`): a NaN or out-of-range value stops the program, like an overflow; the analyzer removes the check when the range of `x` is known.
- **Freestanding Linux target**: kept as an option of the `native` target for the smallest binaries (no libc, raw system calls); the default links against the C library.
- **Tier 1 runtime in C, shipped as IR**: printing, strings, stops and errors are `packages/codegen-llvm/runtime/fa_runtime.c`, compiled by clang 18 to LLVM IR for 64-bit targets and for wasm32; the IR is checked in (`runtime/generate.sh` regenerates it), so building the compiler needs LLVM but not clang. Each program links it and makes it `internal`: what it doesn't use disappears. (LLVM backend M1)
- **Float printing**: the shortest round-trip digits come from the C library on `native` (`snprintf` then `strtod`, the shortest precision that reads back), and from the JavaScript loader on `wasm` (`String(x)`, the very function of the JavaScript backend); the layout of `Number::toString` is the runtime's. The freestanding target has no float printing yet: the compiler reports it. A C-library-free shortest algorithm (Ryu-like, small tables) replaces both later. (LLVM backend M1)
- **Errors** (native and wasm): a function that throws returns `{ result, ptr error }` (the error alone without a result), null when it succeeded; a raised error goes to the innermost `catch` of the function, else to the caller, else (top level) prints `error: <toString>` and exits with 1. No unwinding, no landing pads. An error, like every value of a named union, is a pointer to a box `{ i64 member id, data }`; the built-in errors have the fixed ids of the runtime. (LLVM backend M1b)
- **Value layouts** (native and wasm, first version): an object or a tuple is a struct of its fields (in the order of the shape, sorted by name) passed by value; an anonymous union of different kinds and a named union are boxes; an array is a pointer to a header `{ items, length, capacity }`, copied when a binding or a store reads it from a place (arrays are values), shared by parameters; a function value is `{ function, environment }`, the environment a copy of the captured locals. Generic functions are monomorphized per representation of their type arguments. (LLVM backend M1b; memory: the next entry)
- **Memory management** (native and wasm, LLVM backend M2): every owning value has one owner (a local, a field, an item, a box, an environment, a table entry, or the statement that computed it). A string is `{ ptr, length, capacity }`: capacity 0 is a literal or an argument (never freed, copied for free), `usize::MAX` a view of another string's bytes (the variable of a `for` over characters; copied when stored); `split`, `characters`, `trim` and the other slices allocate. Drops and copies are generated per shape; a scope drops its owned locals in reverse order at every exit (end, `break`, `continue`, `return`, a raised error), a statement its temporaries. No drop flags: a moved-from local is zeroed, and every drop accepts a zero value. A copy becomes a move for a temporary, for the analyzer's `MOVE` flag, and for a local's last textual read outside a loop or a lambda that its declaration is outside of (or the last read in the value of an assignment to the local itself, `head = Link { next = head }`). Module-level values are dropped at the normal end of the program. A recursive edge to an object is a heap block owned by its parent (a named union is a box already); its drop and copy follow the last edge in a loop, so a long list never recurses deeply.
- **Allocator** (wasm and freestanding): size classes (multiples of 16 up to 128 bytes, then four per power of two up to 8 KiB) over 64 KiB pages whose header names the class, so a block is freed from its address alone (`fa_free` ignores its size); larger blocks take runs of pages, returned to an address-ordered list of free runs merged with their neighbors. Memory comes from `memory.grow` / `mmap` 1 MiB at a time and is never returned to the system. Native uses it too, over `aligned_alloc` pages (binary-trees: 1.28 s with `malloc`, 0.61 s with it); a leak-checked native build keeps `malloc`, to poison freed blocks.
- **Parameters a function changes** (`mutates` / `invalidates` roots, `self` included) are passed by pointer to the caller's place; a structural view of another object type is copied in and written back after the call (equivalent under the alias rule). `use` / `mutable use` / `reuse` are pointers into places (a `mutable use` keeps its address in a slot); a `for` variable over an array or a table points at the item. Requirements are hidden pointer parameters after the regular ones, in the order of `FnSig::requires`; `provide` binds a place, or a temporary owned by its block. A closure that doesn't escape (`Analysis::escapes`) holds pointers to the captured variables (local functions included); an escaping one owns heap copies, its environment starting with its drop and its copy. (LLVM backend M2)
- **Maps and sets** (native and wasm): a pointer to an insertion-ordered table of the runtime (entries `{ hash, live, key, value }` in order, an open-addressing index; a deleted entry stays dead until the entries are compacted, when full). Keys are hashed and compared by functions generated per shape: Fa `==`, floats with SameValueZero, like the JavaScript runtime's `FaHashMap`; an existing key keeps its place and its first spelling. `Set.from(…, key = …)` is not lowered yet. (LLVM backend M2)
- **Leak checks**: `Options::leak_check` counts the live blocks; at the normal end of the program a nonzero count prints `leak: <n> blocks` and exits with 102 (and natively, freed blocks are filled with `0xAB`). Every end-to-end program of the native, wasm and freestanding tests runs with it. (LLVM backend M2)
- **Stack overflow** (values brief D-26): on `native`, `main` installs a `SIGSEGV` handler on an alternate stack that prints `stop: stack overflow` and exits with 101; the wasm loader converts the engine's `RangeError`. Not handled yet when freestanding. (LLVM backend M1)
- **Output buffering**: the standard output is buffered by the runtime (8 KiB) and flushed when full, before anything is written to the standard error, at exit and at a stop. (LLVM backend M1)
- **Pools** (native and wasm, `src/lower/pools.rs`): a slab as `collections/pools.md` describes it: chunks of a power of two of 64 KiB pages, aligned on their size (the chunk of an element is its address with the low bits cleared), an occupancy bitmap and a free list per chunk, a table of chunks with a bitset of those with room (`add` fills the first), an emptied chunk kept as the spare or freed, no compaction. A reference into a pool is the element's address; `use x = pool.find(…)` may be null and reads as an optional. The read-only methods (`some`, `reduce`…) and printing run on a bytewise view of the elements. `add` stores a value built first (no construction in place yet). `GrowingPool` is the same pool. (third native shift)
- **Columnars by columns** (native and wasm, `src/lower/columns.rs`, fourth native shift): a `Columnar` or `GrowingColumnar` of objects is a pool of the runtime whose slots are 4 bytes (the free list), followed in each chunk by one run per field (aligned on 64 bytes, all of the chunk's capacity: a power of two, the widest field filling about 64 KiB). A reference is the **address of the element's slot**, not a `u32` index as the implementation notes say: as unique and stable, and the chunk (address with the low bits cleared) and the slot index (offset / 4) give every field's address, so pools and columnars share the reference machinery; a field is one address computation away, a whole element is gathered (read) or scattered (written). `for` over a pool or a columnar walks the chunks and their occupancy words in generated code, and `for { a, b } in columnar` binds the fields straight to their runs. An element type with relation sides stays in rows (the runtime updates sides at byte offsets); `OrderedColumnar` is still an array of rows. Measured (1 M elements of 10 fields, 200 sums of one `Float` field): 1.4–2.1 s by columns against 3.3–5.2 s by rows, on a shared machine.
- **Relations** (native and wasm, `src/lower/relations.rs`, fourth native shift): a side holding one element is the target's address (null for `none`), read as an optional view of the target; a many-to-many side and a `Pool` reverse side point at a set of addresses of the runtime (`FaLinks`: insertion order, an index once it holds more than 8), null while empty. Writes (`relation_writes`) and unlinks (`relation_unlinks`, `clear` unlinks every element before dropping any) are runtime calls given the byte offsets of both sides (`fa_relate_one`, `fa_relate_add`…, `fa_unlink`), as the JavaScript helpers. A copy of an element empties its sides (D18), `take` too; a copy of an owner of related pools maps every element to its copy and relinks the sides and the owner fields through the map (a link to an element outside the owner is left out). Printing, `==` and hashing skip the sides (D21). A local that a `use` designates a part of (`use ana = town.people.add(…)`) is never moved by its last textual read.
- **Iterators** (native and wasm, `src/lower/iterators.rs`): never a runtime value. The chain (`values()`/`keys()`, then `filter`, `map`, `firstValues`) is read back from the syntax, through the locals that name it, and fused into the loop of its consumer (`find`, `reduce`, `every`, `some`, `toArray`, `for`): each element goes through every stage before the next is read, in the order of a lazy iterator. A local naming an iterator lowers to nothing, and its callbacks are evaluated where it is consumed. Without a `map`, the variable of a `for` designates the element.
- **Compile-time values** (native and wasm, `src/lower/constants.rs`): arrays, tuples, objects and optionals of `Analysis::constant` are built at run time from the interpreter's value (an item of a union of literal types is boxed as the member it matches); `@for` lowers its body once per item of `Analysis::unrolled`. Maps and sets are built entry by entry, members of enumerations are their index, members of named unions and errors their box (with their data), ranges a constant (fourth native shift).
- **Strings grow in place**: `text += suffix` appends into the block of an owned string, which grows geometrically (capacity doubles), so a loop of appends is linear; `split`, `replace`, `includes` and `indexOf` find their matches in one pass over the grapheme boundaries. (string-building: 141x Rust at the quick size, 0.67x at the default size)
- **Simple strings** (native and wasm, fifth native shift): the top bit of a string's capacity word, `SIMPLE`, says that every byte is ASCII other than `'\r'`, so every byte is a grapheme cluster and a position is a byte offset (`'\r'` is excluded so that the flag survives concatenation: `"\r" + "\n"` is one cluster). The other bits keep their meaning (0 static, all ones a view, else the owned capacity). Literals and arguments get it at compile time or creation, copies and slices keep it, appends keep it while the suffix is simple; it may be missing from a simple string (any producer that doesn't compute it is correct, only slower), never set on another. With it, `length`, `text[i]`, `get`, slices, `indexOf`, `includes`, `split`, `characters()` and `codePoints()` take constant time per character, and a character of a simple text is one of 128 static one-byte strings (no allocation: `letters[i]`, `characters()`). No cached grapheme offsets nor small-string optimization yet: measured, the remaining string costs are allocations of whole words and arrays, which inline strings of 23 bytes would remove, at the price of a branch on every access (left for later).
- **String slicing** `text[a..b]` (native and wasm): the bounds of `faSliceBounds` in grapheme clusters, `IndexError` outside; a slice of a static string is a view of it (static), others are copies.
- **Bounds checks in loops** (native and wasm): an index check is `0 <= i < length` on the common path, and a negative index (counted from the end) goes through an out-of-line `fa_index_from_end`, so that LLVM's inductive range check elimination (`irce`, run with `licm`, `reassociate` and a second vectorization after `default<O2/O3>`) splits a loop whose indices are the loop variable plus invariants into a check-free main loop between two short checked ones. `blur` vectorizes (16 bytes per step) and runs as fast as Rust (0.09 s).
- **Scalar TBAA** (native and wasm): loads and stores of program values are tagged by their scalar type (`fa i8`, `fa i64`, `fa ptr`, `fa double`…, children of `fa value`; an aggregate access is `fa value`), since a Fa value is never read as another scalar type: a store into an `Array(UInt8)` doesn't invalidate the place holding another array.
- **Narrow arithmetic** (native and wasm): an integer `+`, `-`, `*` (and `//`, `%%` of non-negative values by a positive divisor) whose every step is bounded by the *storage* of its operands (never by the analyzer's facts, which a wrapping build may break) is computed in 16 or 32 bits, then extended: sums of bytes vectorize like Rust's `u16`.
- **Early boxes** (native and wasm): the box of a recursive field (`left: Node?`) given a call or an object literal of the target type is allocated before the value is computed, so that a tree built recursively is laid out in the order a walk visits it (`tree`: 1.43 s → 0.37 s; Rust 0.38 s; Rust allocating after the children takes 1.14 s).
- **Filtering a temporary array** moves the kept items and drops the others (`text.split(" ").filter(…)`), when the callback is a lambda without `try` or `throw`.
- **`text += "{…}"`** builds the template in the runtime's text builder and appends it from there, without a string of its own.
- **The wasm loader** keeps only the host functions the module imports (`// @import <name>` … `// @end` sections of `host/loader.mjs`): no float formatting nor argument copying in a loader that doesn't need them.
- **Moves in exclusive branches**: a local read in one branch of an `if` or a `when` is its last read when the later reads are in the other branches (`if kind < 5 { Add { left, right } } else { Multiply { left, right } }` moves `left` and `right` instead of copying the subtrees: `interp` spent a third of its time copying).
- **No teardown**: the drops at the end of `main` only free memory unless the program has a drop with an effect (a `destroy` of foreign code, a thread-safe value, a `watch`), so they are skipped then (behind a constant decided at the end of lowering), as the system takes the memory back; a leak-checked build always drops.
- **`destroy` and moved-out locals** (native): a local holding a resource of foreign code has a drop flag, cleared when it moves out (`let second = first`, a returned value), so `destroy` runs once, on the value's last owner.
- **Allocator classes in steps of 8 bytes** up to 128 (were 16): a block is aligned on 16 only when its size is a multiple of 16, which the 128-bit integers and the items of arrays ask for; boxes take the size of their type (`interp`'s 24-byte nodes no longer take 32). Its free-list pop is inlined, the rest out of line.
- **Small arrays in one block**: up to 96 bytes of items live right after the header, in its block (a marker word after the header says so), so `codePoints()`, short splits and literals allocate once.
- **Code points without arrays**: `for c in text.codePoints()` decodes in place, and a `let codes = text.codePoints()` that is only indexed, read with `get` and measured, on a text that can't change meanwhile, is never built (`strlist`).
- **Strings, more**: the hash of a string reads 8 bytes at a time (tables are insertion-ordered: the hash is not observable); copies of up to 16 bytes are inlined; `text += …` has an inlined common path (a simple suffix into a block with room).
- **`Integer.truncate(x)`** is a `fptosi` after the range check, without the C library's `trunc` (the x86-64 baseline has no SSE 4.1).
- **Pipeline**: the `instcombine` runs added after `default<O3>` use `no-verify-fixpoint` (LLVM 18 aborts the compiler otherwise when one round doesn't reach a fixpoint).
- **Counted push loops**: before `for i in a..b` whose body pushes onto a local array at its top level, mentions the array nowhere else and has no `break`, `return`, `throw` or `try`, the array reserves room for every round, and the pushes skip the capacity check. Natively, the runtime's copies of the 128-bit builtins are left out: the C compiler's support library provides them.

## Advanced features and architecture

The decisions D1 to D51 of `design/implementation/advanced-and-architecture.md` are accepted, with one change to its tiering: the `wasm` target is built together with `native` (tier 1 of the native backend), since the LLVM backend produces both.

## Types, functions and collections

The decisions D1 to D63 of `design/implementation/types-functions-collections.md` are accepted. Note that the two briefs number their decisions independently: cite them as "types brief D2" or "advanced brief D4".

## Values and control flow

The decisions D-1 to D-105 of `design/implementation/values-and-control-flow.md` (cited as "values brief D-n") are accepted, except where they conflict with another brief:

- **`Float32` and `Float`** (values brief D-19 vs types brief D11): a `Float32` is accepted where a `Float` is expected (exact widening, like integer ranges), but arithmetic, comparisons and equality never mix the two: write `Float(x)` or `Float32(x)`, since `Float32` rounds after every operation and the mix must be visible. `Float` to `Float32` is always the explicit `Float32(x)`.
- **`Integer` and `Int64`** (values brief D-8, types brief D2): the two briefs agree; two types with the same range, assignable as scalars, not interchangeable inside collections.
- **`ArithmeticError`** carries `{ message: String }`, like the other built-in errors of types brief D50 (over values brief D-25).
- **Collections of integers with different storages** (values brief D-8 over types brief D54): `Array(Int8)` is never accepted as `Array(Integer)`, even read-only, since the layouts differ; convert with `map`. Collections whose element types differ only by range and share a storage (`Array(Integer(min = 0))` for `Array(Integer)`) are accepted by parameters that are not mutated.
- **JavaScript property order** (values brief D-81 over types brief D57): objects are built with the field order of their type's declaration (for an anonymous object type, the order of the literal that the type was inferred from), the same at every construction and copy, so one type is one hidden class and `JSON.stringify` follows the declaration, as a JavaScript developer expects.

## Parser

The parser decisions listed in the parser rework (see the "Parser Package Notes" of `AGENTS.md`) are accepted. The ones users see:

- A lone `}` in a string is an error (`}}` writes a brace); `\{` and `\}` are unknown escapes; `\x` covers `00` to `7F`.
- `%` applies to a number literal or a parenthesized expression only: `fifty%` is an error, write `(fifty)%`.
- `when` branches are separated by newlines or commas, so a tuple value in a branch needs parentheses.
- `while let` binds a name, not a pattern.
- `a == b == c` and `x += y += z` are errors.
- A `-` directly before a digit is part of the literal unless it follows an operand: `a-1` is a subtraction.
- `else` on the line after `}` is a diagnostic, but still attached to the `if`.
- A documentation comment is the run of comment lines directly above a declaration, with no blank line in between.
- Integer literals up to 128 bits are kept exactly; whether one fits its type is the checker's job.

## Analyzer

- **Type mismatch code**: `E-TYPE-1` is the canonical code of a value that doesn't satisfy the expected type; `TY002` is its alias. An integer whose range isn't proven to fit keeps the more precise `E-NUM-14`.
- **Imported brief cases** that pass only because their feature isn't analyzed yet keep their `pending` header until the milestone that implements the feature.
- **Number API**: `Math` holds only `Math.max` and `Math.min` (the documented ones); the other math functions are methods of the values (`x.sqrt()`, `x.round()`). Methods of integers are shared by every integer type and return the receiver's storage type. The float to integer conversions `Integer.round/floor/ceil/truncate(x)` exist on `Integer` only, accept a `Float32`, and can't fail on a literal that fits. `minValue`/`maxValue` of an integer type have the literal type of the bound in that storage (`Int8.minValue` is `-128` as an `Int8`); `Float.nan` and the other float constants are plain `Float`s (also on `Float32`). `Float.parse(text)` throws `ParseError`.
- **Shifts**: an amount proven in `[0, width)` can't fail, one proven outside is `E-NUM-20`, any other `throws ArithmeticError` (values brief D-50); the amount's facts are the proof.
- **Tuples are not ordered** (`values/tuples.md`): `<` on tuples is `E-CMP-2`, so the `ORDERED` flag of tuple types is gone.
- **Index proofs over a `mutable` array**: `for i in a..c.length` (and `while i < c.length`) also proves `c[i]` when `c` is `mutable`, as long as the loop only reads, writes or measures the items of `c` (`c[…]`, `c.length`): its length can't change there. Changing `c` (a method like `push`, an assignment) drops the relations to it. (sieve benchmark)
- **`for` over a `Range` value** (not a literal): the variable is an `Integer` without facts; a range without start stops the program, as iterating past `Integer.maxValue` does.
- **Destructuring**: object, array and tuple patterns in `let`/`mutable`, `for` and parameters (`use` patterns wait for references, but `E-DST-1`/`E-DST-4` are reported). An array pattern can fail with `IndexError` unless the length is proven: a literal, a length fact, or a test `if values.length >= 2` (comparisons with `c.length` now narrow the length fact of `c`). A destructured parameter is an anonymous parameter (named by its pattern's text) whose pattern is bound in the body.
- **Parse diagnostics have codes**: `fa_parser::Diagnostic::code` holds the code of the rule a syntax error breaks (`E-STR-1`, `E-NUM-3`, `E-TUP-4`, `E-DST-6/8/9`, `E-DECL-8`, `E-ERR-6`, `E-OBJ-13`, `E-CMP-3`, `E-LEX-*`); the analyzer reports it as is, `AN002` without a code. A unit test checks that every code of the parser is registered.
- **Brief corrections**: T-DST-8 gives each failing call its own `catch` (a `catch` covers its left operand only); the split cases T-NUM-53-b/73-b/80-b/82-b/84-b and T-TUP-22-b repeat the declarations of their first half; T-NUM-88 (`E-NUM-19`) is a JavaScript-backend case.

## JavaScript runtime

- **`none`** is `undefined` (values brief D-7, `optionals.md`), never `null`; an absent optional field and a field set to `none` are equal.
- **Named union members** carry their tag in a `$t` property (types brief §3.5.3); printing and equality skip every `$` property.
- **Errors** are classes extending `FaError` (not `Error`: no stack capture on the success-free path); `throw`/`try` are plain JavaScript; `catch` keeps only `FaError` values and rethrows stops and foreign exceptions. A stop throws `FaStop` (an `Error`, for the stack in browser consoles); the entry wrapper prints `stop: <reason>` with the location and exits with `101`, or `error: <error>` and `1` for an escaped error.
- **Printing**: maps print like their literal `[("a", 1)]`, sets like arrays.
- **Union tags** are the qualified names of the members (`$t: "Shape.Circle"`), so that printing and `when` need no table and two unions never share a tag; a member whose data is not an object is `{ $t, $v }` (`$v`, not `v`: a data object may have a field `v`), a member without data a frozen module-level `Shape$Point`, a literal member the literal. Printing recognizes a tagged object by its `$t`; the runtime collections by their `Symbol.toStringTag` (`fa:HashMap`, `fa:Set`, `fa:Range`) and errors by their static `faName`, so that printing and the entry point don't bring these classes into programs that don't use them.
- **Enumeration members** are their underlying numbers; a module-level table `Color$names` prints them, `Color$members` lists them.

## JavaScript backend (first shift)

- **Output**: one ES module; the runtime helpers it uses are inlined at its start, without their documentation comments. Functions and types' functions (`Point$sum(self, …)`) are module-level function declarations; the top-level statements of a standalone file are the body of a `main` function run by `faRun(main)`; a top-level value read by a function is a module-level `let` assigned in `main`.
- **Names** keep their Fa spelling; a JavaScript reserved word or global (`class`, `Math`, `undefined`…) or a runtime helper name gets a `$` suffix, and a name shadowing a visible one gets `$1` (JavaScript would see a temporal dead zone). Temporaries are `$t0`, `$t1`…: Fa names never contain `$`.
- **Checks** are exactly the analyzer's bits: an `OVERFLOW_JS` (number) or `OVERFLOW_NATIVE` (bigint) n-ary node checks the steps whose interval, recomputed from the operands' facts, may leave the range; `SINK_CHECK` checks against `coercions[n]`. Each check passes the `file:line:column` of its node, the path as given on the command line.
- **Copies**: a composite value read from a place is copied when stored into a `mutable` binding, an assignment, a field, an item or a literal, or bound by `let` from a mutable place; fresh values (literals, calls) never are. A conditional value (`if`, `when`, `catch`, `??`) with a branch read from a place is copied like a place; a function returns a copy of a value read from a place it doesn't own (a parameter, a loop variable, a field of one, a module value, a `let` bound to a place), so a call result is always fresh: its own `mutable` locals and `let`s bound to fresh values are returned as they are. The copy is `slice()` for an array of primitives, a generated `copy$Point` for an object type (fields in declaration order), `faCopy` otherwise.
- **Error members** are module-level classes `ApiError$Timeout extends FaError` with `static faName = "ApiError.Timeout"` and a constructor taking the fields in declaration order; `catch` is `try { … } catch ($e) { const error = faCaught($e); … }` with both sides generated into the destination of the `catch`; `when error is` and `is` test with `instanceof`.
- **`?.`**: the parser keeps a chain `a?.b?.c` in one node without saying which members follow `?.`, so every member is read with `?.` (the same result, since the chain stops at its first `none`).
- **`fa build`** writes `main.js` (and `main.d.ts` with `--declarations`, and a `package.json` declaring an ES module for `node`) into `build/<target>/` next to the file; `fa run` writes `<file>.mjs` into `$XDG_CACHE_HOME/fa/run/<hash of the path>/` and runs it with Bun.
- **End-to-end tests** live in `packages/cli/tests/programs/` (the CLI is what they exercise) and also run every analyzer case that says what it prints.
- **`Integer.parse`** accepts an optional sign and ASCII digits; a number-represented `Integer` beyond ±(2^53−1) throws `ParseError`.
- **Duplicate codes**: `TEST001` is an alias of `E-BOOL-1`, `TY009` of `E-DECL-2`, `FN001` of `E-DECL-6`, `FN014` of `E-DO-2`, `TY070` of `E-DECL-9`.
- **Functions**: an inferred return type is widened like a binding (`() => 42` returns an `Integer`); using a block-local function before its declaration is `E-DECL-1`; `=` on a parameter is `EFF006`. `let f = (x) => x` parses, and the analyzer reports `E-DECL-6` (the parser never rejects a semantic rule).
- **Widening** only turns literal types into their base type: an annotated `Integer(min = 0)` stays ranged.
- **Integer literals at a sink**: a literal out of the sink's range is `E-NUM-6`; `E-NUM-10` is for computed values certain to overflow. `W-NUM-2` (condition always true or false) fires only when the declared types decide it, never from facts; `W-BOOL-1` only on a literal `true`/`false` condition.
- **Check bits for the backends**: `SINK_CHECK` and `coercions[n]` sit on the arithmetic root (parentheses skipped); an n-ary sum like `a + b + c` is one node and `OVERFLOW_*` on it means "check every step". A sink check is only set when a value that passes the node's own overflow check can still miss the sink. `CONVERSION_CHECK` from an integer or `BigInt` sets `CAN_FAIL` (`ArithmeticError`); from a float it is a stop.
- **More duplicate codes** (object codes of the types brief map to the values brief): `TY005`, `TY011`, `TY014`–`TY019`, `TY022`, `TY024` and `WTY001` are aliases of the `E-OBJ-*`/`W-OBJ-1` codes, `TY020` of `E-OPT-1`, `TY023` of `E-DECL-4`; `E-CMP-9` of `TY057`, `TY085` of `E-CMP-2`, `CL001` of `E-DECL-11`.
- **`as` on a union member** whose data is not an object binds the data itself (`UserId.User as id`).
- **Object types** show their declared name in messages, while staying structural.
- **Generics**: an instance of a generic object type is shown as `Point(Float)`; `sort()` without a comparator binds `Order` to `Integer`. A function value given for a collection callback may leave out its trailing `index` (`FnSig::ignorable`); the native backend adapts the call.
- **Structural typing codes** (advanced brief §10 against the other briefs): `STR002` is an alias of `E-OBJ-1`, `STR008` of `E-OBJ-12`, `STR006` of `CL010`, `STR009` of `E-TYPE-1` (the types brief calls a nominal mismatch `TY002`); `STR003` is canonical with the alias `TY026` (an existing value without an optional field). A value without a required field is `STR001`, also for an argument that misses a field of an object constraint at a call (a type application keeps `GN010`).
- **Collections**: the methods of `GrowingSet`/`GrowingMap` resolve to the `Set#…`/`Map#…` built-ins; `C.from(…)` where the context already gives the type, with a list literal and no option, is `WCL001` even in the imported advanced-brief cases. A map read `map[key]` is flagged `INDEX_CHECK | CAN_FAIL` (`KeyNotFound`) until the presence proofs of types brief D32 (flow analysis) remove it.
- **Recursive types** keep one id per declaration: two declarations with the same unfolding (`Node`, `Link`) are assignable both ways (coinductive), not the same `TypeId`. A recursive reference is a `TypeKind::Rec` edge, boxed natively.
- **Methods of structural types** resolve on the type written for the receiver (its annotation, or the type of the literal it was built with), as advanced brief §10.1 says; a value without a written type uses the first declaration of its shape.
- **`Type(parameter)`** is an implicit generic parameter only when written in the signature; the other triggers of types brief §3.11.7 (an unannotated copy of the parameter, a single-expression body returning it) are not inferred yet.
- **`W-OBJ-1`** (type written twice) needs the same spelling: `let r: Round = Shape.Circle { … }`, with `Round = Shape - Shape.Point`, is not a repetition.
- **Narrowing**: declarations keep their declared type and only assignments narrow; verdicts about whether two types are compatible at all (`E-CMP-7`, `W-CMP-1`, equality typing) use declared types; verdicts about whether a value can be `none` at this point (`?.` `E-OPT-3`, `??` `E-OPT-6`, the second `??` of a chain included) use the narrowed type, since that is exactly what a narrowing states (lead, 2026-11-04), and name what narrowed it. Length facts hold until a mutating method or an assignment of the collection. A narrowed local in a place position (a method's receiver, the root of a field or item write, `op=`, a `mutates` argument, `use`) designates its payload, in the optional's or union's own slot (`NARROWED` in `analysis.rs`; native: `payload_place`, the slot itself for a nullable optional, its field 1 otherwise, the data of a union's box); the root of a field place has the narrowed type (`p.score = 1` after `if p is not none`). Natively, `use x = map.get(key)` is a nullable reference to the slot of the value (`map_get_reference`), and `is none` on a value narrowed already is false.
- **`catch`**: the handler's value takes the left operand's type as a hint only and the result is the union of both (values brief D-98); a `try` inside a `catch` operand is `E-ERR-6` and its errors go to that `catch`.
- **Codes**: `TY006` is an alias of `E-IF-2`, `TY025` of `E-CMP-4`.
- **Float printing**: a `Float` with an integral value prints without a fractional part (`20`, as JavaScript does), on every target (values brief D-5).
- **Enumeration members print** as their name only (`red`), as `Color.red.toString()` returns, on every target.

## JavaScript backend (second shift)

- Named union members are objects with `$t: "Shape.Circle"` (the qualified member name); data that isn't an object goes in `$v`, so it can't collide with a field. Private fields `#x` become `$p_x`; methods become `Type$name(self, …)`.
- `fa build` writes `build/<target>/main.js` next to the source (plus a `package.json` for `node`); `fa run` builds into `~/.cache/fa/run/<hash>/` and runs it with Bun.
- An explicit `none` given to an optional parameter that has a default must stay `none` (JavaScript default parameters can't express this: the backend must not use them for such parameters).
- **Optional parameters with a default** (JavaScript backend, second shift): such a parameter is a plain JavaScript parameter; its default applies when the argument is left out (`arguments.length`, so that a JavaScript caller omitting it gets the default) or is the runtime's `faOmitted` symbol, which a Fa call passes when it omits it before a given argument. Other defaults stay JavaScript default parameters.
- **Overflow checks off** on JavaScript: number operations are plain (precision is lost beyond 2^53), and the bigint-represented types (`Int64`…) are not wrapped either: they grow beyond their width, the cheapest choice; `wrappingAdd`… wrap explicitly. Divisor, index, shift and conversion checks stay.
- **Tuples** are JavaScript arrays (`(1, "a")` is `[1, "a"]`, what a TypeScript developer expects); since printing can't tell them from arrays, a value whose JavaScript representation doesn't say how it prints (tuples, enumeration members, `Float32`, percentages, and the arrays, optionals, maps and objects holding them) prints through a formatter generated from its static type, a module-level constant.
- **Ranges** are `FaRange` objects, copied like other composites (`copy$Range`); `for i in range` over a value iterates `faRangeValues`, which stops on a range without start.
- **Sets and maps**: a JavaScript `Set`/`Map` when the elements (keys) are primitives (SameValueZero is Fa's `==` there, and `NaN` is one element, as the case se-9 expects), the runtime's `FaSet`/`FaHashMap` otherwise and for a set with a `key` function. `Array.from`, `Set.from` and `Map.from` take any collection, a range or a string.
- **Structural typing**: a value stored as another object type (`coercions`) is copied with the target's fields only (`copy$Human`); `==` on an object type compares that type's fields (`equals$Human`).
- **Generic functions are erased** (one JavaScript function); a compile-time value parameter and a method required by a constraint are *hidden leading parameters* (`repeatText(times, text)`, `describeAll($Item$describe, items)`), given by each call from its instantiation and forwarded by an enclosing generic function. The analyzer doesn't type arithmetic on an `Integer | Float` parameter yet (`E-NUM-18`), so there is no per-member code.
- **Hot loops**: `a // b` and `a %% b` with a dividend proven `>= 0` and a divisor proven `> 0` are `a % b`, `(a / b) | 0` within 32 bits and `(a - a % b) / b` beyond; writes through a local array and index read them directly (no temporaries); a module value with a literal value is a module-level `const`. Inlining `faIndex` (`i >>> 0 < a.length ? a[i] : …`) was measured and gained nothing on Bun: the helper stays.
- **Minification** (`build.minify`, reviewer, 2026-11-02): `fa build --minify` minifies the module with `bun build --minify` (imports external, exports kept), about half the size (the 48 CLI programs: 284 KB to 146 KB, same output). It is opt-in for now: the configuration page gives `minify = true` as the default, while the architecture asks for readable output; the lead decides the default. Array locals: `local = place` for a `mutable` array of primitives that no loop iterates and no nested function reads copies into the local's own array (`faCopyInto`, fannkuch-redux). Re-measured: an inlined bound check (`i < a.length && i >= 0 ? a[i] : faIndex(a, i)`) is still slower than the `faIndex` call on Bun 1.4.

## Overflow checks (user request, 2026-11-02)

- **Default (user decision)**: like Rust, possible overflows are checked in development (`fa run`, `fa test`, `fa develop`) and NOT in release builds (`fa build`), where they wrap. `overflowChecks: Boolean?` in the build options and `--overflow-checks=true|false` override the default. The entry below describes the option itself.

- The user asked for a way to disable the overflow checks, by a compiler option or an `UncheckedInteger` type, at the lead's choice. **Decision: a build option**, `build.overflowChecks: Boolean = true` in the package configuration and `--overflow-checks=false` for `fa build`, `fa run` and `fa test` (standalone files). It applies to the code of the package being built, not to its dependencies. When off, the backends ignore `OVERFLOW_NATIVE`, `OVERFLOW_JS` and `SINK_CHECK`: native and wasm wrap in two's complement (plain `add`, never `nsw`, so no undefined behavior), JavaScript keeps plain number operations. Certain overflows stay compile errors; divisor, index, shift and conversion checks stay.
- **Why not `UncheckedInteger`**: a type would need its own arithmetic, conversions to and from every integer type, and would spread through signatures, while the explicit `wrappingAdd`/`wrappingMul`… methods already cover the per-operation need; the option has no syntax, keeps one way to write arithmetic, and is what a user reaches for when benchmarking.

## Analyzer (continued)

- **Facts of immutable module-level values** (amends design decision A11): a function body sees the facts established by the declaration of a module-level `let` value (its exact literal, its length, its range), since such a value can never change and is initialized before any function runs; it still sees no narrowing of captured places, and nothing about `mutable` module-level values. (Needed by the sort-objects benchmark: `syllables.length >= 1` inside a method.)
- **`Math`** holds only `max` and `min`, as documented; the other operations are methods of the numbers (`x.sqrt()`). Integer type constants like `Int8.minValue` have the literal type of the bound. Tuples are not ordered (`<` on tuples is `E-CMP-2`). A comparison like `c.length >= n` narrows the length of `c`. Iterating a `Range` with no start stops the program.
- **Parser diagnostics carry their code** (`fa_parser::Diagnostic::code`), so the analyzer no longer matches messages.

## Analyzer: flow, effects and references (E2, second shift)

- **Loops end with their bound**: after the widened fixpoint, up to two descending rounds walk the body again from the entry joined with the ends of the body (no widening); each such head is still a post-fixpoint, so the last round's diagnostics and bits are sound. `while i < 10 { i += 1 }` leaves `i == 10`. The value of a `loop` has the hull of its `break` values. `break`/`continue` in a lambda or a local function inside a loop is `E-LOOP-13`. A name of a `catch` handler hiding its error is `E-ERR-9`.
- **Effect codes**: the advanced brief's codes are canonical. `EF040`–`EF043` are aliases of `EFF008`, `EF044` of `EFF009`, `WEF001` of `EFF011`, `EF016` of `REQ001`, `FN070` of `REF021`. Where the types brief says `EF001` for a body changing a path of a root that has a declared, non-covering path (ef-2, ef-11), the code is `EFF004`. A temporary given to a mutated parameter drops the effect (advanced brief §3.5), so `EF012` is never reported.
- **Who declares effects**: a named function (or method) with a block body, or with written `mutates`/`invalidates`, must cover every effect of its body (`EFF001`–`EFF004`); a single-expression body without written effects, a lambda, a test and the top level infer theirs. `EFF011` is not reported when the body already has an uncovered effect. `mutates` of a whole module-level primitive is allowed (`EFF005` is for parameters).
- **Closures and effects**: a lambda's type carries only the effects written on it; its effects on the places it captures (and on module-level values) are effects of the code that creates it, applied where it ends (it runs inside the call it is given to). A local `function`'s are applied at each of its calls, and where it is given to a callee. A closure escapes when given to a method that stores it (`push`, `insert`, `set`, `add`), assigned to a place, or returned (an object literal field: not yet); an escaping closure writing a capture is `REF021`.
- **`mutates P` drops the facts at and below `P`** (advanced brief §5.5), the lengths of the collections there included; the facts above `P` stay (a write of an element keeps its array's length). The design's "length facts at or above" is superseded.
- **Array lengths**: `push`/`insert` add one to a local array's length fact, `pop` removes one (not below 0), `delete`/`take` one, `clear` sets 0; a call to a function that `mutates` the array forgets it.
- **Iterated collections**: an index below the length of the collection a `for` iterates (`for x, i in c { c[i] = … }`) is proven, since the iteration rule (`REF012`) keeps its length while the loop runs.
- **The alias rule** (`REF013`) compares each changed place with the other arguments' places; reading a `.length` or `.size` is never an overlap (`numbers.push(numbers.length)` is valid).
- **Writes through `for` variables**: a variable over an immutable collection can't be written: `E-DECL-3` as a whole, `E-DECL-4` below (values brief T-LOOP-43); `REF014` stays for read-only elements (set elements, map keys) and `REF015` for a `use` of an immutable place.
- **Brief corrections**: adv-5.13-02 and adv-5.13-27 write `try` before indices the analyzer can't prove (`people[0].pets[0]`); adv-5.13-29 calls its `main`; adv-4.5-02 also expects `W-BOOL-1` (`if true`); printed strings of the types brief cases lose their quotes (`console.log` prints the text).
- **`Analysis::arith` / `Analysis::intervals`** store interned `IntervalId`s (`Analysis::interval_values`); `Analysis::arith(n)` returns an `ArithInfo` by value, so the backends read them unchanged.
- **Requirements**: a key is the requirement's type (object types are structural, so two named types with the same fields are one key); a signature's requirements are sorted by the stable hash of their keys, the order of the hidden parameters. A `provide` is visible from its statement to the end of its block; a lambda sees the ones visible where it is written, a named function none (it declares or infers its requirements). A single-expression named function infers the requirements of its calls; a lambda passes them to the code around it. A mutated requirement needs a mutable provider (`REQ004`). `use first = list.get(0)` (and `map.get(key)`, `getOrInsert`, `find`, a pool's `add`) designates the element (advanced brief §5.3). Brief corrections: adv-9.9-02/03/08/09 repeat the declarations of the section's previous tests.
- **Moves** (advanced brief §6.2): the `MOVE` flag marks the read of a `let`/`mutable` local that is its last use and is a copy (the value of a declaration or an assignment, a returned value, an item given to `push`/`insert`/`add`/`set`), at the loop and function depth of the declaration, for an object, a collection, a string, a tuple or a union holding them. A read through a `use` alias, and a call of a local function capturing the local, are uses. Not yet: items of array literals and fields of object literals.

## Multi-file programs (analyzer E3, third shift)

- **Scan** (`fa-codebase-parser`, `Codebase`): one name table per folder, `(group)` folders merged, test files never names, `MOD001`–`MOD003` on the entries (a folder's on its first file). A standalone file's folder is its root; its own name and the invalid names of unused siblings are never reported. A package counts its top-level `.fa` files (configuration), `library/`, `application/` and `scripts/`.
- **Lookup through proxies**: before the walk, each name written in a file that the module system resolves gets a *proxy* symbol in an imports scope, the parent of the module scope: locals shadow it, it shadows the prelude (§15.3), and every lookup of the walk sees an ordinary symbol of the right kind. At the end of the walk, resolutions to proxies become `Resolution::External(module, declaration node)` (the `export` node for a file's export; stable across re-analyses) or `Resolution::Folder`; `Session::external` gives the file and symbol. `Resolution::Module(ModuleId, Sym)` is gone.
- **The file's export** is a symbol of the module scope named after the file, declared by the `export` statement and analyzed by the `let`/`function`/`type`/`namespace` handlers; a declaration with the file's name is `MOD004`. `MOD013` is an alias of `W-DECL-1` (the same warning). `arguments` stays the program's own implicit value.
- **Cycles between files**: a file whose analysis is in progress is read through the interface it published (each declaration done, then the whole file at its end); a declaration not published yet reads as `UNKNOWN` and marks the reader *deferred*; `analyze_program`/`analyze_package` walk every file again (at most 4 rounds) while one is deferred, each round reading the previous one's interfaces. Value cycles are `MOD007`, from the module-level graph (every value of the program is checked, through the functions it calls; only the values the entry, a script or the tests reach are initialized).
- **`Program`** is owned (no session borrow): `files` (dependencies first), `entry`, `init_order` (`(file, declaration)`), `tests`, `configurations`. `Session::analyze_program(module)` runs a standalone file or a script, `Session::analyze_package(entry)` analyzes every file of a package (D42); `Session::update(module, text)` re-analyzes the file, then its readers when its interface hash changed.
- **Configuration files** (D37) are evaluated, not walked: `fa_analyzer::configuration` checks the literal against the configuration types (`STR002` with the closest field, `E-TYPE-1`, `STR001`), `CFG007` for anything computed, and merges workspace and package per target (`PackageConfiguration::from_value` applies the defaults last). The CLI reads `entry` and `build.output` from it.
- **JavaScript** (§15.7, amends D10): one ES module per Fa file at its module path, the runtime helpers of the whole program in `$runtime.js`, and `main.js`, which calls each value's exported `$init<node>()` in `init_order`, then `$main()` (a program's top-level statements) and the exported entry function with the arguments. A declaration other files use is exported as its path joined with `$` (`counter$count`); namespace members are module-level declarations with that name; `#private` members aren't exported. Other files read an `export mutable` value through its live binding and **write it through an exported accessor** `people$ref.v` (the backend writes assignable places, which a setter call can't be). A standalone file that uses no other file and exports nothing keeps the single-module output.
- **`fa test`** (§18): `main.js` imports each test file's `tests` list and runs `faRunTests(tests, init)`: `init` re-runs the initializers before each test (D33); a false `assert` (a stop whose reason starts with `assertion failed`) fails the test, another stop also marks the rest of its file not run; all files run in one Bun process for now. `TEST004` with `only` on CI or the default branch (D34).
- **Calls across files**: a direct call of another file's function is `Callee::Value` (backends call the imported function), but its arguments are bound with the callee's parameter names and defaults (`Argument::Default` for an omitted one). A function of a type declared in another file is found as its method (`Session::type_origin`): a call `value.method(…)` is `Callee::Value` whose first argument is `Argument::Receiver`, the callee's last member resolved `External` to the function; JavaScript exports the functions of types as `Type$name`.
- **Not yet**: the native and wasm targets compile one standalone file (the CLI says so; `fa_codegen_llvm::compile` takes the `Program` later); the effects of the entry function (D51) wait for the effect checker (workspaces, `fa new workspace` and the process per test file of `fa test`: see "Workspaces, dependencies and development mode").

- **Entry function effects** (advanced brief D51): the function exported by a program file (a standalone file, a script) infers its effects like a single expression; a function of a namespace mutating a `mutable` member declares it (`mutates count`).

## Backends (after the backend review)

- **Minification**: `build.minify` keeps its documented default (`true` for `fa build` on JavaScript and WebAssembly); the generated code is readable before minification, and `minify = false` (or `--minify=false`) keeps it so. The CLI flag `--minify` from the review becomes `--minify=true|false`.
- **Unchecked overflow of sized integers**: with overflow checks off, integers of 32 bits or fewer (`Int8`…`Int32`, `UInt8`…`UInt32`, ranged types stored in them) wrap in two's complement on every target, JavaScript included (`(x << 24) >> 24`, `x >>> 0`, `x | 0`: cheap), so `Int8` 100 + 100 is −56 everywhere. `Integer` keeps plain number operations on JavaScript (precision is lost beyond 2^53) and the 64- and 128-bit `BigInt`-represented types are not wrapped on JavaScript.
- **Shared lowering**: logic both backends need (index normalization, which steps of an operator chain need a check, copy decisions, `when` bindings, argument evaluation order) moves into the analyzer's `lower/` helpers as backends are touched, so the two targets can't diverge.

## Analyzer: collections and relations (E1, third shift)

- **`Array#join(separator)`** exists on arrays of strings (and of string literals or characters); on other items it is `E-OBJ-5` with the `map(…toString())` fix, as `sum` on non-numbers is `CL024`. The documented string API was otherwise complete.
- **Iterators** (types brief §5.0.6): `values()` of every collection and `keys()` of maps give `Iterator(T)` (also writable as a type); `filter`, `map`, `firstValues(count = 1)` give iterators, `find`, `reduce`, `every`, `some`, `toArray()` consume them, callbacks receive the item only. A local holding an iterator is a reference into its collection (`REF001` after a change of it); a `for` over an iterator iterates its collection (`REF012`), and its variable designates the element when the chain has no `map`. `CL030` for an iterator type in a field, a collection element or a function result. On JavaScript, iterators are the engine's iterator helpers (`firstValues` is `take`), and `for x in array.values()` loops over the array.
- **`item, index`** on a collection without positions (a set, a map, a pool, an iterator) is `CL032`.
- **Effects by the receiver's kind**: a growing collection's methods share the paths of their counterpart (`Array#push`), and their effects come from the receiver's type: `GrowingArray.push` is `mutates self.length` and keeps references (ga-1).
- **Pools and columnars**: paths `Pool#…` (also `GrowingPool`), `Columnar#…` (also `GrowingColumnar`), `OrderedColumnar#…` (positional, the `Array` API with `add`); `from` exists for every collection kind (options per D59, `FN023` otherwise). `delete`/`take(element)` taking an element of another collection is the advanced brief's `REF020` (the parameter is `element: T in self`): `CL050` becomes its alias. A reference from `find` is `Existing(t)`, distinct from the fresh references of later `add`s (po-5). The alias rule also covers a callback reading a reference into the changed collection (po-12). `WCL002` for `let x = pool.add(…)`; `CL021` for a columnar of non-objects.
- **Proven negative indices**: a proven index that may be negative counts from the end on both backends (`at()` on JavaScript, `index + length` natively), as an unproven one does.
- **Map key presence** (D32): a literal map bound to a local proves its literal keys until the map changes; `if m.includes(k)` proves `k` (a literal or an immutable local) in its true branch; `m[k] = v` is `mutates m[k], m.size` (`REF012` in a loop over `m`), and writing a value through `for (key, value) in m` keeps the keys (ma-9 loses its `catch`). String keys have their own identity, so `delete("bao")` keeps a reference to `get("ana")` (ma-6).
- **Nested types**: a `type` declared inside an object type is hoisted in the type's scope (`type Town = { people: Pool(Person) = [], type Person = { … } }`); it is not one of the type's functions.
- **Relations** (advanced brief §8): a direct side is typed `T?`, a reverse one-to-one or symmetric side `T?`, a many-to-many direct side `Collection(RelationPool(0), T)` (writable: `add`/`delete` return whether something changed, `clear`), a reverse pool `Collection(RelationPool(1), T)` (read-only, `REL010`). Relation fields are left out of literals (a new element starts unlinked). `T in c` as a type elsewhere (a parameter) is `T`, and the parameter is a reference. Pairing happens at the end of the file; `REL001` is not reported for a direct side whose reverse side was already reported (`REL007`, `REL009`); `REL003`/`REL019` are reported on the direct side only. `Analysis::relations`, `relation_fields`, `relation_writes` and `relation_unlinks` give the backends the relations, the written sides and the removals to unlink (see `analysis.rs`).
- **Not yet** (relations): owner-path substitution in reference types (`(T in o.C)?`), `use` of a relation field designating the target, the linked list of the relations page (adv-8.10-15: references returned by a function, `invalidates` of a reference parameter). The native backend lowers pools and columnars since its third shift, relations since its fourth. Implied effects: see "Implied effects of relations" below; relations across files and reactivity: "Relations across files and reactivity".

## Compile-time evaluation (interpreter, advanced brief §12)

- **The crate**: `fa-interpreter` (`packages/interpreter`) knows nothing of the analyzer: it evaluates *lowered* code (`ir::Expr`, functions named by opaque keys) through a `Host` trait. The analyzer lowers its checked tree (`comptime/lower.rs`: slots, globals, calls in parameter order, arithmetic carrying the range of its result under the target) and is the host, so `fa-analyzer` depends on the interpreter and every analysis can evaluate (no host to install). Values are copy-on-write (`Arc` + `make_mut`), `Send`, plain data the backends embed.
- **Evaluation happens in the walk**, once per construct: a `static` when its declaration is analyzed (on demand when hoisted), an `@` call after its call is checked, an `@if` condition, an `@for` iterable, an `@test` body after it is checked; the functions they call are analyzed by then (on demand) and lowered lazily (memoized per session). A function whose analysis is still in progress (a cycle through compile-time code) can't run: `AN001`.
- **Bounds** (D26): one step per evaluated lowered expression, 100 million per evaluation; nested calls are bounded at 10 000 (`META003`, like the steps), evaluated on a thread with a 1 GiB reserved stack so that the depth, not the compiler's stack, is the limit; 256 nested type-function applications (`META004`).
- **Purity** (`META002`) is checked statically before running: the lowered code and every function it may reach (transitively, memoized) must not contain an impure primitive: `console`, a module-level `mutable` (read or written), a requirement, `arguments`, `provide`. Throwing is allowed: an uncaught error is `META005` with the error's `toString()`; a stop (a failed `assert`) is `META005` too; an integer overflow is `META013` (D49: on a JavaScript target an `Integer` is bounded by ±(2^53 − 1), `Int64` and wider by their width).
- **What is known at compile time** (`META001`): in a `static` value, the arguments of an `@` call, an `@if` condition or an `@for` iterable: literals, statics, `target`, `configuration`, `@` operations, and the locals declared inside the expression itself (a `do` block, a lambda's parameters). Module-level `let` values are not (the brief's `let count = readInput(); @add(count, 4)` is `META001`), but a function called at compile time may read immutable module-level values (evaluated once, their initializer pure). A call without `@` inside a `static` value is evaluated too (the `@` marks where evaluation starts, and the whole value is compile-time already). In a `static` value an error is a compile error, so no `try` is needed there.
- **The type of a static** is its annotation, else the exact type of its value (`comptime::exact_type`: literal scalars, objects of exact fields, arrays of the union of their items, widened beyond 8 distinct items), except a value of a named type (an object type with a name, a union, an enumeration), which keeps it so its functions apply. A static holding a function is `AN001` for now.
- **`@if` / `@for`** (D22): only the kept branch of `@if` is analyzed; `@for` is analyzed **once** with the variable typed by the items' type, and unrolled by the backends (`Analysis::unrolled`). Per-item analysis (an `@if` or an `@readFile` on the loop variable inside the body) is not supported yet. An `@for` over a range bounded by a compile-time parameter of a generic function stays a loop (the parameter is known per instantiation; the generic body is checked once).
- **Per-target analysis** (D22): a session analyzes for one target (`Session::set_target`, `bun` by default; `fa build --target=…` and the LLVM backend set theirs, `native-freestanding` is `native`). `fa check` analyzes again for each other target of the configuration (`web`, `bun`, `native` for a standalone file) only when a file read `target` or `configuration` (`Analysis::reads_target`), and adds the diagnostics not already reported, with the target named.
- **`configuration`** is the configuration merged for the target over the defaults of `PackageConfiguration` (`configuration::defaults`), typed exactly (an optional field that isn't written is absent from its type); a standalone file sees the defaults.
- **Build inputs**: `@readFile`/`@readDirectory` paths are relative to the reading file's folder and stay inside the root (`META008`; absolute paths and `..` beyond the root), missing is `META009`; the module resolver reads them (`ModuleResolver::read_input`/`list_input`, in-memory files for tests); the paths read are `Analysis::build_inputs`. A `@readDirectory` entry's `path` is the argument joined with its name (D28).
- **`@typeToString(T)`** is the spelling at the use site (D49, `check/spelling.rs`): a name as written with its arguments (`UserId`, `Point(Integer)`), an anonymous type in the order it is written, a type built by a spread (directly, or a type function of one applied) as its fields in spread order; the rest as displayed. The brackets of type applications come from `types::display::ARGUMENT_BRACKETS` (the `<…>` flag day changes that constant); **`@typeToSchema(T)`** builds the `Schema` value of `types/types-at-runtime` (`Schema.Named`, `Schema.Object`…), but `Schema` is not a prelude type yet: its static type is unknown, and `TypeFromSchema` is not implemented.
- **Type functions with logic**: `if` on a value parameter, `when` on a type parameter (`is`: the whole type satisfies the pattern) and `do` (its last expression) are checked generically at the declaration and *selected* at each application, the condition evaluated with the value parameters bound.
- **`@test`** runs while checking a test file (`fa check`, `fa test`); a failure is `TEST003` at the test.
- **Computed configuration files** (replaces `CFG007` of D37): when the literal evaluator finds a computed export, the file is walked like a program (it sees `Target` and its own `let`s and functions) and its export is evaluated on the interpreter, then checked against its configuration type as before; only a value a configuration can't hold (a function, a map) is an error.
- **Backends**: JavaScript emits constants (scalars, strings, arrays, tuples, objects, primitive sets and maps; members and ranges not yet), nothing for a `static`, the kept branch of `@if`, and the body of `@for` once per item in a block binding a `const`. LLVM (minimal hook while it is reworked): scalar and string constants, `static` declarations and `@if`; `@for` and composite constants are unsupported there.
- **Brief corrections**: adv-12.8-12 names its function `spin` (`loop` is a keyword); adv-12.8-03 stays pending (`std.time` isn't in the prelude); adv-16.5-02 now computes its configuration (no `CFG007`). Spreads in array literals (`[...targets, "bun"]`) are analyzed (needed by the configuration guide).

## Formatter (`fa format`)

The formatter is `fa-formatter` (`packages/formatter`): it parses a file and prints the tree back, with every comment of the source. It refuses a file with a syntax error. `fa format [<file or folder>...] [--check]` formats the given files, every `.fa` file of the given folders (without the hidden folders, `build`, `node_modules` and `target`), or, without a path, the workspace or package of the current folder; `-` formats the standard input. The language server answers `textDocument/formatting` with it (one edit of the part that changes; the editor's tab size is ignored).

- **Width**: 100 columns, a tab counting for 4 (like the TypeScript code of the repository). Lines are indented with tabs. A line stays longer when it can't be broken (a string, a `-` chain, a trailing comment, which never counts in the width).
- **Breaking**: a call, a parameter list, a list, an object (literal or type) or a pattern is written on one line if it fits, otherwise with one item per line and no commas (syntax basics: newlines separate items). The one exception: an item starting with `.` (an implicit member) or with `in` keeps a comma before it, since such a line would continue the previous one.
- **Written over several lines**: an object, an object type, a list, an object pattern, a block of one statement and a chain of calls written over several lines stay over several lines; written on one line, they stay on one line when they fit. Calls, parameters and operations only follow the width. So both `let point = { x = 1, y = 2 }` and the broken form are formatted, as the syntax basics page allows ("pick one style per literal").
- **Blocks** are written over several lines, except a block of a single statement written on one line (`if valid { level } else { 0 }`), and likewise a `when` of a single branch written on one line (`when V is { String => Integer }`). An empty block, object or list is `{}`, `[]` (the documentation used `{ }` and `{}`).
- **Operations** break before their operators (a line starting with an operator continues the previous one): `isAdmin` then `or isOwner` on the next line, like the chains of calls. A subtraction never breaks (a line can't start with `-`), nor `..`, `->` and the `in` of a reference type; a union breaks only as the value of a type declaration, the arguments of a type (`Map(String, Integer)`) never. An operation with an operand that holds a block (`a + do {`) keeps its operators on their lines.
- **Signatures**: a return type and the `throws`, `requires`, `mutates`, `invalidates` clauses written on one line stay on one line; when the signature doesn't fit, its parameters break first (`(` / `request: Context` / `): { ...Context, ...Logged } => {`), as Prettier keeps a return type whole. A list, an object or a lambda written over several lines as the last argument hugs the parentheses (`Task.all([` … `])`).
- **Chains of calls** (`users.filter(…).map(…)`) with two calls or more break before each `.` when they don't fit (or were written so).
- **Lambdas**: a lambda with a block, an object or a list as the last argument of a call hugs its parentheses (`items.map((item) => {`), as a lambda with a block as the first argument (`setTimer((item) => {`, `}, 30)`). A body after `=>` (of a lambda, a `catch`, a `when` branch) that doesn't fit goes to the next line, indented, unless it opens a block.
- **Comments** are never dropped. A comment keeps its place: on its own line before a statement or an item, at the end of the line of the code before it, after an opening bracket (`for item in items { -- error: …`). One written where no line can end (`let a = -- note` then `5`) moves to the end of the statement (`let a = 5 -- note`). The lines of a block comment are re-indented with the code. A trailing comment follows the code after one space, and the comments ending consecutive lines are aligned in a column (lead's arbitration below).
- **Blank lines**: at most one between two statements, items or comments, none at the start or the end of a block or of the file; a file ends with one new line. The blank line between a comment and a declaration is kept, since it decides whether the comment documents the declaration.
- **Literals** are kept as written: the digits of numbers (`0xFF`, `1_000`, `1.5e9`), the escapes of strings, the lines of a multi-line string. `\r\n` becomes `\n`, in strings too (strings page). Parentheses are kept as written.
- **Canonical rewrites** asked by the documentation (`Options::rewrites`): `Percentage(width + margin)` is `(width + margin)%` and `Percentage(50)` is `50%` (numbers page); `score is in 0..60` is `score is 0..60` (ranges page); `-2.4.abs()` is `(-2.4).abs()` (numbers page); `({ name, greeting }: { name: String, greeting: String })` is `({ name: String, greeting: String })` when the pattern lists the fields of the type without renaming them (defining functions); `let point: Point = Point { … }` is `let point: Point = { … }` when the two types are written the same (declaring types); `when` branches separated by commas go on their own lines; `a-1` is `a - 1`.
- **Field shorthand**: `{ id = id }` is written `{ id }` in object literals (not in types), since the objects page makes the shorthand the way to write it.
- **Not done**: `Array.from(…)` where the context gives the type (arrays page) needs the types of the analyzer, which the formatter doesn't run.

## JavaScript backend (third shift)

- **References** (`codegen-js/src/generate/references.rs`, advanced brief §6.6): `use x = place` of an object or a collection (optional or not) is `const x = place` (the JavaScript reference); `mutable use` is a `let` that `reuse` reassigns. A primitive place (numbers, strings, unions, enumerations) is never boxed: the container and the key are evaluated once (a local name stays a name, since reading it again reads the same Fa place; an unproven index is checked and normalized once), each use of `x` is the place (`player.score`, `items[$t0]`, `counts.get($t1)`, written with `counts.set`); a `mutable use` of one is a pair of `let`s `x$o`, `x$k` that `reuse` reassigns (`reuse x = none` empties `x$o`). References returned by `map.get`, `map.getOrInsert` and `array.get` are places too; other calls returning a reference to a primitive (`find` on an array of numbers, user functions) are `AN001` for now. A `mutable use` of a whole primitive local is `AN001` (JavaScript can't designate a local). A module-level reference read by functions keeps its pair in module-level `let`s, prepared before the functions are generated.
- **In-place writes (D60)**: a whole write of an object or a collection through an object reference, or into a place whose root a `use`/`mutable use`/`reuse`/`provide` of the file designates, is `faAssign(place, value)` (fields assigned, nested objects of the same kind kept, collections' contents replaced); other places, union and optional places, and values of maps are replaced. The roots are computed once per file (conservative: no flow); a `for` variable doesn't make its collection a root (a whole write of an item of the collection a `for` iterates, while the variable is live, is the one case left).
- **Map values as places**: `map[key] op= value` reads the value (`KeyNotFound` when not proven present) and writes it with `map.set` (it wrote a JavaScript property of the `Map` object before: a silent bug).
- **Requirements**: hidden trailing parameters in `FnSig::requires` order (the body's `Requirement { index }` symbols take their names; an inferred requirement gets the requirement's name). A call passes `Analysis::requirement_args`: a `provide` of a composite value or of a computed one is a `const <key>$p` evaluated once at the statement; a `provide` of a primitive place is read again at each call (an alias, so a later write of the place is seen); `Own(key)` is the innermost enclosing function's hidden parameter of that key (lambdas see it as a JavaScript closure). With hidden arguments every regular slot is passed (an omitted argument as `undefined` or `faOmitted`). With a variadic parameter, the hidden arguments follow the variadic ones and the function takes them off the end of its rest parameter (`const [logger] = names.splice(names.length - 1)`).
- **Escaping closures** (`Analysis::escapes`): before the closure, each capture that may change after its creation (a `mutable` local, a `for` variable over a collection, a reference) is copied into a `const name$copy` (the generated copy function for a composite), which the closure reads. Top-level values of a standalone file are module values, never captured: an escaping closure sees their later writes.
- **Moves** (`MOVE`, D15): a read flagged `MOVE` is never copied (bindings, assignments, returns, items given to `push`/`add`), and doesn't go through `faCopyInto`.
- **Pools and columnars**: a `Pool`, `GrowingPool`, `Columnar` or `GrowingColumnar` of objects is a JavaScript `Set` of these objects (as `collections/pools.md` says for pools): a reference is the object, `add` is `faAdd` (stores and returns the element, a copy of a value read from a place), `delete(element)` and `take(element)` go by identity, iteration is insertion order (the slot order of a fresh columnar), a copy copies each element. An `OrderedColumnar` is an array of objects with the array's methods (`add` appends). The column layout of `collections/columnars.md` (typed arrays per field, slot indices as references) is not implemented: the `Set` gives the same observable semantics, at the cost of the single-field loops' speed. Pools and columnars of primitive values are `AN001`. Brief correction: po-7 adds the three humans its comment says the pool holds.
- **`for (key, value) in map`** is `for (const [key, value] of map)` (`Map` and `FaHashMap` both iterate entries); a value written through the loop variable (ma-9) is an alias of `map.get(key)`, written with `map.set(key, …)`.
- **Relations** (advanced brief §8.8, `codegen-js/src/generate/relations.rs`): the sides are properties of the elements: a direct side, a reverse one-to-one side, a symmetric side and an owner field hold the object or `undefined`; a many-to-many direct side and the `Pool` reverse sides a `Set` (`new Set()` in every new element). A write in `Analysis::relation_writes` is `faRelateOne(holder, direct, reverse, target, many)` (one-to-many, one-to-one, symmetric) or `faRelateAdd`/`faRelateDelete`/`faRelateClear`; an owner field is a plain write; a literal given to `add` that sets direct sides is linked right after `faAdd`. A removal in `Analysis::relation_unlinks` calls `faUnlink(element, table, owner)` first, the table (a module-level constant) giving per relation its kind and the role of the removed element (holder or target: the relation's collections are matched with the receiver by field name or module declaration); `clear` unlinks every element, `deleteWhere` each one its predicate keeps out. A relation side given in a literal is a reference, never copied, and so are the items of a many-to-many side's list (`friends = [ana]`, D19: `new Set([ana])`, then linked). A copy of an element resets its sides (no links, D18), including a `let` of an element read from a place, which the D15 rule would otherwise share; `faUnlink` empties the sides of the element it unlinks, so `take` returns an element without links; a copy of a type owning related elements is `faCopyGraph` (every object copied once, links relinked to the copies, §8.5). Printing and `==` skip the sides (D21): such a type always gets a typed formatter. Brief correction: adv-8.10-12 moves its comment off the `prints:` line.
- **`fa build` minifies by default** (decision above): `--minify=true|false` (a bare `--minify` is a usage error that names both), the package's `build.minify` otherwise, every module of a program minified separately (imports external). Without Bun, the default build stays readable and says so; an explicit `--minify=true` fails.
- **Wrapping without overflow checks**: a value the analyzer range-checks at a sink (`SINK_CHECK`) of 32 bits or fewer wraps there (`(x << 24) >> 24`, `x & 255`, `x | 0`, `x >>> 0`), like native code truncating its `i64` result; a two-operand product wrapped to 32 bits is `Math.imul` (exact beyond 2^53); compound assignments wrap their result. Tested by `overflow-wrapping.fa`, which also runs natively.
- **Size**: `faFormatError` prints the fields of an error with `faQuote` and `String` only (the runtime's errors hold numbers and strings), so throwing or reporting an error no longer brings the whole printer: one `Integer.parse` program goes from 7.4 KB to 4.8 KB (3.7 KB to 2.5 KB minified). A generated error class with composite fields overrides `toString` with `faFormatErrorFields` (the generic printer). `a // b` and `a %% b` with a divisor proven non-zero call `faFloorQuotient`/`faFloorRemainder` (and the bigint ones), without the zero test nor `DivisionByZero`. Removed, never emitted: `faLog`, `faLogError` (`console.js`), `Cancelled` (no program can build one yet). `faAssign` is now emitted (D60) and tested.
- **JavaScript `when` of 64 arms or more**: an `else if` chain is a nested statement for the JavaScript parsers, and Bun overflowed its stack on 20,000 arms. From 64 arms (`FLAT_WHEN_ARMS`), a `when` is a `switch` on the subject when every test compares it with a constant (a literal, an enumeration member, `none`) and no arm has a `break` (which would leave the `switch`), otherwise a labeled block of `if`s, each arm ending with `break $label`. Shorter `when`s keep the `if` chain.
- **JavaScript 64-bit integers stay bigints** (checked for the Goose suite): the `UInt64` values of its xorshift generator, of FNV-1a and of the seeds use the whole 64-bit range (the analyzer's intervals are the full type), so no rule "a sized integer whose interval fits ±(2^53 − 1) is a number" applies to them, and none was implemented. Cheaper bigint code instead: a shift by a proven amount is inline (`BigInt.asUintN(64, v << 13n)`, `v >> 7n`, `13n` for a literal amount; it built a `BigInt` of the amount and went through `faBitwiseResult`), `bitNot` too, and `a %% b` / `a // b` with `a >= 0` and `b >= 1` proven are `a % b` and `a / b`. Each bigint operation still allocates on the heap (about 1 µs per xorshift step on Bun): a representation of 64-bit values as two 32-bit numbers would be about 4 times faster, but changes every place a 64-bit value crosses.
- **Bun memory of `push` and `sieve`**: `sieve` keeps its `Uint8Array` (123 MB peak RSS at the default size; its failure was the memory of the parallel run). `push` still fails under a 4 GB address-space cap: its 32 million items alone take 1.56 GB, but the generator's dead bigints (about 9 per item) make the heap grow past the cap before a collection; the items' representation is not the cause (a class or a literal take the same 50 bytes per item).
- **Shared lowering, first helpers** (`fa_analyzer::lower`): `index` (`IndexAccess::{Checked, FromEnd, Direct}`, and the interval of an index), `copies` (place roots, conditional values, `MOVE`, the D15 decision, given whether the type owns memory on the target), `calls` (the written position of each argument value: the order of evaluation), `when::arm_bindings` (the names an `as` binds, paired with fields by name: the JavaScript backend paired them by position and scanned every symbol per arm). The JavaScript backend uses all four; the LLVM backend can adopt them as it is touched. A proven index that may be negative is now read with `items.at(i)` (it went through `faIndex`).

## JavaScript backend (performance)

Measured on Bun 1.4 against the benchmarks of `benchmarks/` (medians, A/B in the same session); each rule keeps the observable semantics and has a golden test (`codegen-js/tests/golden/performance.fa`) and an end-to-end program (`cli/tests/programs/fast-paths.fa`).

- **Byte arrays** (`generate/typed_arrays.rs`): a `mutable` local `Array(Boolean)` declared empty (`[]` or `Array.from([], capacity = …)`) and filled by the next statement, `for 0..n { flags.push(<literal>) }`, is a `Uint8Array` (`new Uint8Array(Math.max(n, 0)).fill(1)`; `Math.max` left out when `n` is proven non-negative) when every other use, in the function that declares it, is an item read, an item write (`flags[i] = value`) or `flags.length`: no method, loop over it, copy, argument, return, print, capture by a nested function, reference, compound or whole write. A read is `flags[i] === 1` (a `Boolean` again), a write stores `true`/`false` as `1`/`0`, and the index checks (`faIndex`, `faIndexSet`, `at`) work on typed arrays: nothing outside the function sees the typed array. The sieve's 100,000,001 flags take 100 MB instead of 800 (1.6 GB of peak memory with the growth copies): from 4.2 to 1.2 times Rust's time. Other typed arrays are not used: JavaScriptCore already stores an array of `Float`s unboxed, and an array given to a function (nbody, spectral-norm) would need an interprocedural rule; the columnar layout of `collections/columnars.md` stays unimplemented for the same reason.
- **Quotients by a power of two**: `a // 2^k` (a constant divisor, `k` ≤ 52) with a dividend that may be negative is `Math.floor(a / 2^k)`, exact since the division only changes the exponent (spectral-norm: from 3.0 to 1.5 times Rust's time); the non-negative case keeps `(a / b) | 0` and `(a - a % b) / b`.
- **Sorting**: `faArraySortInPlace` (and `sort`, which copies first) is a stable merge sort written in JavaScript (insertion-sorted runs of 16, then merges), no longer `Array.prototype.sort` through `faComparator`: Bun calls a comparator from C++ while it inlines it into JavaScript, 25 % faster on sort-objects' million records (with the other changes, from 5.7 to 4.6 times Rust's time: the rest is the cache misses of a million objects and their strings). The comparator's sign decides (a number or a bigint, NaN equal); the items are sorted in a copy written back at the end, so a comparator that throws leaves the array unchanged. The natural order of number-represented integers is `faSortIntegers` (a `Float64Array` sort copied back, without comparator calls: 450 ms to 30 ms for a million; equal integers are indistinguishable, `-0` is the integer `0`), of floats `faSortFloats` (`a - b`, which is `faCompare` on numbers, NaN included), of strings `faSortStrings` (the merge sort with `faStringCompare`).
- **Strings**: `faStringCompare` walks the code units and reads code points only when the first difference is between a surrogate and a unit above `U+D7FF` (it ran two regular expressions per comparison); `faIsSimpleText` tests a text of 256 units or more with `TextEncoder.encodeInto` by chunks of 16 KiB (ASCII when each unit took one byte, then no `\r`), fifteen times faster than the regular expression; `faStringSplit` of a simple text is JavaScript's `split` (every position is a boundary); `padStart`/`padEnd` are JavaScript's methods when the receiver and the filler are proven simple (ASCII literals without `\r` or `\`, numbers and booleans converted by `toString()` or interpolated, templates of them). string-building: from 2.0 to 1.65 times Rust's time.
- **Measured without gain, not done**: `map.getOrInsert` with one lookup fewer (word-count's time is JavaScriptCore's `Map`: hashing fresh rope keys and the cache misses of a 100,000-entry map, 300 ns per access against 40 ns for an array); indexed loops instead of `for…of` over arrays of objects (nbody); `faArraySortInPlace` without `faComparator` but still native (9 %, below the merge sort's 25 %). fib, mandelbrot and nbody are plain number code already: what remains is the engine's (boxed fields of objects, calls).

## Formatter (lead's arbitration)

- **Trailing comments are aligned** in a column over a run of consecutive lines that all end with a comment (like `gofmt`), as the documentation writes them; a blank line, a line without a trailing comment or a change of indentation ends the run (lead's decision: like `gofmt` within a block, so the alignment never depends on the width of a tab). (Overrides the first version of the formatter, which didn't align them.) Done after printing (`document::align_trailing_comments`): the comments don't count in the width, so the layout doesn't change.
- **Empty braces** are written `{}`; `{ id = id }` becomes `{ id }`. Examples meant to show a warning are formatted like any code.
- `=> { ...request, auth = "t" }` is a block (the reference: a lambda body `=> { … }` is a block), not an object literal: write `=> Request { ...request, auth = "t" }`.

## Reactivity

- A function that receives a reactive place gets one extra JavaScript instance `name$r`, taking a source per parameter (`null` for a plain argument), not one instance per combination (advanced brief D24). A watch's cleanup copies the reactive values it reads. Writing a map entry notifies the map's size only when the size changed.
- **Natively** (`src/lower/reactivity.rs`, the "reactivity" section of `fa_runtime.c`, fourth native shift): the same push-pull algorithm. A `reactive` value's source is in a global (top level) or an alloca; a `reactive` field's source is kept by the runtime per object address. `derived` and `watch` bodies are functions of their observer, reading the locals around them through an environment of pointers, or of copies for `mutable` locals not read for their reactive fields (made when the observer is declared); a derived value keeps its value in a block of its observer. A function given reactive places is **one** function, not two instances: its callers set the sources of its parameters in the runtime right before the call (null for a plain argument) and it reads them as it starts. A `watch` outside the module's top level is disposed by a cleanup of its block. Sources and observers are freed at the end of the program only (a disposed watch block stops running; a loop creating watch blocks keeps their memory until then). The 100-round stop prints the JavaScript message.
- **Disjoint references** (native, `src/lower/aliasing.rs`): `for body, i in items { for j in i + k..… { use other = items[j] … } }` (a literal `k ≥ 1`, `items` a local not assigned in the loop) gives the loads and stores through `body` and through `other` two alias scopes that exclude each other, declared again at each round of the outer loop (`llvm.experimental.noalias.scope.decl`): LLVM keeps `body`'s fields in registers across the inner loop (nbody).

## Workspaces, dependencies and development mode

- **Selection** (D44): `check`, `build`, `test`, `develop`, `preview` (and `run`) take a `.fa` file, a folder, or the `name` of a package of the closest workspace (`CLI004` lists the packages). Without one, the closest `package.fa` or `workspace.fa` above the current folder decides: a package alone, or every package of the workspace that implements the command (`check`/`format` all, `build`/`develop`/`preview` those whose entry file exists, `test` those with a `*.test.fa` in `library/` or `application/`); each one is announced on stderr (`fa check: package `api` (packages/api)`), and the command fails with the first failing code. Package names must be unique (`CFG004`); a `package.fa` inside a package is `CFG006`. `fa new workspace [<name>]` writes `workspace.fa`, `dependencies.fa` and `packages/` (D46).
- **Dependencies as mounts**: the CLI resolves the dependencies, then gives the analyzer a `fa_analyzer::mounts::MountedResolver`: the package's own files, then its keys, each dependency mounted under the module prefix `$dependencies/<id>/` (`shared`, `farm@4.2.1`, `<file>-<hash>` for remote code), with its own keys. A key resolves to the `library/` folder of a package or repository, the export of a remote file, or the root of a remote folder; the dependencies of a dependency are only visible in its files. The JavaScript backend writes the dependencies' modules under `$dependencies/` next to the others. A key that is a root entry name is `DEP005`; a dependency whose `package.fa` doesn't list the target is `DEP009`.
- **Sources**: `"../x"` must be a package of the workspace (`DEP008`); outside a workspace, a folder holding a package (below). Git: `github:o/r@range`, `gitlab:o/r@range`, `git+<url>@range` (the `@` of a user name is not a range); remote: `https://`, `http://`, and `file://` (for tests and local mirrors). `DEP004` for an unversioned Git source or URL (a URL is versioned when it holds `1.2`, `@1` or `v1`). A `DependencySource` object with `generate`, and a computed `dependencies.fa`: see "`DependencySource.generate`" below.
- **Resolution** (§17.2): all the packages of a workspace are resolved together (one lockfile at its root, one version per repository and major for the whole workspace); a package outside a workspace has its own lockfile. A locked version is kept while it satisfies every range of its major; otherwise, and for `fa update`, the mirror's tags are read (the mirror is fetched again when no tag fits). `fa update <key>` re-resolves the repositories and URLs that key names (every major of a repository). Unused entries leave the lockfile. Tags `4.2.1` and `v4.2.1`; a tag whose `package.fa` has another `version` is `DEP003`.
- **Lockfile and cache** (D45): `dependencies.lock` is written only when it changes (never created for a program without remote sources), sorted by source then version. The cache is `$FA_CACHE`, else `$XDG_CACHE_HOME/fa`, else `~/.cache/fa` (`~/Library/Caches/fa`, `%LOCALAPPDATA%\fa`): `git/<hash of the URL>.git` mirrors (`git clone --mirror`, `git fetch`), and `sources/<sha256>/` the content (Git: `package.fa`, `dependencies.fa`, `library/` of the commit, read with `git ls-tree` and `git cat-file`; a remote file: its bytes; a remote folder: `manifest.fa` and its files), written to a new folder and renamed. Every command checks the cached content against the lockfile's hash (a damaged entry is fetched again); content fetched again that differs is `DEP001`, named by its key. Remote URLs are fetched with `curl`. SHA-256 is implemented in the CLI (`sha256.rs`) to avoid a dependency. `FA_GITHUB_BASE` / `FA_GITLAB_BASE` replace the hosts (tests).
- **Development mode**: `fa develop` polls the files (150 ms, `FA_WATCH_INTERVAL_MS`) of the package, of the workspace packages it depends on and the root files of its workspace; an edit of its own sources goes through `Session::update` (the file, then its readers), anything else (a file added or removed, a configuration file or the lockfile, another package) reloads the package. Without errors, the changed modules are swapped in the running program when possible (hot reloading, below), else it is compiled again and **restarted**, with the reason; with errors, they are printed and the running program is kept. `--target=web` and `--target=native`: below. `fa test --watch` reuses the watcher and runs every test of the package again (not only the affected ones). `FA_DEVELOP_RUNS=<n>` ends the command after `n` runs (tests).
- **Hot reloading by module swap** (D43, `src/hot.rs`): `fa develop` generates a development build (`fa_codegen_js::Options::hot`): every module reads the declarations of the other modules through a registry entry per module (`import * as $h$m from "./greet.js"; const $h = faHotModule("library/greet.js", $h$m)`, uses `$h.ns.greet(…)`: two property reads per use, development builds only; ES live bindings can't be repointed), and `main.js` registers the modules with values and connects to the channel of `fa develop` (`faHotListen`): a local TCP socket on 127.0.0.1 whose port `fa develop` gives in `FA_HOT_CHANNEL`, the same mechanism on every system (no signal, so Windows works; the program's stdin stays its own; the socket is `unref`'d and doesn't keep the program alive); a request is the line `swap`, its answer a line of JSON. While the program runs, an edit of the package's own sources (no file added or removed, no configuration, lockfile or other package: those restart as before) is analyzed incrementally and the whole program generated again; the modules whose code changed are swapped when (1) they are all edited files: a change that reaches the code of another module (renamed or removed export, other union tags…) is an interface change, (2) the type declarations of the edited files have the same text: values of the old shape may be kept elsewhere, (3) the program has the same modules and the same runtime helpers (`$runtime.js` is not swapped), (4) it has no worker, (5) no swapped module has `watch` blocks (they would run next to the old version's). Otherwise it restarts and says why (`restarting (a type of `library/greet.fa` changed)`). A swap writes the new modules next to the old ones (`greet.hot<N>.js`) and `$hot.json`, asks Bun on the channel, which imports them, points the registry entries to them and calls, in initialization order, the initializers of every value of a swapped module, of the values whose initializers read one of those (`Session::initializer_reads`), and of the values new to the program; the other values keep theirs. A failure (an initializer that throws, a module that doesn't load) or no answer in 10 s restarts. Code already running in an old module (a loop of the entry function, a closure) keeps its version: only the calls through the registry reach the new code. `develop.hotReload = false` restarts. **Reactive state** survives by declaration path (`<module path>#<name>`): the source of a module-level `reactive` value is kept (`faHotKeep`: its observers stay subscribed), and the initializer of a swapped module's `reactive` value takes the value of the previous version (`faHotValue`) instead of running. **Tests**: after a swap, or a restart or new run caused by edits of the package's own sources, the test files that read an edited module (directly or through other files, `Session::readers`; an edited test file itself) are compiled and run, each in a Bun process (`run_test_processes`), while the program goes on; the granularity is the test file, not the declaration. Fixed on the way: a module-level `reactive` or `derived` value was not in the interface (`check/interface.rs`), so the initialization order skipped it and a function of its module read it uninitialized in a program of several files.
- **`fa develop --target=web`**: the hot web build is written into the cache and served by a development server (`src/develop_server.js`, run by Bun) on `develop.port`, with no-store headers: `/` is the build's `index.html`, else a page loading `/main.js`. The pages connect to the WebSocket `/$fa-hot` (`faHotListen` in a browser), and the server connects to the channel of `fa develop`: a `swap` is sent to every page (each runs `faHotSwap`, the manifest fetched), the first page's answer is relayed (with no page open, the swap counts as done, the next page loads the new modules); when a swap isn't possible, the new build replaces the old one in the served folder and the server asks the pages to reload (`reloading the pages (…)`); the server stays up and exits when `fa develop` does. `develop.open` opens the page in a browser when the server starts (`xdg-open`, `open`, `start`, or the command `FA_OPEN_COMMAND` names; the URL is printed when none can run).
- **`fa develop --target=native`**: `fa` hands the command to `fa-native`; each start builds the executable with `build_native` in development mode into a cache folder per package (`develop-native-<hash>`), so the units whose code didn't change come from the object cache, then starts it; it prints `built for native in <n> ms`. No hot reloading natively: every change rebuilds and restarts. Measured (release build, a generated package of 100 files and 20,557 lines, `benchmarks/compiler/generate.ts --files 100 --lines 200`, 6 cores): the first build from an empty cache 11 s; then, after an edit of a body never compiled before, 1.1 s for a leaf file and 1.2 s for a file 90 files read (0.7 to 1.0 s in a session whose cache already holds the program); with nothing changed 0.7 s.
- **Object cache keys of development builds per unit** (lead, fine-grained): a unit's key no longer hashes the whole-program facts. Its lowering records every fact it consults (`facts::FactLog`: the kind, the key and the answer, through `ProgramFacts::consulted`: dense maps, maps deleted while iterated, the failed proof claims), written next to the object (`<key>.facts`, sorted, so deterministic); the object is reused only while every recorded fact has the same answer (`cached_unit`), so a change of a fact rebuilds only the units that read it. One object per key: a unit whose fact changes back is compiled again. The runtime object's key holds no fact either (it reads none): it was compiled again (6 to 7 s) at every change of the facts. `FA_SPLIT_TRACE=1` prints the units compiled and the time of the units, the instance waves, and the entry and the link. Tested by `codegen-llvm/tests/object_cache.rs`.
- **`@import` in remote files and folders**: the files a remote source fetched are scanned for `@import`s, resolved as the dependencies of that library (a remote file still sees no other dependency). A Git repository only such an import asks for is chosen on demand, for that request alone (not unified with the ranges of the rest of the program). A dependency folder used whole (`use { openapi } = @import("github:…")`, `use { cows } = farm`) now reaches every module of the folder (`ModuleResolver::modules_in`, so the JavaScript build writes them).
- **Tooling review (CLI)**: every unknown option says `see fa help <command>`, a second path says to give one; `fa help develop`, `test` and `update` describe the targets of `develop`, the process per test file and `@import` sources; `fa update` outside a package says where to run it. Checked: usage errors exit with 1, the program's code for `run`/`preview`.
- **Interface hash**: the hash of a file's interface includes the node of each exported declaration: the files using it name it by its node, so a body edit that renumbers the nodes re-analyzes them (`Session::update`).
- **`fa preview`**: runs `<package>/<build.output>/<target>/` of the first configured target among `native`, `bun`, `node`, `wasm`, `web` whose build exists and whose runtime is installed; `web` is served by a small Bun server on `develop.port` (an `index.html` of the build, else a page loading `main.js`). Nothing to run is `CLI006`.
- **Path dependencies outside a workspace** (lead): a package outside any workspace may depend on a local folder that holds a package (`shared = "../shared"`), like npm's `file:` dependencies; it is locked by the SHA-256 of its content like any other source. Inside a workspace, a path must name a package of the workspace (`DEP008` otherwise). Implemented: the entry of the lockfile is the path from the lockfile's folder (`../shared`, also for the path dependencies of a path dependency, resolved transitively with their Git dependencies), its hash the D45 hash of `package.fa`, `dependencies.fa` and `library/`; the files are read from the folder itself (not copied into the cache), and a change is `DEP001` until `fa update <key>`.
- **Language server and dependencies**: a package's dependencies are resolved by `fa::editor_session` like `fa check` does (the cache filled, the network used when something isn't cached), except that the lockfile is never written. An error of the resolution is the only diagnostic of the package's open documents, at their first character, with its code (`DEP002`…), as `fa check` prints only it; the package is still analyzed without its dependencies for hover and completion. The warnings (`DEP004`) go to `dependencies.fa` when it is open. The resolution is read again when the editor saves a configuration file (`package.fa`, `dependencies.fa`, `workspace.fa`, `dependencies.lock`: every loaded package below its folder is loaded again), not at each keystroke (a source typed character by character would reach the network each time); a lockfile written by `fa` outside the editor is read at the next load of the package.
- **`fa test` runs each test file in a process** (the tooling line of the to-do list): `main.js` of the tests lists the tests by module (`faRunTests([[module, tests]…], $init, runAsync, argv)`); with `--fa-test-file=<module>` it runs that file's tests only (a `test only` of any file still hides the others: the focus is computed over every file) and ends its output with a line `\u0001fa-test-summary <passed> <failed> <skipped> <not run>`. `fa test` starts one Bun process per test file (processes rather than Bun workers: each one's stdout and stderr are captured whole, and a crash ends only its file), as many at once as cores (`FA_TEST_WORKERS` overrides), prints each file's output in the order of the files as soon as it and the files before it are done, then the counts added up in the format of `faRunTests`. A process that ends without its counts counts as one failure (`✗ <file>: its tests didn't finish (exit code N)`). One test file runs in place, as before. Module-level values are still initialized again before each test; `--watch` goes through the same runner. Without the argument, `bun main.js` runs every file in one process, as before.
- **`DependencySource.generate`**: a `dependencies.fa` whose export is computed (functions, values), or holds `{ source, generate }` objects, is analyzed alone (with a placeholder `package.fa`) and its export evaluated on the interpreter (`fa_analyzer::comptime::host::dependency_sources`); in the package's own analysis, the `generate` functions are left out of the configuration value (`configuration::from_value_without_functions`). The `source` must be the URL of a remote file (`https://`, `http://`, `file://`; a folder or a Git repository is an error naming the expected form): it is fetched, cached and locked like a remote file (its entry in the lockfile, `DEP001` when it changed), then `generate` runs on its UTF-8 content (`run_generate`, the bounds of compile-time evaluation; it must return a `String`). The Fa source returned is the module of the key, stored in the cache by its D45 hash as `<key>.fa` (mounted as `$dependencies/<key>-<hash>/`, shown as `<url> (generated)/<key>.fa`); it is generated again at each resolution (not cached by the source's hash: the function may change with `dependencies.fa`), and isn't in the lockfile (the source is). A failure of `generate` is `DEP010` ("the `generate` of `stripe` failed: …"). With `@import` (below), the function can come from a library, as in the documentation's `openapi` example.
- **`@import`** (architecture/dependencies.md, "Inline imports"): `fa` finds the `@import("…")` calls with a string literal in the files of a package (its configuration files, `library/`, `application/`, `scripts/`), of the workspace's `dependencies.fa`, of the Git libraries and of the path packages, and resolves their sources like those of `dependencies.fa` (Git, remote file or folder; locked in the same lockfile, `DEP004`/`DEP001` alike) under the key `@import <source>` (`fa_analyzer::scan::import_name`: no written name can be it). The analyzer's scan reads the call as that name (used whole), so `use weather = @import("…")` is a name alias of the module (D14) and `use { openapi } = @import("…")` aliases its members; the backends generate nothing for them. The `@import`s of a `dependencies.fa` are resolved and mounted before the file is evaluated (`Bootstrap` in `dependencies.rs`, nested up to 4 levels), so the documentation's `openapi` example works, its entries joining the lockfile. `@import` elsewhere than in a `use` (as a value), a source that isn't a string literal, a local path (`./x`, `../x`: `fa` reports it before the analysis), or a source `fa` didn't resolve (a remote file or folder importing: not resolved yet, a lone analysis) is `META010` with the reason. `fa update <source>` re-resolves an `@import` (it has no key). Untouched: `@extern` (foreign code).
## Foreign code

- **No `rust` target (user decision 2026-11-02)**: Fa compiles with LLVM (`native`, `wasm`) and to JavaScript (`web`, `bun`, `node`), never to Rust source. Rust code is used like any C library: a crate exposing `#[unsafe(no_mangle)] pub extern "C"` functions, built as a `staticlib` or `cdylib`, bound in a `*.foreign.fa` file with `@extern` (or with `fa bind` on a `cbindgen` header), and linked with `build.link` and `build.libraryPaths`. `targets = ["rust"]` in a `package.fa` is an error (`E-TYPE-1`, like any unknown target; `overrides.rust` too) whose message suggests `native` and the C ABI.
- **No `deno` target (user decision 2026-11-02)**: the Deno runtime is considered abandoned, so Fa doesn't compile for it. The targets are `native`, `wasm`, `web`, `bun` and `node`; the server JavaScript runtimes are Bun (the default) and Node.js. Foreign code on JavaScript goes through `bun:ffi` only (the `Deno.dlopen` lowering is removed). `targets = ["deno"]` in a `package.fa` is an error (`E-TYPE-1`, like any unknown target; `overrides.deno` too) whose message suggests `bun` or `node`, and `fa build --target=deno` says the same.
- **A foreign file** is a module whose path ends with `.foreign` (`*.foreign.fa`); a standalone `*.foreign.fa` file is a program, so a single file can bind and use C. A standalone program with a foreign file is checked for `bun` and `native` only (not `web`).
- **`std.c`** is a built-in alias target: `use c = std.c` declares `c`, and `c.Int`, `c.SizeT`… are the integer types of the target's C (LP64 on native and JavaScript hosts, ILP32 on wasm); `c.Float`/`c.Double` are `Float32`/`Float`. `Float64` is accepted as a type name (the table of C types writes it).
- **`CStruct`** is a nominal object type whose fields keep their declaration order (`TypeStore::object_in_order`): the backends lay it out like C without a mapping. `CArray(T, n)` values (2026-11-05) are written as an array literal of exactly `n` items (no spread, `E-TYPE-1`), indexed like an array (counted from the end when negative; `IndexError` unless the index's range is within `-n..n`), written in place, iterated (with an index), `length` (`CArray#length`), copied, compared and printed like arrays. On JavaScript a `CArray` is an array (copied with `slice`); natively it is laid out as a tuple of `n` items (C's layout of `T[n]`), indexed through memory, and a `for` loop runs over an array of its items written back to its place.
- **The passing rules** apply to the calls of `@extern` functions only (`Analysis::extern_calls`, `Analysis::foreign_args`). A callback may take `Pointer(T)` where the C type says `Pointer(Void)` (C converts `void *`), so a `qsort` comparator reads `Int32`s directly. A `mutates` pointer parameter accepts a parameter of the caller too (its effect is then checked like any other).
- **Function types** accept `throws E` and `mutates p` (a whole parameter, by name); other clauses in function types stay unsupported.
- **Move-only**: a type with `destroy` is a `NominalKind::Resource`; a copy of a local holding one moves it (`MEM002` on a later use, like a stopped `Subscription`). `destroy` runs when the native backend drops the value. On JavaScript, a `let` or `mutable` local of a type with `destroy` that no read moves out (`MOVE`: `let second = first`, a returned value) is destroyed at the end of its block (`try`/`finally`, the end of `main` at the top level); a local moved on some paths only, a resource inside another value or a collection, and the old value of a replaced local are not destroyed there (gap).
- **Native ABI**: scalars directly (`signext`/`zeroext` below 32 bits), `CStruct` by value classified for x86-64 System V (≤ 16 bytes in one or two eightbytes, else `byval`/`sret`); other targets reject a `CStruct` by value. A `String` for a `CString` is copied into a zero-terminated block of the runtime allocator for the call (no stack buffer yet).
- **JavaScript**: an `@extern` function binds its symbol on its first call (`faFfiBind`), searching `build.link` (resolved in `build.libraryPaths`) then the C library and `libm`, through `bun:ffi`.
- **`fa bind`** parses headers by hand (no libclang, no C compiler): see the limits in the documentation.
- **Types declared inside a type (2026-11-05)**: `Self.Name` and `Type.Name` (also through a module path, `library.Farm.Error`) reach a type declared in a type's body, in types and values (members, typed literals, patterns, functions, `members`); `Interface::nested_types` publishes them to other files. `type Error = …` is accepted (the token after `type` and before `=` is a name), the word alone stays the prelude's `Error`. A nested type is keyed under its outer types (`Farm.Error`: the C header's `farm_FarmError`); it prints with its own name (`Error.Empty`). JavaScript: the functions of nested types are module functions named `Farm$Animal$make` (also their export names), and a generated error class is tested by its qualified name (`?.constructor?.faName`) instead of `instanceof`, since each module declares the classes it uses (errors thrown by another module were never matched before).
- **C libraries (`build.cLibrary`, 2026-11-05)**, decided where the documentation is silent (simplest behavior consistent with it):
  - *Outputs*: `fa build --target=native` of a package with `build.cLibrary` writes `lib<prefix>.a`, `lib<prefix>.so` (`.dylib` on macOS) and the header into `<build.output>/native/`, and no executable. The API file is the program's entry (no entry function: `MOD015` is skipped for it); every declaration of it is reached. Only `native` builds one: `wasm` and `native-freestanding` are refused by the backend (gap: exports of a wasm module).
  - *The API*: the functions of the exported namespace, in declaration order (its other members are ignored); `<prefix>_<snake_case>` (`parseHTTPRequest` → `parse_http_request`). At the boundary: integers of a fixed width (not `Integer`, nor 128 bits), `Boolean`, `Float32`/`Float64`, `CString`, `CString?`, `Pointer<T>`, `Pointer<T>?` (any `T`) and `CStruct`s by value; not callbacks, `CArray` by value, generic functions (`FFI014`, a new code of the advanced brief, also for an export that isn't a namespace and for errors of several types). `requires` is `REQ006`; a module-level `mutable` value that isn't thread-safe, reached through the calls, is `FFI012` (the program's check of worker code, `worker_diagnostics`); `FFI013` on a JavaScript target only when it is among the package's `targets` (the API file is analyzed per target).
  - *Header*: `<stdint.h>` exact-width types (`c.Int` is an `int32_t`, the same type everywhere Fa runs), `bool`, `const char *` for `CString`; a `CStruct` defined with its fields in order (`typedef struct farm_Point { … } farm_Point;`), an empty one or a Fa value behind a pointer opaque (`typedef struct farm_Farm farm_Farm;`); type names are `prefix_` and the type's name path joined (`Farm.Error` → `farm_FarmError`); a pointer to a type without a name is refused. An `Errors` type is `typedef enum farm_FarmError { FARM_FARM_ERROR_EMPTY = 1, … }`. `extern "C"` guards for C++.
  - *Errors*: a function's `throws` is the members of one `Errors` type; it returns an `int`, 0 on success, else the member's position from 1; its result goes through a last pointer parameter `result` (skipped when `NULL`; a function without a result has none). The message (the error as `console.log` shows it) is copied into a thread-local buffer of 1024 bytes, cut at a character (nothing to free, any thread); `<prefix>_last_error_message()` returns it, `""` before the first error, and a success doesn't reset it (like `errno`).
  - *Load and unload*: `llvm.global_ctors`/`llvm.global_dtors` (`.init_array`/`.fini_array`: target machines are created with `UseInitArray`, through the C++ shim, since `ld.lld` ignores `.ctors`). The constructor initializes the module values in the program's order and runs the API file's top level; the destructor drops them when a drop does more than free memory (`destroy`) or the build is leak-checked (then reports the leaks: `leak: <n> blocks`, 102), and flushes. No stack guard (the host's `SIGSEGV` handler is left alone).
  - *Calls*: the wrappers are `ccc`, external with default visibility, structs by the target's C ABI (the classification of `@extern` calls, shared: `c_function_type`). The library runs in synchronous mode: an `async` function is exported as its blocking version, a started task runs to its end. Each call ends with the flush of `console` (its output keeps its order with C's) and the release of the thread's text builder (a C thread may end after any call).
  - *Visibility*: the shared library exports only the API (a version script); the static library is one relocatable object (`ld.lld -r`, LTO applied there) whose other symbols are made local (`llvm-objcopy --keep-global-symbol`); it leaves `-lm -pthread` and the libraries of `build.link` to the program linking it. The thread-local variables (the runtime's are `initial-exec`) use the general dynamic model in a library, so that `dlopen` (Python's `ctypes`) loads it.
  - *Builds*: per unit (ThinLTO or full LTO for `fa build`, plain objects at `-O0`; the wrappers live in the API file's unit, `UnitSymbols::c_exports`; the entry object defines the constructor and destructor), or as one module (`FA_SPLIT=0`, the fallback). `pointer.value` of a Fa value in a block of `Pointer.allocate` is now a place natively (a method's receiver: `farm.value.countAnimals()`).

## Concurrency without async (advanced brief §14, D23, D31)

- **`std.concurrency`**: `use { Mutex } = std.concurrency` is checked (each name must be a member: `AtomicInteger`, `AtomicBoolean`, `Mutex`, `Channel`, `Ordering`, `ChannelClosed`); the names are known like the prelude's, the `use` is not required yet. `ChannelClosed` is a built-in error (native id 7). Named arguments are accepted for the `ordering` parameter of the built-in methods.
- **Targets**: `for parallel` is `CONC001` on JavaScript and `wasm`. On `native-freestanding` (no C library, no threads) it compiles and runs its iterations in order; a wait that no other thread can end (`lock` of a held mutex, `receive` on an empty open channel, `send` on a full one) stops the program (`stop: deadlock: …`). Thread-safe types work on every target, with one-thread semantics on JavaScript and `wasm`; their waiting methods (`lock`, `send`, `receive`) are `CONC010` there.
- **Writes in a parallel body**: the variable of a `for parallel i in a..b` counts as the iteration's position, like an index binding: `results[i] = …` is the iteration's own place. Reads of a collection written by index are only `T[i]` and `T.length` (`CONC013` otherwise). A call changing a module-level value it reaches by itself is `CONC012`; one changing a value it is given (`results.push(…)`) is `CONC002`.
- **Index proofs**: a copy of a local has the local's length (`mutable results = numbers`), and `index < numbers.length` with `numbers` no longer than `results` proves `results[index]`.
- **Native pool**: one thread per processor but one (`sysconf`), started at the first parallel loop; the calling thread takes part; iterations are taken in chunks of `count / (threads × 16)`; a nested parallel loop, or one started while another runs, runs on its own thread. `parallel(threads = n)` caps the threads of the loop. `pthread_*` are weak references: without them (freestanding) everything runs on one thread.
- **Native runtime state**: the text builder and the small-block free lists of the allocator are thread-local (`initial-exec` TLS, made plain globals on the freestanding target); the output buffer and the free spans are guarded by spin locks; leak counts are atomic.
- **Atomics** are always sequentially consistent natively: the `ordering` argument is accepted and evaluated never weaker. `AtomicInteger` arithmetic wraps (no overflow check).
- **Guards**: natively, a guard holds a handle of its mutex and unlocks at its drop. On JavaScript, a guard declared in a block is released at the end of the block (`try`/`finally`); a guard used as a temporary (`m.tryLock()?.value`, `m.tryLock() == none`) is kept in a temporary and released after its statement (in a `finally` when the statement leaves the block). A guard of an awaited `lock()` used as a temporary is not released (gap).
- **Workers** (D31, blocking calls only): natively, a worker is its state and its calls run on the calling thread, which waits for them anyway; two threads can't call a method changing its state at once (`CONC002`), and the other methods only read it. Its own thread (and the copy of arguments across threads) comes with `start` and `await`. `let other = worker` moves the handle (`MEM002` after); a field read is `CONC008`, a method named `stop` is `CONC008`; creating a worker on another target than `native` is `CONC010`.
- **`for parallel`** (2026-11-05) also iterates growing arrays (each item found with `fa_segmented_at`), pools and columnars (the addresses of their elements taken before the loop, in slot order); the values given with `provide` and the requirements of the function around are passed to the outlined body in its environment, like the locals it uses.
- **`parallel()` views** (2026-11-05): `collection.parallel()` is the collection itself, typed as it, which must be the target of one of `map`, `filter`, `reduce`, `some`, `every`, `sum` at once (else `CONC001`; `CONC001` off `native`; a relation side isn't supported yet, `AN001`; a map has `map`, `filter`, `some` and `every`, over its entries in its order: a function of a key and a value can't combine partial results, so `reduce` is `CONC001` there). The lambdas given to the operation follow the rules of a parallel body (a `ParallelFrame` marked `callback`, whose `return` is its own). Natively, the callbacks run on the threads of `fa_parallel_for` over an array of the items (a view of a growing array, a pool, a columnar or a set), each writing its slot of a result (zeroed first, so that an error drops only what was written); `filter`, `some` and `every` read flags in order afterwards (the copies of `filter` made in order, in the collection's kind); `reduce` folds up to 256 chunks of items from their first item in parallel, then combines the partial results in order from the initial value, so its accumulator is of the items' type (`E-TYPE-1`); `sum` adds in order. On `native-freestanding` the same functions run in order on one thread.

## Strings: byte access (lead, after the fifth native shift)

- **`text.bytes(): Array(Byte)`** gives the UTF-8 bytes of a string, next to `characters()` and `codePoints()`. It is the one way to read bytes: no `byteAt`/`charCodeAt`-like method. When the result is only indexed, measured or iterated (`text.bytes()[i]`, `text.bytes().length`, `for byte in text.bytes()`, a local only read), the compiler reads the string's bytes in place without building the array (natively a view of the UTF-8 bytes; on JavaScript `charCodeAt` for a string known to be ASCII, otherwise one `TextEncoder` encoding). The documentation's string pages list it.
- Implemented (sixth native shift): natively, `text.bytes()[i]`, `.get(i)`, `.length`, `for byte in text.bytes()` and a `let` local only indexed read the string's bytes (`arrays.rs`, as `codePoints()`); a kept array is one copy of the bytes. On JavaScript, `faStringBytes` reads an ASCII text with `charCodeAt` and encodes any other one with `TextEncoder`; a `text.bytes()` only indexed, measured or iterated where it is called keeps the bytes of the last text (`faStringBytesView`), so a loop over one text encodes it once. The interpreter evaluates it at compile time. The Goose ports read bytes where Goose does (`calc` and `sexp` parse `self.text.bytes()` instead of an `Array(Character)`; `respond`, `strlist`, `words`, `records`).
- **Implementation**: without `--target`, `fa build` reads `targets` (the package's configuration merged with its workspace's, without analyzing the package), builds each target in turn (`fa build: target `web``), then reports each outcome (``fa build: `web` built, `native` failed``); it exits with `1` when one fails. Every command finds its project with one function, `fa_codebase_parser::discover` (the closest `package.fa` and `workspace.fa`; `Discovered::closest` says which one a command without a path works on), used by the CLI and the language server.
- **`fa` doesn't link LLVM** (startup time): loading `libLLVM.so` cost every command ~25–30 ms (`fa version` took ~25 ms, now ~2 ms; `fa check small.fa` ~26 ms, now ~4 ms). The `fa` binary and the language server use the plain data of `fa-codegen-llvm` (targets, options) and link none of its LLVM code, so `libLLVM` isn't loaded (checked with `readelf -d`). ## Minimal representations (user decisions, 2026-11-03)

- **Text is bytes, characters are views.** A `String` stores UTF-8 bytes (like Rust and Goose). `characters()` gives a view over those bytes, not an array of 24-byte values: a `Character` is a small value (the bytes of one grapheme cluster, inline when short, else a slice of its string), and an `Array(Character)` that a program builds explicitly stores compact characters. Programs that walk text work on the bytes (`bytes()`, views), never on a copied array of characters.
- **Small strings never touch the heap.** Strings up to 23 bytes live inline in the 24-byte string value (the documented layout). Local strings that don't escape, up to 64 bytes, live in stack buffers; a string goes to the heap only when it is longer or escapes.
- **Capacity is managed by the programmer when it matters.** Strings and every collection (`Array`, `GrowingArray`, `Set`, `Map`, `Pool`, `Columnar`, growing variants) take `capacity` in `from(…, capacity = n)`, expose a read-only `capacity` property and a `reserve(additional)` method. On JavaScript, `reserve` does nothing and `capacity` equals `length` (or `size`).
- **Parameters are never copied.** Every parameter is passed by reference (a pointer natively), mutated or not; only scalars that fit in a register are passed by value, which is the same thing for them. A copy happens only when the callee stores the value (an escaping use) and the analyzer can't move it.
- **Module-level `let` values with known values are constants** (folded, in read-only data), never reloaded in loops; other immutable module values are invariant loads.
- **Small optimizations are inlined**: the allocator's fast path, string appends with known capacity, hashing of short keys, getters, `current()`-like helpers — whatever removes a call in a hot path without growing code much.
- **`WorkerPool` state** (lead, question of the async engineer): a pool's options take `state: T`, the initial state of each worker, copied into every worker of the pool (`WorkerPool(DataProcessor) { count = 4, state = DataProcessor { factor = 2 } }`); it may be left out when every field of `T` has a default (then `T {}`). A worker restarted after a `timeout` starts again from a fresh copy of `state`. The concurrency page gets the field in its options example on resume.
- **Implemented: analyzer, JavaScript, documentation** (the native side is the LLVM engineers'):
  - **`reserve` effects**: `mutates self` where a growth may move the elements or the bytes (`Array`, `Set`, `OrderedColumnar`, `String`), like `push`/`add`/`+=`; `mutates self.capacity` on the collections whose elements never move (`GrowingArray`, `Map`, `GrowingMap`, `GrowingSet`, `Pool`, `GrowingPool`, `Columnar`, `GrowingColumnar`). `capacity` is a new path step (`PathStep::Capacity`, `flow::Step::Capacity`, written `mutates self.capacity` in a signature): distinct from the elements, `length` and `size`, so it invalidates no reference and keeps the facts on the length (index proofs survive a `reserve`); a `reserve` of a collection being iterated is still `REF012`; it is not a reactive write. Rejected: `mutates self.size` (drops the length facts, and says something false).
  - **`String.from(text, capacity = n)`**, the shape of every collection's `from(source, capacity = n)` (`capacity` named only). Rejected: `String(capacity = 64)`, which reads as a conversion and has no source. Every collection's `from` now takes `capacity` (the growing ones and `OrderedColumnar` too): its call has the arguments `(source, capacity)`, `(source, key, capacity)` for sets.
  - **`capacity`** is a read-only `Integer(min = 0)` property (`Array#capacity`… `String#capacity`, in bytes for a string); assigning it is `E-OBJ-11`. JavaScript: the `length` or `size` (the grapheme `length` for a string); the interpreter: the length, in bytes for a string. `reserve(additional: Integer(min = 0))` needs a mutable receiver (`EFF007`); on JavaScript it compiles to nothing but its argument when that has effects, and `String.from` to its text.
  - **`characters()` keeps the type `Array(Character)`**: the view is a representation, chosen by the native backend from the syntax when the array is only read (as for `bytes()` and `codePoints()`), and an array the program keeps and changes is built of compact characters. Rejected: a `Characters` view type, which every API taking an `Array(Character)` would have to convert, for no semantic difference. JavaScript keeps its array of strings (same semantics: nothing can change the string while it is read).
  - **Stack strings**: `Analysis::is_non_escaping(symbol)` lists the `let`/`mutable` locals of blocks and functions whose value never leaves the frame (`check/locals.rs`, conservative): never returned, thrown, the value of a used block, an item or a field of a literal, stored by a built-in (`push`, `add`…), assigned to a field, an element or a module-level value, moved into a detached `start`, nor moved into a local that escapes (a fixed point). Arguments of user functions don't escape (parameters are references), nor do captures (an escaping closure copies them).
  - **Module constants**: `Analysis::module_constant(symbol)` gives the value of a module-level `let` (or `export =`) whose value is a constant expression (literals, templates, arithmetic, comparisons, lists, tuples and objects of constants, other constants and statics), evaluated once by the interpreter, silently. A separate table from `constants`: the JavaScript output keeps `const name = value` and its reads.
  - Not done natively yet: the analyzer case `collections/capacity.fa` skips the native targets until `capacity`, `reserve` and `String.from` are lowered.
  - **`WorkerPool` in the analyzer** (it had none): `WorkerPool(T)` (`T` must be a worker type, `E-TYPE-1`), its literal `{ count, state, maxQueueSize, timeout }` (integers, and `state: T`; `count` is required, as no default is documented), `submit` typed `(task: async (worker: T) => R) => Task(R) throws WorkerTimeout` (always `WorkerTimeout`: the type doesn't say whether the pool has a `timeout`; the task's own errors are not accepted yet), `shutdown()`, `WorkerTimeout` in `std.concurrency` (the concurrency page's example now imports it). A literal of the worker type given as `state` builds the object, not a worker. `CONC010` off `native`, like workers. Gap: the defaults of a type declared in another file are not known to a typed literal (`Counter { }` of an imported type with defaults is `E-OBJ-2`, an older gap), so `state` can be left out only when every field of the worker type is optional (`?`) for now.

## Native representations (`perf/native-goose`, reviewed 2026-11-04)

What the merged Goose work decided for the native backend (details and conditions: `design/llvm-backend-plan.md`, "Native representations of the Goose work"):

- **Optimizations are generic.** A representation or a shortcut is chosen from types, proven uses and the target; never from a program's name, an input size or an expected output. A check (bounds, keys, divisors, conversions) stays until the analyzer proves it away.
- **One region mechanism: root arenas.** Recursive values built by their builders live in page-aligned chunks owned by the root (`trees.rs`), under a closed, conservative proof; any other shape keeps the general ownership path. The sixth shift's statement regions were measured on top of it, gained nothing, and were not merged.
- **Small unions are inline, up to 3 machine words of payload** (the size of a string value). Larger payloads stay boxed: inlining a 40-byte payload widened `Array(Event)` and slowed `records` by 40 %. The next step is variable-size payloads in collection buffers, not a larger budget.
- **An optional pointer is a nullable pointer** (recursive edges, boxed unions, arrays), and collection slots store recursive objects directly: an edge is boxed only where the layout would otherwise be infinite.
- **Direct calls borrow aggregates** by address (the "Parameters are never copied" decision above, for synchronous direct calls; indirect calls and coroutines to follow).
- **Huge pages on native Linux**: 2 MiB spans advised `MADV_HUGEPAGE`, with an ordinary fallback; a larger RSS for small programs is accepted for the faster address translation of large heaps.

## Async scheduler: wakes before yields (lead, after the B2 benchmarks)

- The `starve` benchmark missed its target (timer lateness p99 25 ms for 2 ms): a timer-woken task queued behind 1,000 always-ready tasks that each spend their whole budget. The executor keeps two FIFO queues: **woken** (timers, I/O readiness, remote wakes, a finished task waking its waiter) and **yielded** (a task that spent its coop budget, `Task.yield`, a back-edge yield). Each tick runs the woken queue first, then the yielded queue; when both are non-empty, woken turns take at most half of the tick's 61 turns, so a flood of events can't starve the tasks that yielded either. A task that waited for an event was not using the thread, so serving it first is the fair order; FIFO holds inside each queue.
- **Timers checked inside a tick** (lead, after the second `starve` run: p99 17–19 ms, because a tick of 61 full-budget turns lasts ~5 ms): the executor reads the clock every 8 turns of a tick and moves expired timers to the woken queue then, so a timer is late by at most a few turns.
- **`WorkerPool.submit` is async** (it waits while `maxQueueSize` calls are queued) and gives the task: `pending.push(await pool.submit(f))`. Fa is colorless: a plain `pool.submit(f)` is a blocking call (it waits for room on the calling thread), allowed wherever blocking is (native); it is `CONC010` only on targets that can't block, like any other async-only primitive.

## Async follow-ups on JavaScript (S1, J2, after J1/W1)

- **Workers exist on JavaScript (J2)**: a worker is a `worker_threads` `Worker` on Bun and Node, a Web Worker on the web, running `$worker.js` (written next to `main.js` when a module uses workers: it runs the `$init` functions of the program, so the thread has its own copies of the module-level values, then serves the calls). `CONC010` for creating a worker or a pool is now only for the targets without workers (`wasm`, `native-freestanding`: `builtins::concurrency::has_workers`); a **blocking** call of a worker's method is `CONC010` off `native` (only threads of `native` can wait), so JavaScript awaits or starts them, and `submit` is awaited there (it already was `CONC010` blocking). The submitted function runs on the main thread on JavaScript (a closure can't cross threads); its calls of the worker run on the worker's thread, and the rules of worker code still apply to it (below), so the program means the same on every target. Values cross by structured clone (copies); Fa errors are rebuilt with the classes the method may throw; a pool's `timeout` terminates the worker's thread and replaces it. **Atomics and mutexes given to a JavaScript worker are shared** (follow-up): before a message leaves, they move into a `SharedArrayBuffer` (an atomic's value a cell updated with `Atomics`, a mutex's lock a word taken with `compareExchange` and its value JSON text read by whoever holds it; the web needs cross-origin isolation for it); the receiving side gives them their class back. A worker's method that awaits runs its Promise API on the worker's thread. **A `Channel` given to a worker is shared the same way** (2026-11-04): its queue moves into a `SharedArrayBuffer` (a lock word, a closed flag, the length of the queue's JSON text and a version word, then the text); a waiting task waits for the version (a mutex: its lock word) with `Atomics.waitAsync`, woken by the `Atomics.notify` of every send, receive and unlock (a timer whose delay doubles from 1 to 16 ms where `waitAsync` is missing: Firefox), a worker's blocking wait with `Atomics.wait`. On Bun, a ping-pong round trip between the main thread and a worker went from 1.8 ms (polling every millisecond) to 0.18 ms, and a task idle 3 s on a channel from about 0.3 s to 0.1 s of CPU (the start of Bun included). Not a `MessagePort`: a port has one end per side, a Fa channel any number of senders and receivers on any thread. Without shared memory (a web page that isn't cross-origin isolated, which the analyzer can't know), giving an atomic, a mutex or a channel to a worker is a run-time stop that names the two headers to send; Bun and Node always have it.
- **The work given to `submit` follows the rules of worker code** (`CONC008`): no module-level `mutable` value that isn't thread-safe; a requirement it needs from outside is `REQ007` already (the work is stored). Only the work's own body is checked, not the functions it calls.
- **Loop back-edges of the top level and of tests yield** (the todo of A2): the backends spend the coop budget there too. The analysis forgets at those back-edges only the module-level `mutable` values that **other code** may change: those named in a function, lambda, `start do` block or test of a file that starts tasks (`start`, `submit`); the top level's own variables (named nowhere else, not exported) keep their narrowing — no other task can change them while the top level yields. The names are matched by text, which only makes the analysis forget more.
- **`std.net` on Node**: Node binds a listener asynchronously, so `listener.port` of `port = 0` is `0` until the listener listens (after the first wait); Bun binds at once. Hosts stay IPv4 addresses or `localhost` (no name resolution), as natively.
- **`fa test` awaits**: a test whose summary `suspends` (in an asynchronous test program, the mode the analyzer resolves for the tests) is an async function run as a task (`faTestTask`); the runner waits for it and for the detached tasks it started before the next test. Natively there is no `fa test` yet.
- **Two async divergences between native and JavaScript** (lead): (1) a detached `start do` at the top level copies the top-level values it uses, as the documentation says for detached tasks, on every target (JavaScript must copy too); (2) a function with a single instance (an `async` function that can't suspend runs as a blocking call, A4) starts its tasks eagerly, by the documented blocking-call rule, on every target (JavaScript must run them at once too). The same program prints the same thing everywhere.
- **A mutation of a narrowed payload keeps the narrowing** (lead, after the narrowed-places fix): `if items is not none { items.push(1); items.push(2) }` is valid. The narrowing is a fact about the optional's (or union's) tag, and a call that mutates the payload (`mutates self` on the narrowed `items`) changes what is at and below the payload, never the tag: by the fine-grained rule (`mutates P` drops facts at and below `P` only), the tag fact stays. An assignment of the whole place (`items = none`, `items = other`) or a call that mutates the optional itself (a `mutates` parameter typed `Array?`, or a module value through its own effect) still ends it. The narrowing page is updated to say "an assignment of the place, or a call that may replace it".
  Implemented (`kept_narrowings` in `check/effects.rs`): the receiver of a built-in method and the argument of a `mutates` parameter (or `self`) whose declared type is not a union keep their narrowing; the closures' captured effects and module values written by a callee don't. A `use` alias keeps its narrowing when the effect is strictly below the place it designates, or is such a payload mutation of it (`invalidate_references`).
- **`E-OPT-3` on a narrowed value** (lead, 2026-11-04): `?.` on a value narrowed to a non-optional type is `E-OPT-3`, decided on the narrowed type (a narrowing changes the type; D-22, one way to write it). When the value is optional by declaration, the message says it is narrowed and where (`zoe` is never `none` here: it was narrowed at line N), with a related span on what narrowed it: each narrowing fact records its site (`Fact::narrowed_at`: the test, or the assignment; a join keeps the first site in the file). `E-OPT-6` (`??`) followed (lead): decided on the narrowed type, with the same message and related span.
- **Narrowing of optional fields** (lead, implementing the narrowing page): a path of fields of a place (`h.items`, `self.owner.name`, not a relation side, not through an index or a call) is narrowed by `is none`/`is not none`/`is Type` tests, early exits, `and`/`or`, and the assignment of a value (`h.items = [1]`); the fact lives on the field's flow place (`Fact::narrowed`). A narrowed read flags the member node `NARROWED` with the narrowed type (also inside a longer access, `h.counter.count`), revalidated at each visit like a local's (`revalidate_fields`); the last member of a written place keeps its declared type, except as the target of `op=` (its payload, narrowed again after the write). The backends treat a `NARROWED` member like a narrowed local: its payload's value or place (`payload_place`). An assignment of the field or of a prefix, a call that may replace it (a `mutates` of a prefix) and the other rules of locals end it.
- **JavaScript copies of collection elements** (lead): a built-in returning elements as stored (`get`, `find` of arrays, maps, sets, pools and columnars; `filter`, `values`, `keys`, `sort`, `reverse`, set operations, `Iterator` `toArray`/`firstValues`) reads its receiver's place for the D15 rule (`lower::copies::element_view`): `mutable c = map.get(k)` is a copy, and a new collection of composite elements is copied when stored into a `mutable` destination or read from a mutable place. Native code already copied them.
- **Native builds per unit, follow-ups of step 6** (lead, 2026-11-04): ThinLTO stays the default of release package builds (parallel, bounded memory); `FA_LTO=full` stays an environment switch for measurements, not a CLI flag. The size gap with full LTO (592 KB against 447 KB on 100 files) and the cold `fa run` cost come from code nobody calls: each unit lowers only the declarations the entry reaches, computed from the call graph that the units' interfaces record (a declaration's reachable callees, generic instances included), before any LLVM work. Goal: ThinLTO within 10% of full LTO, cold `fa run` CPU no more than `fa build`'s. The fallbacks to one module are to remove in this order: asynchronous programs (most programs are), generic calls from inside instances, module values with non-trivial cleanup. A C++ compiler is required to build `fa-native` with LLVM (the ThinLTO bitcode shim); the `fa` binary still needs none.
- **Benchmark ports keep the source's integer widths** (lead, 2026-11-04): the Rust and Goose versions of `lru` store `i32`/`u32` fields, the Fa port `Integer` ones: that compares 32-byte nodes with 16-byte ones, a difference of program, not of compiler. A Fa port uses the Fa type of the same width and range as the Rust/Goose source (`Int32`, `UInt32`, `Byte`…) wherever those use one; where they use 64 bits or `usize`, the port keeps `Integer`. Inferring narrower field layouts from ranges stays a compiler goal (it helps programs written with `Integer`), but the benchmarks don't wait for it.

## Generics with angle brackets (user, 2026-11-04)

The user decided that generic lists are written with `<` and `>`, as in TypeScript; the documentation is rewritten by another agent. Detection rules (user's):

1. `<` followed by whitespace (space, tab or line break) is the comparison operator. Any other `<` opens a generic list, whatever comes before it.
2. Inside an open generic list, `>` always closes it. Outside one, `>` is the comparison operator.
3. A comparison inside a generic list goes in parentheses: `Storage<(size > 255)>` (Rust needs `{ }` for complex const generic arguments).
4. `<=`, `>=` and `=>` are separate tokens, so they are never generic brackets.

Lead's resolutions, to align with the rewritten pages when they land:

- **Scope**: every list written in parentheses today because it is generic moves to `<>`: the parameter lists of type declarations (`type Pair<Left, Right> = …`, defaults `<T = Integer>`, constraints `<Value: Integer | Float>`), and every application of a type, built-in or user, generic type or type function (`Array<Integer>`, `Map<String, Array<User>>`, `Integer<min = 0, max = 200>`, `Matrix<Float, 4, 4>`, `Omit<Entity, { password }>`, `TypeFromSchema<schema>`), in type positions and in expressions (a typed literal `Pair<Right, Left> { … }`, explicit arguments of a generic function `first<Integer>(items)`). Ordinary calls, compile-time ones included, keep parentheses.
- **Tokenizer**: the decision is lexical. The tokenizer keeps a stack of open brackets; `<` not followed by whitespace pushes a generic list and is `TokenKind::GenericOpen`, `>` with a generic list on top of the stack pops it and is `TokenKind::GenericClose`; inside `(`, `[` or `{` opened within a generic list, `>` is a comparison again (rule 3). `>>` is always two tokens (`Map<String, Array<Integer>>`). `GenericOpen` is an opening token and `GenericClose` a closing one for the line continuation rules. `<=`, `>=`, `=>`, `->` keep priority (rule 4): `Box<T>= …` is a comparison `>=`, and the diagnostic says to write `Box<T> = …`.
- **Diagnostics**: an unclosed generic list (`a <b` meant as a comparison, `1<2`) is reported where it opens, saying to put a space after `<` for a comparison; a `<` with whitespace where a generic list was expected (`Array< Integer>`) says to remove the space.
- **Syntax tree**: a generic application is its own node (not a `Call`), and declarations keep their generic parameter list; the formatter prints `<…>` with no inner padding.
- **Migration**: during the transition the analyzer accepts both spellings (a call of a type is the old application); a migration tool rewrites the repository's Fa code from the analysis (it knows which calls are type applications), in one commit at a moment no engineer has pending Fa code; then the old spelling becomes an error whose message gives the new one, and printed types (diagnostics, hover, `@typeToString`) use `<>`.
- **Full LTO when it fits the memory budget** (lead, 2026-11-04): ThinLTO stays 32% bigger than full LTO on 100 files (579 KB against 437 KB) because it can't inline across modules what is called once; that breaks the minimal-output principle. A release `fa build` therefore links with full LTO when its estimated memory (from the units' bitcode size, measured) fits the LLVM memory budget (`FA_LLVM_MEMORY`), and with ThinLTO above it; `fa run` keeps plain objects. The choice is printed with `--verbose`, and the output stays deterministic for a given program and budget.
- **Generic functions carry their list on the function value** (user, 2026-11-04): `function first = <Item>(items: Array<Item>): Item? => …`, not `function first<Item> = …`. The list belongs to the function expression, so lambdas use the same syntax (`<T>(value: T) => value`), methods too (`function map = <Output>(self, transform: (Item) => Output) => …`), and function types can be generic: `type Identity = <T>(value: T) => T`, then `function f: Identity = <T>(value: T): T => value`. Lead's resolutions: an annotated function satisfies its type when, for every argument its type accepts, the function accepts it (annotations are constraints): `<T: SomeConstraint>` implements `<T: Other>` only when `Other` satisfies `SomeConstraint`, so a constraint can't be narrower than the type's (`E-` code chosen by the analyzer engineer). Explicit arguments at a call stay `first<Integer>(items)`. Phase 1 (syntax and today's semantics): a generic function declaration means what `function first(Item) = …` means today. Phase 2 (new semantics): generic lambdas and generic function types as values (a parameter typed `<T>(value: T) => T` called at several types). Natively, a generic function value is passed with the instances its receiver needs, which the whole-program analysis knows (the receiver's uses, per instance of the receiver), with no boxing; on JavaScript it is a plain function.
  - **Phase 2, done** (2026-11-04): a generic function type binds its own parameters (`FnSig::generics`), not free in the types around it. A generic lambda checks its body with its parameters rigid; an expected generic function type gives its parameter types (renamed to the lambda's). Each call of a generic value instantiates its parameters (inferred like a generic call, or explicit, `f<Integer>(1)`); given where a function type that isn't generic is expected, the value is instantiated (recorded on the value node). A generic `function` declaration given where a generic type is expected is a generic value. `function f: Identity = <T>(…) => …` is called as its type says. Codes: `E-GEN-1` (another number of parameters, or a constraint narrower than the type's), `E-GEN-2` (a function that isn't generic where a generic type is expected). `let f = <T>(…) => …` stays `E-DECL-6` (a function is declared with `function`); generic values are stored in fields, collections and other `let`s, and returned. Natively (design in `design/llvm-backend-plan.md`, "Generic function values"): the usual function pair whose first word is a constant table of the instances its type's class is called at in the program, filled at the end of the lowering; a class that keeps growing is a polymorphic recursion error naming its first types; per-unit builds compile such a program as one module. JavaScript: plain functions.
- **Flag day of the generics migration** (lead, 2026-11-04): in two steps. Step 1, when the running engineers have merged (no new shift starts before it): `fa migrate-generics --write` over the repository's Fa code (not `documentation/`), the Fa embedded in Rust tests reviewed by hand (tests of the old spelling stay, the others move), printed types (`ARGUMENT_BRACKETS`, diagnostics, hover, `@typeToString`) and `fa bind`'s output switch to `<>`. Step 2, after the rewritten documentation lands: the old spelling becomes an analyzer error whose message gives the new one (and a `fa migrate-generics` hint), the old declaration lists (`type Pair(Left, Right)`, `function first(Item) =`) become parser errors, and the transition code is removed. The engineers' decisions of the parser work are accepted: a generic list ends only at its `>` or an enclosing bracket, `<` before a line break is a comparison (so generic lists stay on one line), a top-level comparison inside a list is an error, `Array< Integer>` is diagnosed only when the `<` touches a capitalized name and a `>` follows on the line.
- **Dense maps: entries that move when no reference can see them** (lead, 2026-11-04; native): the entries of a `Map` live in stable chunks so that a reference into a value survives insertions. When the whole program is lowered in one module and nothing in it can keep such a reference for maps of a given type, their entries are one contiguous array that moves when it grows (the chunk directory keeps the live bits and the free list): a lookup reads the index slot, then the entry, without the directory. The fact, per map type, syntactic and conservative over every file (`program::unsafe_maps`): no node of that type appears in the value of a `use`, `mutable use`, `reuse` or `provide`; in an argument of a call of a function of the program other than as the whole argument (parameters are references: `f(map[key])` points into a value); or in a lambda (a callback may run while its caller holds a value). Refined 2026-11-05: a `use` whose block, after it, calls no function of the program, creates no closure and changes no map (no built-in method of a map but its reads, no assignment of a map item) dies before any entry can move: it doesn't count (`facts::short_reference`; `words`' `use count = counts.getOrInsert(word, 0)`). `GrowingMap`, whose type promises stable values, and sets keep their chunks; programs compiled per unit too (each unit would have to agree). Rejected for now: keys and values in the probe array itself (the entries would move at every deletion's backward shift, and the generated code reads an entry after the index lets go of it); measured gain of the dense entries on `lru`: 34.0 M → 32.1 M instructions.
- **Field defaults across files**: a typed literal of a type declared in another file fills in the fields it omits with the defaults that file evaluated at compile time (`Interface::field_defaults`, `FieldValue::Constant`, emitted like a compile-time value: a fresh value per literal). A default that isn't a constant expression (`at: Integer = now()`) must be given by the literals of other files (`E-OBJ-2`, saying why): evaluating it would need the other file's scope at run time.
- **`WorkerPool.submit` errors** (lead's shift): the task of `pool.submit(work)` fails with the errors of `work` (the callback's `throws` is a parameter `Errors` of `submit`, bound by unification: `unify` now binds the errors of function types when they hold a parameter) and with `WorkerTimeout` unless the pool is known to have no `timeout`: a local of a function (not a module-level value, a field or a parameter), declared with a `WorkerPool(T) { … }` literal without `timeout`, whose name (by its text) the file never assigns with anything else nor aliases with `use`. JavaScript runs the work on the main thread (its errors settle the task); natively, a job's raw result is the work's `{ value, error }`, and a task that can't fail stores the value alone. The `FnInfo::throws` of a lambda is the effective one (inferred from a single-expression body), which native code follows.
- **Fewer errors satisfy more** (lead, 2026-11-04): a value whose type throws fewer errors satisfies a type that throws more — `Task(T)` is a `Task(T) throws E`, `(x) => T` is a `(x) => T throws E` — wherever the analyzer accepts it, on every target. Natively: a task's promise always has room for an error (`{ value, error }`, the error alone for a task without value; null when it can't fail), so the conversion keeps the same frame (`promise_type`, `to_promise_raw`/`load_promise_raw` in `tasks.rs`: what a function returns is stored with a null error, and a reader that can't fail never reads the slot). A function value's convention differs (a value, or a value and an error): it becomes a closure of an adapter whose environment holds a copy of it (`adapt_function_errors` in `closures.rs`); a function or lambda value is typed with its own function type, and converted to the type it is given to. Also: `await` consumes the task of any place (a field, an item: the place gives it up), and the task of a parameter is left to its caller, which owns its frame (it was freed twice).
- **Tasks and worker handles move** (lead, from `concurrency.md`: a task can't be copied): passing one to a function (a direct call or a function value), storing it in a field of a literal, capturing it in a lambda, assigning, returning, pushing it or giving it to `Task.all` moves it; a later use of the local or parameter is `MEM002` (on every path: a move on one branch, in a loop). The callee owns a task parameter: natively the caller gives the task up (its place becomes null, which drops skip), the callee drops it at its end unless it moves it on (returned, stored, awaited: `give_task`), and a task read from a field of a temporary object moves out of it. JavaScript has no frees: only the analyzer's errors apply.

- **Small map entries in the probe array** (lead, 2026-11-04; native): a dense map whose key is an integer of 8, 16 or 32 bits and whose value is at most 32 bits (`Map<Int32, UInt32>`) keeps its entries in the probe array: a slot is the low 32 bits of the hash (0: empty; a hash whose low bits are 0 is stored as 2^31, same home slot) followed by the entry, so a lookup reads one array. A position is a slot. `fa_table_remove` only finds the entry; the backward shift happens when the generated code releases it, after reading it (the lowering order the shift needs). Positions change at a release and at growth only, which no generated code holds across. Excluded: map types some `deleteWhere` iterates over (a shift during the iteration would move entries it has yet to visit; `program::no_inline_maps`), wide tables (more than 2^31 slots: out of memory). Measured: `lru` 30.9 M → 28.6 M instructions, CPU 1.43x Goose.
- **Dense maps across units (design, not implemented)**: per-unit builds keep stable chunks today (`with_whole_program`). To let them use dense and inline entries, each unit's interface records, per map type its code mentions, whether the unit has a reference use of its values (the `unsafe_maps` fact) or a `deleteWhere` over it; the driver unions the records of every unit of the program (the reachability walk already visits every interface) before lowering any unit, and passes the two sets to each unit, so that every unit computes the same layout for a type. A unit lowered alone (`fa check`, the language server) never needs the layout. Found when starting it (2026-11-04): the root session of `compile_package` holds the interfaces, not the bodies (each unit is analyzed again in its own session, `compile_units`), and `TypeId`s differ between those sessions; so the fact has to be produced by each unit's analysis and published in its interface (keyed by the type's display name: two types sharing a name merge their facts, which only makes the layout more conservative), the union passed to every unit and hashed into each unit's object cache key (a change anywhere recompiles the units whose map layouts it changes).
- **Index proofs for fields (implemented 2026-11-05 for programs lowered as one module from one file, `src/lower/index_proofs.rs`; per unit: to publish through `facts.rs`)**: `lru`'s `unlink`/`linkFront` check indices read from fields. The fact, per field `T.f` of an integer type and per array place `X` (a module-level or local array of `T`, named by its declaration): "`T.f` holds an index of `X`" when every store to `T.f` in the program (literals of `T`, assignments, compound assignments) is a constant in `0..k` with `X.length >= k` at every use (the sentinels, `X` initialized with `k` items), a read of `T.f` of an item of `X`, a read of another fact-carrying place (the values of a map whose every store is such an index, the items of an `Array<UInt32>` free list idem), or `X.length - 1` right after a push to `X`; and `X` never shrinks (no `pop`, `delete`, `take`, `clear`, `deleteWhere`, assignment of another array, nor a call that may do so, on `X`). Parameters: `nodes[index]` with `index: UInt32` a parameter carries the fact when every call passes a fact-carrying value and `nodes` is `X` at every call. A greatest fixpoint over these places (assume all hold, remove the violated ones). The analyzer would expose it as a range fact on the reads (`INDEX_CHECK` cleared), so both backends benefit.
- **Never-negative places** (2026-11-05, native shift; `src/proofs.rs`, `src/lower/index_proofs.rs`): the claims of the index proofs with another goal, "never negative", so that `get(self.position)` and `x[i]` don't count a negative index from the end (`calc`'s `current()`, `sexp`). A place (field, items, map values, local, parameter, result) holds when every store is: a value whose interval or type is non-negative, a read of a place that holds, and, with overflow checks, a sum or product of such values; without overflow checks (a wrap is defined), a stored value must be at most 2^32 and a compound assignment only `+=` of 0 or 1 (each place then holds at most 2^32 plus the number of steps executed, far from 2^63): `position += 2` proves nothing in a release build. Every claim also fails when its place may be changed under another name: the value of a `mutable use`, `reuse` or `provide`, an argument whose parameter the callee `mutates`, or (for fields) a write through a deeper chain (`a.b.f`) or `.=`; a parameter's claim fails when its function is used as a value (its calls are not seen; this also closed a hole of the index proofs). A program parsing JSON proves nothing. Builds per unit (`fa build` of a package): each unit publishes its part of the claims through `facts::PROOF_CLAIMS` (`proofs::unit_claims`: per goal, `goal|place|dependencies` or `goal|place|!`, the fields, items and map values keyed by stable type names, the locals, parameters and results by module and node; a parameter of a function other files can call, or a value they can write (`export mutable`), fails), the driver resolves the merged edges into the failed places (`FactKind::finish`, `proofs::resolve_claims`, a deterministic propagation, hashed into every object's cache key), and each unit proves its roots against them. - **Index proofs per unit (design, not implemented)**: publish, per unit, the array types of objects it mentions (`a|Array<T>|unit`) and the places it stores to (`s|place|unit`); an array type mentioned by one unit only can be proven inside that unit (its family and its uses are all there), provided every place of the proof is stored only in that unit too. - **A type holding a task is move-only** (lead, 2026-11-04): the documentation already states it for resources ("a type with `destroy`, and every type that contains one, is move-only, like a `Task`", foreign code page), and the same holds for tasks and worker handles: an object, tuple, union or collection that contains one moves when assigned or passed, so `(holder: Holder) => holder.task` receives `holder` by move and owns it. Moving a field out of an owned value leaves the value unusable until the field is assigned again (`MEM002` otherwise); its drop skips the moved field. Moving a field out of a value the function doesn't own (a `use` alias, `self` of a non-consuming method) is `MEM002` with a message saying to move the whole value.
  Implemented (one rule for tasks, worker handles and resources: `TypeStore::is_move_only`; `owns_unique` without the worker handles, which natively share a counted block): `check/foreign.rs` `consume_local` moves a whole local or parameter, or a field of one (`FlowState::moved_fields`, `MEM002` on a later use of the field or of the whole until the field is assigned: `restore_moved_fields`), and reports a field moved out of a `use`, a loop variable or `self`. The backends get the moving reads in `Analysis::moved_reads`: natively the place gives the value up, and a move-only parameter is passed by value and owned by its function (`self` stays borrowed). An item can't move out of a collection (`MEM002`: take it out with `take`), nor a field out of a resource (its `destroy` uses every field).
  Moved resources are tracked by drop flags, never by a zero left in the place (decided): a zero is a valid sentinel only where it is never a valid value (a task's or a worker handle's pointer), while a C resource may be all zero (a file descriptor 0, a handle index 0). Natively (`ownership.rs`), a local or an owned parameter holding a resource has a one-bit drop flag on the stack (LLVM folds it away where the moves are static: only a move on some paths keeps one, checked by `tests/checks.rs` `only_a_move_on_some_paths_keeps_a_drop_flag`), cleared where it moves out; a field moved out of it has its own flag (`field_flags`, the paths of `moved_reads`), set again when the field is assigned (`drop_replaced`), and the drop walks the fields to skip the moved ones (`drop_place`). A move-only field read out of a temporary drops its other fields at once (`drop_all_but`). On JavaScript (`codegen-js/src/generate/resources.rs`), the same points: a generated drop function per type holding a resource (`drop$Holder`: `destroy`, then the fields, items, keys, values), a local or a parameter dropped at the end of its block (`finally`) with a drop flag when it moves out somewhere, a moved field left `undefined` (never a resource, which is an object), a replaced value dropped before the assignment, a discarded new value dropped at once. A resource type of another file is destroyed by its imported `destroy` (`Type$destroy`, the interface's `type_functions`); a named union by the tag of its members; a union of objects by a field the other members lack or a literal discriminant (the analyzer's rule for telling them apart); a recursive type by drop functions declared before their bodies; a new value read by a field access or a method call is dropped at the end of its statement (`guarded`, but a field moving out of it), like natively. - **JSON form of named union members** (lead, 2026-11-05): a member is identified by a `"type"` property holding its member name, as TypeScript's discriminated unions are written: an object member is its fields plus `"type"` (`{ "type": "Circle", "radius": 1 }`); a member without data is `{ "type": "Empty" }`; a member whose data isn't an object, or whose object has its own `type` field, is `{ "type": "Member", "value": data }`; a member defined by a literal stays the literal itself (types-at-runtime page). A program lowered as one module computes the same set over its files. With the fact, a method reads each such field of `self` that its body (with the methods it calls on `self`, a read in a loop counting twice) reads at least twice, once at its entry: scalars and strings, a string with its bytes and length past the inline-or-heap test (`string_parts` returns them for that value). A call `self.m(…)` of a small method (at most 48 nodes, scalar parameters and result, no `return`, `throw`, `try`, closure, task, reference, nor call of anything but built-ins and methods of its own `self`; not generic, asynchronous nor recursive) is expanded at the Fa level into a method that reads fields of the same object once, its `self` standing for the caller's: LLVM's inlining alone reloaded the field after every call the caller made. `calc`'s parser: 139.2 M → 130.7 M instructions (its per-byte test of `self.text` gone; the parser now runs as many instructions as Goose's); `sexp` 94.8 M → 91.0 M.

## Relations across files and reactivity (relations page, reactivity page)

- **Both sides of a relation are declared in one file**, the file that declares the element types (the sides are their fields). The collection may be another file's module-level value (`people.fa` + `Person.fa`, the page's second form): the relation names it **by key** (`CollectionRef::External`), built from the file's module and name without analyzing it, since that file reads this one for the type of its elements. A reverse side over such a collection is typed by the type of this file that declares the direct side it names (its own type for a symmetric side); none is `REL008` ("both sides of a relation are declared in the same file").
- **The collection's own file checks it**: it imports the relation, and reports `REL003` (elements that move) and `REL004` (another element type) on its declaration. `REL019` (not `mutable`) stays on the relation's file, from the kind the other file's scan gives. A `reactive` collection is mutable (`REL019` accepts it).
- **Published, then imported by type**: each file publishes its relations in its interface (`Interface::relations`: the object types of the sides, the collections by key or by owner type, `CollectionRef::ExternalField`), merged and hashed with the interface. A file imports the relations of the files that declared a type when it first looks for a side of it, and at the end of its walk those of every file it may read that declares relations (`FileScan::has_relations`): its values may be of their types (literals, copies, printing). A file of the same cycle whose walk is in progress makes the reader walk again. `Relation` now carries the object types (`holder_type`, `target_type`), `Analysis::relations` lists the file's relations then the imported ones, and `Analysis::relation_sides` gives the backends every side by (object type, field).
- **Effects on another file's export**: `mutates people` of a function of another file is accepted (`EFF008` before; ef-10, adv-15.9-07). Writes of another file's values are still not tracked as effects (they never were), so that declaration is never `EFF011`. A value reached through namespaces (`library.people`) now has a place: `use dan = library.people.add(…)` works, and both backends reach it as a receiver.
- **Builds per unit** (native): a relation side is laid out as the target's address or a set of links, not as a copy, so every unit must agree on it. Every unit already imports the relations of the files it reads; an instance emitted by a module that doesn't read the relation's file takes the sides from the program's facts (`facts::RELATION_SIDES`, `<stable type name>\u{1f}<field>`), the representation following from the field's type.
- **JavaScript, erased generic code**: an element of a type with sides carries `[faSides]` (a constant array of their names, `Symbol.for("fa.sides")`), so that `faCopy` copies it without links (D18), and `faFormatObject`, `faDeepEquals` and `faHash` leave its sides out (D21). A relation pool field no longer makes its type an "owner of related elements" (copies of elements went through `faCopyGraph` and kept their links). An empty pool, set or map given as the default of a field of another file's type is built as such (it was an array on JavaScript and unsupported natively).
- **Reactivity: a relation side is a source of its object**, like a `reactive` field, when it is read below a reactive place, or through a parameter (a function's, a callback's: `people.find((person) => person.bestFriendOf.size == 0)`). A write of a direct side there notifies exactly the sides it changes, on each object: the holder's direct side, the reverse side of the previous and of the new target, the direct side of the target's previous holder (one-to-one), the previous partners (symmetric); a removal the sides of the elements that pointed at the removed one. No collection source is notified: relation sides are not data (D21), so a reader of `people.size` or of another element's sides doesn't run again (`Analysis::relation_notifies`; `faNotifyField` given to the JavaScript helpers; a `notify` flag of `fa_relate_*` and `fa_unlink` natively, the sources of sides keyed by their byte offset with bit 62 set in `fa_field_source`). The static may-write sets include the implied sides (§8.6): a `watch` that writes `ana.bestFriend` and reads `bao.bestFriendOf` is `REA003`.
- **Not yet**: a function of a file without reactivity that writes sides doesn't notify (reactivity is instrumented per file); erased generic code on JavaScript shares an element it pushes instead of copying it without links (the copy is elided for type parameters).

## `Fields` types and key sets (types brief §3.9, 2026-11-05)

- **Identity**: a `Fields` type is the interned ordered flag tree that `Keys<T>` already built (`TypeKind::Fields`: a leaf is a string literal, a group a tuple of its name and its own tree), not a list of dotted leaf paths: the two are equivalent (names are unique per level and a group's leaves are contiguous), and the tree is what `Keys`, `Pick` and printing need. `type A = Fields { … }` names the type for messages; two declarations with the same tree are one type (the first name is shown).
- **Values are compile-time constants**: `T { … }`, `T.flag`, `T.group`, a key set `{ … }` where a `Fields` type (or an optional of one) is expected, and `+`/`-` of constant operands get their bits in `Analysis::constants` (an `Integer`); the backends emit the number. A value lists flags and groups; `group {}` lists nothing (allowed in a value, `TY090` in a declaration). Unknown names are `TY092`, also for a `static` typed `Keys<T>` (it is a plain `Fields` type then); `TF010` only for a key set given as a compile-time argument or to a key-taking type function.
- **Operations**: `+`, `-`, `+=`, `-=` (both sides of the same `Fields` type, `E-TYPE-1` otherwise, also for any other arithmetic operator), `is in` / `is not in`, `==`, `Integer(s)` and the other integer conversions when the target holds every value of the set (`E-NUM-16` otherwise, suggesting `UInt128`), `toStringArray()`. A set prints as a key set, `{ read, nested { a } }` (`{}` when empty), also nested in composites. **JSON** (lead's choice, readable): a set is the array of the dotted paths of its flags, as `toStringArray()` (`["foo","nested.baz2"]`); reading accepts a flag or a group's name (all its flags), duplicates included; another name is a `JsonError` listing the accepted names (natively the array is checked as an enumeration of the names, the same message on every target). **`when`**: an arm whose pattern is a value of the subject's `Fields` type (`T { … }`, `T.flag`, a key set) matches an equal set; such arms cover no type, so the other sets need an `else` (`E-WHEN-1`). Not yet: sets as `is` patterns.
- **Representations**: JavaScript, a number up to 32 flags (bit operations, `>>> 0` at exactly 32 flags), a `bigint` above; natively an unsigned integer of 8, 16, 32, 64 or 128 bits (`Repr::Int`, unsigned; at most 128 flags, so no array of words is needed). Printing and `toStringArray` are unrolled over the flags natively, table-driven on JavaScript (`runtime/fields.js`) and in the interpreter.
- **`Keys<T>` order**: the declaration order of `T` (its `type` declaration, else the order the anonymous object type was first written in, else the shape's order).
- **Key-set compile-time parameters** (`<Value, keys: DeepKeys<Value>>`): the argument is checked against the keys of the subject's type argument (`TF010`, the subject must come first) and bound to `Tuple(Fields type, bits literal)` (`Analysis::key_set_params`). In the body the parameter is only the iterable of `@for` for now (`AN001` elsewhere: `Pick<Entity, keys>` and `pick(entity, keys)` of gn-22/gn-23 belong to the generics work and can build on this binding).
- **`@for key in keys` over a key set** (a key-set parameter, a `static` key set): `key` is the dotted path of a key (a `String`); the body is checked once per key after unrolling (lead, superseding a first single generic check), `value[key]` at that key's field type: over a `static` key set at once, over a parameter for each application of the file once the module is walked, in the context saved at the loop (the function's own walk of the body is quiet). An error there is `TF011`, naming the key (and noting the application); the same error for several keys is reported once. The target must be a value of the key set's subject type, or for a `static` key set hold every key (`TF011`). Each check leaves a snapshot of the file's analysis (`Analysis::key_loop_bodies`) that the backends lower the key's body with. Natively the loop is unrolled per instance; on JavaScript it is a `for…of` over the keys when every key (of every application) gives the same code (`value[key]` read with `faFieldAt`), else unrolled (fields read directly; for a parameter, a `switch` on the application's index, its hidden value: `Analysis::key_set_instances`). Applications from other files are not checked per key (`GN008` there).
- **Effects on another file's values are tracked** (lead, 2026-11-05): a function that writes a module-level value of another file (directly, through a call, or a relation side) has that effect in its signature as seen by callers, through the interfaces, exactly like an effect on its own file's values: facts about that value are invalidated after the call (fine-grained: the written path and below only), and an undeclared write is reported as for local values. Until now these writes weren't tracked, so `mutates people` on an import was never checked (`EFF011`) and callers kept stale facts.
- **Native executables stay position-independent** (lead, 2026-11-05): PIE (address randomization of the main binary) is kept; its cost must go instead: every symbol of the program and the runtime that isn't exported is `dso_local` with hidden visibility, so it is addressed relative to the instruction pointer without the GOT and without holding addresses in callee-saved registers.
