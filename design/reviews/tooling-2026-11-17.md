## Findings in detail

Environment for every repro: `source /tmp/audit-tooling/env.sh` = `PATH=<fa without fa-native>:~/.bun/bin:$PATH`, `FA_CACHE=/tmp/audit-tooling/cache`, `R=/home/claude-dev/fa-lead/reports/repros/tooling`.
Most runs used the trunk's release `fa` at `0eea9cc9` (a descendant of `5e3b602d`, no CLI change in between) while the audit build compiled; W1, S1, S2, C3, P1, P3, P7, C1, C4 and W2 (3 of 12 concurrent builds fail) were then re-run on the debug `fa` built from `5e3b602d` and reproduce identically.

### S1. `@import` never works in a standalone file (doc promises it, message is circular)
```
cd $R/standalone-import   # main.fa: use weather = @import("file://$R/remote/weather.fa")
fa run main.fa            # error[META010] … isn't resolved: `fa` resolves it when it builds the package (`fa check`)   exit 1
fa check main.fa          # same error, exit 1; no dependencies.lock written
```
`architecture/overview.md` ("Remote modules can be imported with `@import` … locked in a `dependencies.lock` file next to the standalone file") and `dependencies.md` ("one lockfile … per standalone file, next to it"). Cause: `project.rs` `load_session` never resolves dependencies for a non-package (`warnings: Vec::new()`). The message tells the user to run `fa check`, which fails the same way. Fix in the tool (resolve the `@import`s of a standalone program with a lockfile next to the file), and `fa update` must accept a standalone file (see S3).

### S2. `fa test <file.fa>` passes silently with zero tests
```
cd $R/standalone2         # mySiblingFile.fa + mySiblingFile.test.fa (one test)
fa test main.fa                 # "fa test: no test file (`*.test.fa`) in this package"  exit 0
fa test mySiblingFile.test.fa   # same, exit 0
fa test                         # CLI001, exit 1
```
A standalone folder's tests cannot be run at all, and the file form exits 0 (a CI step is green with no test run), with a message that talks about a "package". `fa help test` documents only `[<package>]` yet the file is accepted without a usage error. Fix in the tool: either run the `*.test.fa` files of the standalone program (the docs' "standalone file … like a package" model) or reject a file argument with a usage error (exit 1). Already listed as "silently unsupported" by the inventory (§6), still open.

### S3. `fa update` has no form for a standalone file
`fa update` in `$R/standalone2` → `CLI001 … run fa update in a package or a workspace`, and it takes no path. The docs give standalone files a lockfile; there is no way to update it. Tool (accept `fa update [<file.fa>] [<dependency>...]`) or page.

### S4. Bun swallows one extra `--` in `fa run`
`fa run allargs.fa -- -- a` → program sees `[a]` (1 argument); docs: "a `--` right after the file is accepted and dropped", so `[--, a]` is expected. `node build/node/main.js -- a` keeps `--`. Low; tool (`run.rs`: pass `--` to Bun before the script's arguments, or call `bun run <script> -- …`).

### P1. `fa build scripts/x.fa` overwrites the application's build, and `fa preview` then runs the script
```
cd $R/pkg/hello          # fa new package hello + scripts/seed.fa
fa build --target=bun    # build/bun/main.js runs application/main
fa build scripts/seed.fa --target=bun   # writes build/bun/main.js again: now `import … from "./scripts/seed.js"`
fa preview --target=bun  # prints "seed 0 / Hello, seed!" instead of the application
```
Docs: scripts are "one-off scripts, run with `fa run`"; `fa build` help says "a script too" but nothing says it shares the application's output folder. Tool: build a script into `<output>/<target>/scripts/<name>/` (or refuse to build scripts).

### P2. `fa run` without a path doesn't run the current package
In a package: `fa run` → `fa run: which file? ex: fa run main.fa` (exit 1), while `fa check`, `fa build`, `fa test`, `fa preview`, `fa develop` all default to the closest package; `fa run .` works. The `fa new` message even says "`fa run .`". Tool: default to `.` (or say "`fa run .` runs this package").

### P3. `fa run application/main.fa` (or any non-script file of a package) runs it as a standalone file
```
cd $R/pkg/hello/library
fa run ../application/main.fa   # warning W-DECL-1 `arguments` hides the built-in; error E-DECL-1 `library` is not declared
fa run greet.fa                 # MOD015 the entry function takes (arguments)…
```
The natural newcomer command fails with errors that don't mention the package. Only `scripts/` files run in their package (`project.rs` `locate`). Tool: when the file is the package's entry, run the package; for any other file inside a package, say "`x.fa` is a module of the package `hello`: run the package with `fa run <package folder>`, or move the file to `scripts/`".

### P4. Defaults that fail without the native backend
`fa build` of a standalone file or of a fresh `fa new package` (default targets `web`, `bun`, `native`) exits 1 when `fa-native` is missing, after building `web` and `bun` (`CLI009`, clear message). A newcomer following `hello-world.md` ("`fa build`") gets a failure. Acceptable if the release always ships `fa-native`; otherwise report the native target as skipped (warning) when it isn't explicitly requested. Tool decision for the lead.

### P5. Documentation drift found while following the pages
- `getting-started/installation.md`: "the `fa` command-line tool described on this page is **not built yet**", "Once the `fa` command exists…", crate table lists 3 crates, the language server "reports syntax errors" only. All stale. Page.
- `architecture/overview.md`: "`fa build` writes … JavaScript modules … (bundled into one `main.js` for `web`)": `build/web/` holds `main.js`, `$runtime.js`, `application/`, `library/` (unbundled). Page or tool.
- `testing.md` "Coverage" (`fa test --coverage` writes LCOV to `build/coverage`) and the installation table (`--coverage`): the tool says "`--coverage` is not available yet" (exit 1). Page (mark as planned) until implemented.
- `guides/performance.md`: `fa preview --profile` → "unknown option `--profile`" (exit 1). Page.
- `hello-world.md` shows `package.fa` with `targets = ["web", "bun", "native"]`; `fa new package` writes no `targets` (same default) and an `application/main.fa` taking `(arguments: Array<String>)` rather than `()`. Cosmetic; page.
- `guides/build-your-application.md` "Scaffold" shows an empty `library/` and no test; the scaffold has `library/greet.fa` and `greet.test.fa`. Page.

### P6. `fa preview --target=web` leaves its Bun server running when `fa` is terminated
`fa preview --target=web & sleep 4; kill %1` → `bun …/cache/run/preview-3000.mjs` is reparented to PID 1 and keeps port 3000 (`ss -ltnp`). Ctrl-C in a terminal kills the group, so it shows up under IDEs/supervisors/CI. `fa develop --target=web` did not leak in the same test. Tool: forward SIGTERM / kill the child on exit.

### P7. A library-only package "builds", "runs" and "previews" an empty program
```
cd $R/ws/myWorkspace      # `shared` has no application/
fa build shared --target=bun   # exit 0, writes build/bun/main.js = `faRun(()=>{})` (+ stale application/ from an older build, W3)
fa run shared                  # exit 0, prints nothing
fa preview shared              # "running the `bun` build", exit 0, nothing
fa develop shared              # "the package has no application to run (`application/main.fa`)", exit 1   ← the right behaviour
```
At a workspace root, `build`/`preview` skip such packages (they implement only "with an application"), so the named form disagrees with the "all" form. Tool: `build`, `run`, `preview` of a package without its entry file → the `develop` message, exit 1 (a library is checked with `fa check`, tested with `fa test`).

### P8. `fa build --output=<dir>` is relative to the current folder, not to the package
From `hello/library/`, `fa build --target=bun --output=out1` writes `hello/library/out1/bun/` (inside the library source folder), while `build.output` in `package.fa` is relative to the package. Docs don't say. Low; page (say "relative to the current folder") or tool.

### D1. One bad tag in a Git library blocks every consumer's `fa update`
```
# farm.git has v1.0.0, v1.1.0 (package.fa 1.1.0) and v1.2.0 whose package.fa still says 1.1.0
cd $R/deps/consumer      # farm = "git+file://$R/git/farm.git@1"
fa update farm           # error[DEP003]: the version 1.2.0 … is rejected … exit 1; lock stays at 1.0.0
```
`dependencies.md`: "otherwise the version is rejected with an error". The consumer can't fix the library's tag and can't move to `1.1.0` with `@1` (only by pinning `@1.1`). Page ambiguity ("rejected" = skipped, or fatal?) for the lead; recommendation: skip the mismatching tag with a `DEP003` warning naming it, and choose the latest valid version.

### D2. `fa update <key>` is blocked by an unrelated changed dependency
With `shared` (a local path dependency) changed since locking, `fa update farm` fails with `DEP001` for `shared`. The help text is right (`fa update shared`), but updating `farm` alone should not need it. Low; tool.

### W1. Errors in `workspace.fa` are silently ignored
```
cd $R/edges/ws1
printf 'export = {\n\tname = \n' > workspace.fa          ; fa check   # exit 0, nothing reported; fa run api works
printf 'export = {\n\tnmae = "x"\n}\n' > workspace.fa   ; fa check   # exit 0, no "did you mean `name`"
```
The same mistakes in `package.fa` give `AN002` / `E-OBJ-1 … did you mean version?` (good). `configuration.md`: "a typo in a field name or an invalid value is an error". Cause: `workspace::workspace_configuration` keeps only `evaluate_source(..).0` and drops its diagnostics, and no command analyzes `workspace.fa`. Tool; high (the workspace defaults silently stop applying).

### W2. Concurrent `fa build` of one package fails (shared `.partial` folder)
```
cd $R/pkg/hello; for i in 1 2 3 4; do fa build --target=bun & done; wait
# 3 of 4: "fa build: can't write `…/build/bun/main.js`: No such file or directory (os error 2)", exit 1
```
Intermittent (a second batch passed). `build.rs:594-598` `stream_build` uses `<output>.partial` with no process id and starts with `remove_dir_all(partial)`, so builds delete each other's staging folder. Happens with an editor's build-on-save next to a terminal build, or `fa develop` + `fa build`. Concurrent `fa run` (finding 5 of the 2026-11-05 review) is fixed: 6 parallel runs all pass. Tool: `.partial.<pid>`, then rename.

### W3. `fa build` never removes stale modules from the output folder
`library/stale.fa` built once, then deleted: `build/bun/library/stale.js` stays, as do `scripts/` (from P1) and foreign files (`junk.txt`). For `web`, a deleted module keeps being deployed. Docs are silent. Tool: delete the files of the previous build that the new one didn't write (keep a manifest), or document it.

### W4. Workspace-level `dependencies.fa` errors repeat once per package, with absolute paths
`printf 'export = {\n\tfarm = \n' > dependencies.fa; fa check` → the same 2 errors printed under each package, as `/home/…/ws1/dependencies.fa:3:1`, while every other diagnostic is relative to the current folder. Low; tool.

### W5. Package dependency cycles are accepted without a word
`shared` → `api` → `shared` (each `dependencies.fa` naming the other, with code using both directions): `fa check`, `fa run api`, `fa test shared` all pass. The pages neither allow nor forbid it (the 2026-11-05 review said a cycle gives `MOD007`; no longer true at this commit, or only for initializer cycles). Language/design question for the lead: allowed (like function cycles), or an error naming the cycle?

### W6. `DEP008` for a missing sibling path says neither why nor how to fix
`nope = "../nope"` in a workspace package → `error[DEP008]: nope = "../nope" is not a package of the workspace` (absolute file path, no `help:`). `dependencies.md` documents `DEP008` as "a fetched dependency declaring a local source", a different error. Tool: own code, and "no `package.fa` in `…/nope`: create the package or fix the path".

### C1. `fa <command> --help` works for no command
`fa run --help` → "`--help` is neither a .fa file, a folder, nor a package of a workspace" (exit 1); `fa check|build|test|format|update|preview|develop --help` → "unknown option `--help`: see `fa help <command>`"; `fa new --help` → "what to create?". Only `fa --help`/`fa -h`/`fa help <command>` work. Every newcomer tries `fa build --help` first. Tool: treat `--help`/`-h` anywhere before the file/`--` as `fa help <command>`, exit 0.

### C2. No spelling suggestion; the whole help is dumped instead
`fa buidl`, `fa chek`, `fa help buidl` → "unknown command `buidl`" + the 25-line summary (exit 1, correct). `fa new pacakge x` → "what to create?". Options: `fa build --target bun` / `--output dir` (space form) → "unknown option `--target`" although the option exists (and `fa bind --output <file>` *requires* the space form). Tool: "did you mean `build`?"; accept `--option value` or say "write `--target=bun`".

### C3. `--format=json` loses every error that stops the load
`fa check --format=json` prints `CFG004`, `DEP001`, `DEP006`, `DEP008`, `CLI001`, unreadable files… as text on **stderr**, nothing on stdout, exit 1: an editor or CI parsing stdout sees a failure with no diagnostic. Analysis diagnostics, configuration errors (`E-OBJ-1` in `package.fa`), syntax errors and the `DEP004` warning (`"file":null,"range":null`) are JSON. Repro: `cd $R/edges/ws1; mkdir -p packages/copy && cp packages/shared/package.fa packages/copy/; fa check --format=json 2>/dev/null` → empty, exit 1. Tool: emit load errors as JSON objects (`file`/`range` null when unknown).

### C4. `fa help | true` panics (broken pipe)
`for i in 1 2 3 4 5; do fa help | true; done 2>&1 | grep -c panicked` → 5 (`failed printing to stdout: Broken pipe`, from `print!`). Same for `fa -h | head -0`. Low, but it breaks the no-panic rule; any `print!`/`println!` path of `fa` can hit it (`check --format=json | head`). Tool: write through a handle that treats `BrokenPipe` as exit.

### C5. Documented options the commands reject or ignore
- `fa test --overflow-checks=false` → "unknown option" (exit 1); `configuration.md`: "`fa build`, `fa run` and `fa test` take the same option as `--overflow-checks=true|false`". Tool or page.
- `fa build -O2 --target=bun`, `fa build --emit-ir --target=bun` succeed silently (LLVM-only options ignored on JS targets). Low; warn.
- `fa test --target=bun --target=wasm`: the last one wins, silently. Low.
- `fa check` has no `--target` (it checks every configured target); fine, but undocumented asymmetry with `build/test/develop/preview`.

### C6. `fa new` creates nested projects without a warning
- `cd hello/library; fa new package inner` succeeds; then `fa check` of `hello` fails with `library/inner/application/main.fa:3:14: error[E-DECL-1]: library is not declared` (the inner package is read as modules of the outer one). A workspace reports `CFG006` for a nested package; a standalone package doesn't. Tool: refuse (`CLI007`-like) inside a package, or `CFG006` everywhere.
- `fa new package rootpkg` at a workspace root (not in `packages/`) succeeds; the package is not part of the workspace (`fa check` skips it) yet `fa run rootpkg` works (as a folder). Tool: say "packages of a workspace go in `packages/`".
- `fa new workspace inner2` inside a package succeeds. Low.

### L1. Release JS builds spawn Bun once per module to minify
600-file package (`$R/large/big`, 7 MB): `fa build --target=bun` 29 s, of which `minify` 31 s CPU `(×603)` in `--timings`, vs `fa check` 4.8 s and `--minify=false` 14.9 s. `build.rs` runs `bun build --minify` per module. Tool: one `bun build` call for all modules (or minify in-process). Medium (release builds of real apps).

### L2. `fa build` analyzes the test files
Same package, `fa build --timings`: "units 1201 … largest unit `library/m99.test`" (600 library files + 600 test files + the entry). Docs: test files "are excluded from builds". Half the analysis of `fa build` is wasted. Tool.

### L3. Lockfile edges
- Prior critical finding 1 (a forged `hash` deleting a folder) is **fixed**: `hash = "sha256:/tmp/…/victim"` → "not a valid lockfile … the hash of `…` is not `sha256:` followed by 64 hexadecimal digits", folder intact.
- An invalid lockfile has no error code (`error: … is not a valid lockfile`), and `fa update` refuses to rewrite it ("delete it, then run `fa update`"); `fa update` is the natural repair command. Low; tool.
- A lock entry whose `version` is inconsistent with its `commit` (`9.9.9`) is silently re-resolved instead of reported. Low.
- Changing a range in `dependencies.fa` (`@1` → `@1.1`) makes the next `fa run` move the lock from 1.0.0 to 1.1.0 without a message. `dependencies.md` says both "a locked version is never changed implicitly" and "a source added … is resolved by the next command": a changed range falls between. Page: say it; tool: print "farm 1.0.0 -> 1.1.0 (range changed)".
- A tag deleted upstream stays in the cache's mirror (re-resolution still saw `v1.2.0` after `git tag -d` in the bare repo). Low.

### L4. Message and path presentation (low, tool)
- The same diagnostic is shown as `library/m10.fa` by `fa test` and `./library/m10.fa` by `fa run .`; `fa build` from a subfolder prints `wrote /home/…/build/bun/main.js` (absolute) and from the root `wrote build/bun/main.js`.
- A workspace-wide `fa test` prints one total per package and no grand total.
- `fa test` of a test file with no test (`let x = 1`) is silent (no "no test in `…`").
- `TEST004` is not reported on the default branch before its first commit (`git init -b main`, no commit: `test only` passes; after one commit: `TEST004`). Very low.
- `fa build api` with an invalid `targets` value in `package.fa` builds the default 3 targets, printing the same 2 configuration errors once per target.

### G1. Following the guides literally
- `guides/build-your-application.md` (`$R/guide/scores`, every `-- path` block written as is): `fa check`, `fa test` (4 passed), `fa run . scores.csv`, `fa build --target=bun`, `fa preview` all **work**. But the guide's code yields 4 `W-DECL-2` warnings ("the error `error` is never used") on every command, 2 of them in the test file, which `fa build` also prints (confirms L2). Page: write `catch _error =>` (or whatever the unused-binding form is) in the guide.
- `guides/web-server.md` (`$R/guide/api`): nothing compiles: `std.http` "is not a module of the standard library the compiler knows" (14 errors). The caution says the API is "provisional and will change", not that it doesn't exist. Page: say "not implemented yet", or move the guide under a "planned" banner.
- `guides/hello-world.md`: every step works on Bun (`fa run hello.fa [Ada]`, `fa new package hello`, `fa develop`, `fa test`); `fa build` fails only on `native` without `fa-native` (P4).
- `guides/deploy-a-library.md`: consuming a tagged Git library works (`git+file://…@1`, lock written, `fa update farm` moved 1.0.0 → 1.1.0 once the bad tag was removed); `fa test --target=native|wasm` need `fa-native` (clear `CLI009`).

### C7. A busy port gives a Bun stack trace, and `fa develop` keeps waiting
```
cd $R/pkg/hello; fa develop --target=web &      # serves on 3000
cd $R/edges/ws1; fa develop --target=web api    # Bun source excerpt + "error: Failed to start server. Is port 3000 in use? … EADDRINUSE … at …/develop-server.mjs:19:20"
                                                # then "fa develop: the program exited with code 1; watching for changes" (never exits)
```
No `--port` option either (only `develop.port` in `package.fa`). Tool: check the port first: "port 3000 is in use: stop the other server, or set `develop.port`", exit 1.

### C8. `fa format` doesn't take a package name in a workspace
`fa format --check shared` at the workspace root → "`shared` is neither a file nor a folder" (exit 1), while `check|build|test|develop|preview shared` work and `workspaces.md` lists `format` among the commands run per package. `fa format --check` prints absolute paths from the root and relative ones with a folder argument. Low; tool.

### C9. Name/folder ambiguity in workspace selection
A package named `server` in `packages/api`: at the root `fa run api` → `CLI004 … its packages are server, shared` (good), but from `packages/`, `fa run api` runs it as a folder. A folder argument always wins over a package name, silently. Low; document it ("a path, else a package name").

## Memory: what the repository's tests cover

- `tests/memory.rs`: `fa check` under `ulimit -v 512 MB` on one typical 5,000-line file, compile-time evaluation, and (ignored by default) a 50,000-line file and a static array of millions of items.
- `tests/package_memory.rs`: `fa check` of a generated 2,000-file package, peak RSS < 512 MB (ignored by default, release).
- `tests/format_memory.rs`: `fa format --check` of the repository and of pathological generated files under 512 MB.
- **Not covered**: `fa build` (JS codegen + minify, or LLVM) of a large package, `fa test` (many files, many Bun workers: the workers' memory is not bounded together), `fa run`, `fa develop` over many reloads (growth), a workspace of many packages, `fa build --target=native` with LTO (the LLVM side is the likely 512 MB breaker), `fa-native`'s JIT for `fa test --target=native`.
- Measured here (600 files, 7 MB, debug-free release binary, `/usr/bin/time` max RSS incl. children): `check` 96 MB / 4.8 s; `build --target=bun` 113 MB / 29 s; `build --target=web` 116 MB; `test` 120 MB / 127 s (600 files, 600 tests); `run .` 107 MB / 10 s. 30-package workspace `check`: 23 MB / 4.8 s. No JS-side memory problem; the time of `build` (L1) and `test` (one Bun process per file) is the issue.
