# Foreign code

Fa calls C libraries, and exposes Fa libraries to C, Python, Rust or any language that speaks the C ABI. A call between Fa and C is a direct call, with the C calling convention: it costs the same as a call between two C functions.

The compiler can't check C code. So everything that touches C lives in **foreign files**, the only place where the compiler trusts declarations instead of proving them. A foreign file binds a library and exports a safe interface; the rest of the program uses that interface, and keeps every guarantee of Fa.

## Foreign files

A foreign file ends with `.foreign.fa`, and is named by the part before it: `Database.foreign.fa` is `Database`. Like any file, it has a [single export](/architecture/modules).

Only foreign files can:

- declare C functions with [`@extern`](#declaring-c-functions), and call them;
- use [`Pointer(T)`](#pointers) and [`CString`](#c-types);
- declare a [`destroy`](#releasing-c-resources) function in a type.

Other files can't use a value whose type contains `Pointer` or `CString`, so the unchecked part of a program can't leak out of its foreign files. Keep them small: the bindings of the library, and the safe interface built on them.

A typical binding has two foreign files: the raw bindings, generated by [`fa bind`](#generating-bindings), and the safe interface written on top of them.

```fa
-- sqlite3.foreign.fa, generated by `fa bind sqlite3.h`, then edited
use c = std.c

export namespace = {
	type Sqlite3 = CStruct { } -- an opaque C type, only used behind a pointer

	static ok = 0

	function open: (path: CString, database: Pointer(Pointer(Sqlite3)?)) => c.Int mutates database = @extern("sqlite3_open")
	function close: (database: Pointer(Sqlite3)) => c.Int = @extern("sqlite3_close")
}
```

```fa
-- Database.foreign.fa
export type = {
	#handle: Pointer(sqlite3.Sqlite3)

	type OpenError = Errors { Failed = { code: Integer } }

	function open = (path: String): Self throws Self.OpenError => {
		mutable handle: Pointer(sqlite3.Sqlite3)? = none
		let code = sqlite3.open(path, handle) -- `path` is passed as a C string, `handle` by its address
		if code != sqlite3.ok or handle is none {
			throw Self.OpenError.Failed { code }
		}
		Self { #handle = handle }
	}

	-- called when a `Database` is destroyed
	function destroy = (self) => {
		sqlite3.close(self.#handle)
	}
}
```

The rest of the program sees an ordinary Fa type:

```fa
-- application/main.fa
export function = () throws Database.OpenError => {
	let database = try Database.open("farm.db")
	...
} -- `database` is destroyed here, which closes it
```

## C types

| C | Fa |
| --- | --- |
| `int8_t` to `int64_t`, `uint8_t` to `uint64_t` | `Int8` to `Int64`, `UInt8` to `UInt64` |
| `float`, `double` | `Float32`, `Float64` |
| `bool` | `Boolean` |
| `char`, `int`, `long`, `size_t` and the other types whose size depends on the platform | `c.Char`, `c.Int`, `c.Long`, `c.SizeT`... from `std.c`, sized for the target |
| `T *` | `Pointer(T)?`, where `none` is `NULL` |
| `T *` that is never `NULL` (`_Nonnull`) | `Pointer(T)` |
| `void *` | `Pointer(Void)?` |
| `const char *` (a string) | `CString` |
| `struct` | `CStruct { ... }` |
| an opaque `struct`, only used through pointers | `CStruct { }` |
| `T field[N]` in a `struct` | `CArray(T, N)` |
| `enum`, integer `#define` | `static` integer values |
| function pointer | a function type (see [callbacks](#callbacks)) |

C unions, bit fields and variadic functions (`printf`) are not supported in this version.

The types of `std.c`, `CStruct` and `CArray` can be used in every file. `Pointer` and `CString` can only be used in foreign files.

### `CStruct`

`CStruct` is a type constructor, like [`Union`](/types/unions) or [`Enum`](/types/enumerations). A `CStruct` type has the memory layout C gives to the same `struct` on the target: fields in declaration order, with C's alignment and padding. A plain Fa object type has no fixed layout: the compiler orders its fields for speed.

```fa
type Vertex = CStruct {
	position: CArray(Float32, 3)
	color: CArray(UInt8, 4)
}

mutable vertices: Array(Vertex) = []
```

- A `CStruct` type is nominal: two `CStruct` types with the same fields are different types, like two C `struct`s.
- Its fields have C types: numbers, `std.c` types, `CStruct`, `CArray`, and `Pointer` (a `CStruct` with a `Pointer` field can only be used in foreign files).
- An `Array` of a `CStruct` is a C array: it is passed to C, or to a GPU API, without any copy.

## Pointers

`Pointer(T)` designates a `T` in memory that Fa doesn't manage. It is never `NULL`; a pointer that can be `NULL` is a `Pointer(T)?`, with the same size.

| Operation | Meaning |
| --- | --- |
| `pointer.value` | the `T` it designates, as a reference: `use farm = pointer.value` |
| `pointer.read()` | copies the `T` it designates |
| `pointer.write(value)` | writes a `T` |
| `pointer.offset(count)` | the pointer to the `count`-th `T` after it |
| `pointer.toArray(count)` | copies `count` elements into a new `Array(T)` |
| `cString.toString()` | copies a C string into a `String` |
| `Pointer.allocate(value)` | moves `value` into a new block of memory, and returns a pointer to it |
| `pointer.free()` | destroys the value of a block made by `Pointer.allocate`, and frees it |

What a pointer designates is not checked: reading a pointer that C freed, or reading past the end of a C array, is the error the compiler can't catch. This is why pointers stay in foreign files.

### Passing Fa values to C

When a C function expects a pointer, Fa values are passed without conversion, for the duration of the call:

| The parameter expects | The argument | What C receives |
| --- | --- | --- |
| `Pointer(T)` | an `Array(T)` | a pointer to its first element (pass the length separately, as C expects) |
| `Pointer(T)` | a `mutable` value of type `T` | its address; the parameter must be declared with `mutates` |
| `Pointer(T)` | any value of type `T`, for a parameter without `mutates` | its address, read-only |
| `CString` | a `String` | a copy that ends with a zero byte; a string literal is passed as is, since literals are stored with that byte |

A pointer made from a Fa value is valid until the call returns: C must not keep it. Memory that C keeps after a call must be allocated by C, or with `Pointer.allocate`.

## Declaring C functions

A C function is declared with its function type and `@extern`, which names the C symbol:

```fa
function close: (database: Pointer(Sqlite3)) => c.Int = @extern("sqlite3_close")
```

- A parameter that C writes through is declared with `mutates`, like in any [function type](/functions/defining-functions#function-types). The compiler trusts these declarations.
- A C function can't declare `throws` or `requires`, and it is never [pure](/functions/defining-functions#pure-functions).
- The libraries are linked with the [`build.link`](/architecture/configuration#build) option of `package.fa`: `link = ["sqlite3"]`.

### Callbacks

A function-typed parameter of a C function is a C function pointer. The argument must be a function known at compile time, that captures nothing, with C types. It can't throw: C can't propagate an error. Pass the data the callback needs through a `Pointer(Void)?` parameter, as C libraries do with their `userData` parameter.

```fa
function sort: (base: Pointer(Void), count: c.SizeT, size: c.SizeT, compare: (a: Pointer(Void), b: Pointer(Void)) => c.Int) => Void mutates base = @extern("qsort")
```

## Releasing C resources

In a foreign file, a type can declare a `destroy` function. It runs when a value of the type is destroyed: at the end of its scope, when it is replaced, or when the collection holding it removes it.

- A type with `destroy`, and every type that contains one, is **move-only**, like a [`Task`](/advanced/concurrency#tasks): assigning it moves it, and using the source afterwards is a compile error. A C resource is therefore released exactly once.
- `destroy` takes `self`, and can't throw or be `async`.

This is the only kind of destructor in Fa: since these values can't be copied, the moment the compiler moves a value stays invisible.

## Generating bindings

`fa bind` reads a C header and writes a foreign file with its declarations:

```
fa bind sqlite3.h --output library/sqlite3.foreign.fa -- -I/usr/include
```

- functions become `@extern` declarations, with camelCase names (`sqlite3_open` becomes `open` in a `sqlite3` namespace when every name has that prefix, `sqlite3Open` otherwise);
- `struct`s become `CStruct` types, and opaque ones `CStruct { }`;
- `enum`s and integer `#define`s become `static` values;
- a `const` pointer parameter has no effect, any other pointer parameter is declared with `mutates`; pointers are optional unless the header marks them `_Nonnull`;
- declarations that can't be translated (unions, bit fields, variadic functions, macros that aren't constants) are written as comments.

`fa bind` runs once, when you add or update a binding: its output is committed and edited like any source file. Builds never read C headers, so they don't need a C compiler.

## Exposing a library to C

A package can be built as a C library: a static and a shared library, with a C header. Name the foreign file whose export is the C interface in [`build.cLibrary`](/architecture/configuration#build):

```fa
-- package.fa
export = {
	name = "farm"
	targets = ["native"]
	build = {
		cLibrary = { header = "farm.h", prefix = "farm", api = "library/capi.foreign.fa" }
	}
}
```

```fa
-- library/capi.foreign.fa
use c = std.c

export namespace = {
	function createFarm = (name: CString): Pointer(Farm) => Pointer.allocate(Farm { name = name.toString() })
	function destroyFarm = (farm: Pointer(Farm)) => farm.free()
	function animalCount = (farm: Pointer(Farm)): Int64 throws Farm.Error => try farm.value.countAnimals()
}
```

Every function of the exported namespace becomes a C function, named with the prefix and in snake case: `createFarm` becomes `farm_create_farm`.

- Parameters and results have C types. A Fa value goes to C behind a `Pointer`: the header declares its type as an opaque `struct` (`typedef struct farm_Farm farm_Farm;`), and the interface gives C a function to free it.
- A function that `throws` returns an `int`: `0` on success, and otherwise the position of the error member, starting at 1 (the header declares them as an `enum`). Its result goes through an extra last parameter, a pointer. `farm_last_error_message()` describes the last error of the calling thread.
- An `async` function is exported as its blocking version. An exported function can't declare `requires`.
- C can call the library from any thread, so its functions can't use a module-level `mutable` value unless its type is [thread-safe](/advanced/concurrency).
- The module-level values are initialized when the library is loaded.

## Targets

| Target | Calling C | Exposing a C library |
| --- | --- | --- |
| `native` | yes | yes |
| `wasm` | yes: a C function is an import of the module, provided by C compiled to WebAssembly and linked with it, or by the host | yes: the functions are exports of the module |
| `rust` | yes: `extern "C"` declarations | yes |
| `bun` | yes, through `bun:ffi` (a `CStruct` can't be passed by value) | no |
| `deno` | yes, through `Deno.dlopen` | no |
| `web`, `node` | no: a compile error | no |

To support several targets, branch with [`@if target`](/advanced/metaprogramming) around the code that uses the binding.

## Implementation details

### Native

- A call to an `@extern` function is a direct call with the C calling convention of the target. `CStruct` parameters and results are classified like clang does for the target's C ABI (System V x86-64, AAPCS64, Windows x64), in `fa-llvm`: LLVM doesn't lower C struct arguments by itself.
- A `CStruct` is an LLVM struct with the C layout. It is nominal, so it is interned by declaration, not by shape.
- A temporary C string is built on the stack up to 256 bytes, on the heap beyond. String literals are stored with a final zero byte, which `length` doesn't count.
- `destroy` is pushed on the scope-exit cleanup stack like any destruction. Move-only types are checked by the checker, like `Task`.
- `Pointer.allocate` and `free` use the runtime allocator (`fa_alloc`, `fa_free`).
- A C library includes `fa-runtime`. Its exported functions are thunks: they convert the error union into a status and an out-parameter, store the error message in a thread-local buffer, and start the thread's executor on the first call from a new thread. Module-level values are initialized from `.init_array` (ELF), `__mod_init_func` (Mach-O) or `DllMain` (Windows).
- When a C library is built with clang's ThinLTO and given as bitcode, `lld` optimizes across the two languages, and can inline C functions into Fa code.

### WebAssembly

- `@extern` functions are imports (module `env` by default). `wasm-ld` resolves them against C compiled to WebAssembly; the unresolved ones are left to the host.

### JavaScript

- On `bun`, the libraries of `build.link` are opened with `dlopen` from `bun:ffi`, with one symbol table generated from the `@extern` declarations. A `Pointer` is a number; `read` and `write` go through a `DataView` over `toArrayBuffer`. Callbacks are `JSCallback`s.
- On `deno`, `Deno.dlopen` with the same table; `CStruct` parameters use Deno's `struct` type, and callbacks are `Deno.UnsafeCallback`s.
- A `CString` argument is encoded with a `TextEncoder`, plus the final zero byte.
:::
