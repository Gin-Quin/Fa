# Foreign code

Fa calls C libraries, [Rust code](#using-rust-code) and any code that exposes a C interface. It exposes Fa libraries to C, Python, Rust or any language that speaks the C ABI. A call between Fa and C is a direct call, with the C calling convention: it costs the same as a call between two C functions.

The compiler can't check C code. So everything that touches C lives in **foreign files**, the only place where the compiler trusts declarations instead of proving them. A foreign file binds a library and exports a safe interface; the rest of the program uses that interface, and keeps every guarantee of Fa.

## Foreign files

A foreign file ends with `.foreign.fa`, and is named by the part before it: `Database.foreign.fa` is `Database`. Like any file, it has a [single export](/architecture/modules).

Only foreign files can:

- declare C functions with [`@extern`](#declaring-c-functions), and call them;
- use [`Pointer<T>`](#pointers) and [`CString`](#c-types);
- declare a [`destroy`](#releasing-c-resources) function in a type.

Other files can't use a value whose type contains `Pointer` or `CString` in its public fields, so the unchecked part of a program can't leak out of its foreign files. Keep them small: the bindings of the library, and the safe interface built on them.

A type declared in a foreign file may still keep a pointer in a [private field](/values/objects#private-fields): other files use it through its methods.

A typical binding has two foreign files: the raw bindings, generated by [`fa bind`](#generating-bindings), and the safe interface written on top of them.

```fa
-- sqlite3.foreign.fa, generated by `fa bind sqlite3.h`, then edited
use c = std.c

export namespace = {
	type Sqlite3 = CStruct { } -- an opaque C type, only used behind a pointer

	static ok = 0

	function open: (path: CString, database: Pointer<Pointer<Sqlite3>?>) => c.Int mutates database = @extern("sqlite3_open")
	function close: (database: Pointer<Sqlite3>) => c.Int = @extern("sqlite3_close")
}
```

```fa
-- Database.foreign.fa
export type = {
	#handle: Pointer<sqlite3.Sqlite3>

	type OpenError = Errors { Failed = { code: Integer } }

	function open = (path: String): Self throws Self.OpenError => {
		mutable handle: Pointer<sqlite3.Sqlite3>? = none
		let code = sqlite3.open(path, handle) -- `path` is passed as a C string, `handle` by its address
		if code != sqlite3.ok or handle is none {
			throw Self.OpenError.Failed { code }
		}
		Self { #handle = handle }
	}

	-- called when a `Database` is destroyed
	function destroy = (self) => {
		sqlite3.close(self.#handle)
	}
}
```

The rest of the program sees an ordinary Fa type:

```fa
-- application/main.fa
export function = () throws Database.OpenError => {
	let database = try Database.open("farm.db")
	...
} -- `database` is destroyed here, which closes it
```

## C types

| C | Fa |
| --- | --- |
| `int8_t` to `int64_t`, `uint8_t` to `uint64_t` | `Int8` to `Int64`, `UInt8` to `UInt64` |
| `float`, `double` | `Float32`, `Float64` |
| `bool` | `Boolean` |
| `char`, `int`, `long`, `size_t` and the other types whose size depends on the platform | `c.Char`, `c.Int`, `c.Long`, `c.SizeT`... from `std.c`, sized for the target |
| `T *` | `Pointer<T>?`, where `none` is `NULL` |
| `T *` that is never `NULL` (`_Nonnull`) | `Pointer<T>` |
| `void *` | `Pointer<Void>?` |
| `const char *` (a string) | `CString` |
| `struct` | `CStruct { ... }` |
| an opaque `struct`, only used through pointers | `CStruct { }` |
| `T field[N]` in a `struct` | `CArray<T, N>` |
| `enum`, integer `#define` | `static` integer values |
| function pointer | a function type (see [callbacks](#callbacks)) |

C unions, bit fields and variadic functions (`printf`) are not supported in this version.

The types of `std.c`, `CStruct` and `CArray` can be used in every file. `Pointer` and `CString` can only be used in foreign files.

### `CStruct`

`CStruct` is a type constructor, like [`Union`](/types/unions) or [`Enum`](/types/enumerations). A `CStruct` type has the memory layout C gives to the same `struct` on the target: fields in declaration order, with C's alignment and padding. A plain Fa object type has no fixed layout: the compiler orders its fields for speed.

```fa
type Vertex = CStruct {
	position: CArray<Float32, 3>
	color: CArray<UInt8, 4>
}

mutable vertices: Array<Vertex> = []
```

- A `CStruct` type is nominal: two `CStruct` types with the same fields are different types, like two C `struct`s.
- Its fields have C types: numbers, `std.c` types, `CStruct`, `CArray`, and `Pointer` (a `CStruct` with a `Pointer` field can only be used in foreign files).
- An `Array` of a `CStruct` is a C array: it is passed to C, or to a GPU API, without any copy.

## Pointers

`Pointer<T>` designates a `T` in memory that Fa doesn't manage. It is never `NULL`; a pointer that can be `NULL` is a `Pointer<T>?`, with the same size.

| Operation | Meaning |
| --- | --- |
| `pointer.value` | the `T` it designates, as a reference: `use farm = pointer.value` |
| `pointer.read()` | copies the `T` it designates |
| `pointer.write(value)` | writes a `T` |
| `pointer.offset(count)` | the pointer to the `count`-th `T` after it |
| `pointer.toArray(count)` | copies `count` elements into a new `Array<T>` |
| `cString.toString()` | copies a C string into a `String` |
| `Pointer.allocate(value)` | moves `value` into a new block of memory, and returns a pointer to it |
| `pointer.free()` | destroys the value of a block made by `Pointer.allocate`, and frees it |

`CString.toString()` decodes the bytes before the first zero as UTF-8, replacing each maximal invalid subpart with one `U+FFFD`, following WHATWG, like `String.fromUtf8Lossy`. Invalid text never stops the program. For exact bytes, a C binding returning `Pointer<Byte>` can use `toArray(count)` with a known byte count; `CString` itself has no byte accessor.

What a pointer designates is not checked: reading a pointer that C freed, or reading past the end of a C array, is the error the compiler can't catch. This is why pointers stay in foreign files.

### Passing Fa values to C

When a C function expects a pointer, Fa values are passed without conversion, for the duration of the call:

| The parameter expects | The argument | What C receives |
| --- | --- | --- |
| `Pointer<T>` | an `Array<T>` | a pointer to its first element (pass the length separately, as C expects) |
| `Pointer<T>` | a `mutable` value of type `T` | its address; the parameter must be declared with `mutates` |
| `Pointer<T>` | any value of type `T`, for a parameter without `mutates` | its address, read-only |
| `Pointer<Void>` | any argument that a `Pointer<T>` parameter accepts | its address, as C converts any pointer to `void *` |
| `CString` | a `String` | a copy that ends with a zero byte; a string literal is passed as is, since literals are stored with that byte |

A pointer made from a Fa value is valid until the call returns: C must not keep it. Memory that C keeps after a call must be allocated by C, or with `Pointer.allocate`.

## Declaring C functions

A C function is declared with its function type and `@extern`, which names the C symbol:

```fa
function close: (database: Pointer<Sqlite3>) => c.Int = @extern("sqlite3_close")
```

- A parameter that C writes through is declared with `mutates`, like in any [function type](/functions/defining-functions#function-types). The compiler trusts these declarations.
- A C function can't declare `throws` or `requires`, and it is never [pure](/functions/defining-functions#pure-functions).
- The libraries are linked with the [`build.link`](/architecture/configuration#build) option of `package.fa`: `link = ["sqlite3"]`.

### Callbacks

A function-typed parameter of a C function is a C function pointer. The argument must be a function known at compile time, that captures nothing, with C types. It can't throw: C can't propagate an error. Pass the data the callback needs through a `Pointer<Void>?` parameter, as C libraries do with their `userData` parameter.

```fa
function sort: (base: Pointer<Void>, count: c.SizeT, size: c.SizeT, compare: (a: Pointer<Void>, b: Pointer<Void>) => c.Int) => Void mutates base = @extern("qsort")
```

## Releasing C resources

In a foreign file, a type can declare a `destroy` function. It runs when a value of the type is destroyed: at the end of its scope, when it is replaced, or when the collection holding it removes it.

- A type with `destroy`, and every type that contains one, is **move-only**, like a [`Task`](/advanced/concurrency#tasks): assigning it moves it, and using the source afterwards is a compile error. A C resource is therefore released exactly once.
- `destroy` takes `self`, and can't throw or be `async`.

`copy resource` is an error (`MEM003`); create a new instance with `open`, `create` or a constructor when two resources are needed. A resource parameter borrows: the callee never destroys it, including when it owns a Task. It cannot return or store that borrowed resource as an owner. Moving an owner invalidates its aliases too (`MEM002`). An escaping closure cannot own a resource.

A destructor still owns every field when it runs. Never move a field out from under it: move the whole resource, or use `copy resource.items` for a copyable data field. A function adapter cannot silently copy a resource result into plain data; write the projection and any required `copy` in the function itself.

Finalization binds the exact written owner and its generic arguments and lexical capabilities at construction. A different type with equal fields cannot supply its destructor. Local methods and finalizers retain the environment they capture; structural equality does not choose a default or finalizer.

## Generating bindings

`fa bind` reads a C header and writes a foreign file with its declarations:

```
fa bind sqlite3.h --output library/sqlite3.foreign.fa -- -I/usr/include
```

- functions become `@extern` declarations, with camelCase names (`sqlite3_open` becomes `open` in a `sqlite3` namespace when every name has that prefix, `sqlite3Open` otherwise);
- `struct`s become `CStruct` types, and opaque ones `CStruct { }`;
- `enum`s and integer `#define`s become `static` values;
- a pointer parameter is declared with `mutates`, unless it points to `const` data, a function or an opaque type; pointers are optional unless the header marks them `_Nonnull`;
- declarations that can't be translated (unions, bit fields, variadic functions, variables, macros that aren't integer constants) are written as comments; a `struct` with a bit field or a union field becomes an opaque type.

`fa bind` reads the header itself, without a C compiler, so it only understands plain declarations:

- it doesn't expand macros: a macro word before a type, like `SQLITE_API int`, is skipped, and a declaration built by a macro is written as a comment;
- it doesn't follow `#include`s, and reads every branch of `#if` and `#ifdef` except the blocks of `#if 0`;
- the flags after `--` are ignored for now.

`fa bind` runs once, when you add or update a binding: its output is committed and edited like any source file. Builds never read C headers, so they don't need a C compiler.

## Using Rust code

Fa doesn't compile to Rust: Rust code is used like any C library, through the C ABI. The Rust crate exposes `extern "C"` functions with unmangled names, and is built as a static library:

```toml
# geometry/Cargo.toml
[lib]
crate-type = ["staticlib"] # or "cdylib" for a shared library
```

```rust
// geometry/src/lib.rs
#[unsafe(no_mangle)] // `#[no_mangle]` before the 2024 edition
pub extern "C" fn geometry_distance(x1: f64, y1: f64, x2: f64, y2: f64) -> f64 {
	((x2 - x1).powi(2) + (y2 - y1).powi(2)).sqrt()
}
```

`cargo build --release` writes `libgeometry.a` into `geometry/target/release/`. A foreign file declares the functions with `@extern`, and exports a Fa interface:

```fa
-- library/distance.foreign.fa
function rustDistance: (x1: Float64, y1: Float64, x2: Float64, y2: Float64) => Float64 = @extern("geometry_distance")

export function = (from: { x: Float64, y: Float64 }, to: { x: Float64, y: Float64 }): Float64 => rustDistance(from.x, from.y, to.x, to.y)
```

The library is linked with [`build.link`](/architecture/configuration#build), and `build.libraryPaths` says where to find it:

```fa
-- package.fa
export = {
	name = "farm"
	targets = ["native"]
	build = {
		link = ["geometry"]
		libraryPaths = ["geometry/target/release"]
	}
}
```

A Rust static library may need system libraries too: `cargo rustc --release -- --print native-static-libs` lists them, to add to `link`.

The rules of C apply at the boundary: numbers, `CStruct` (a `#[repr(C)]` struct in Rust), pointers and C strings cross it. A panic that reaches an `extern "C"` function aborts the program, so return failures as status codes, and turn them into Fa errors in the foreign file. [`fa bind`](#generating-bindings) can read a header generated by `cbindgen`. A Fa library is used from Rust the same way, through the [C library](#exposing-a-library-to-c) it builds.

## Exposing a library to C

A package can be built as a C library, with a C header: a static and a shared library on `native`, or a WebAssembly module on `wasm`. Name the foreign file whose export is the C interface in [`build.cLibrary`](/architecture/configuration#build):

```fa
-- package.fa
export = {
	name = "farm"
	targets = ["native"]
	build = {
		cLibrary = { header = "farm.h", prefix = "farm", api = "library/capi.foreign.fa" }
	}
}
```

```fa
-- library/capi.foreign.fa
use c = std.c

type Farm = {
	type Error = Errors { Empty }
	name: String
	animals: Int64 = 0
	function countAnimals = (self): Int64 throws Self.Error => {
		if self.animals == 0 { throw Self.Error.Empty }
		self.animals
	}
}

export namespace = {
	function createFarm = (name: CString): Pointer<Farm> => Pointer.allocate(Farm { name = name.toString() })
	function destroyFarm = (farm: Pointer<Farm>) => farm.free()
	function animalCount = (farm: Pointer<Farm>): Int64 throws Farm.Error.Empty => try farm.value.countAnimals()
	function twice = (value: Int32): Int32 => value * 2
}
```

Every function of the exported namespace becomes a C function, named with the prefix and in snake case: `createFarm` becomes `farm_create_farm`.

- Parameters and results have C types. A Fa value goes to C behind a `Pointer`: the header declares its type as an opaque `struct` (`typedef struct farm_Farm farm_Farm;`), and the interface gives C a function to free it.
- A function that `throws` returns an `int`: `0` on success, and otherwise the position of the error member, starting at 1 (the header declares them as an `enum`). Its result goes through an extra last parameter, a pointer. `farm_last_error_message()` describes the last error of the calling thread.
- An `async` function is exported as its blocking version. An exported function can't declare `requires`.
- C can call the library from any thread, so its functions can't use a module-level `mutable` value unless its type is [thread-safe](/advanced/concurrency).
- The module-level values are initialized when the library is loaded.

`fa build --target=native` writes the static library, shared library and header (for example `libfarm.a`, `libfarm.so`, `farm.h`) into `build/native/`. A C program links the static library with `-lm -pthread` and the libraries in `build.link`. Only API functions are visible; the library can be loaded with `dlopen`, and owned module values are destroyed on unload. Console output is flushed at the end of each API call.

The header uses `int8_t` through `uint64_t`, `bool`, `float`, `double`, `const char *` for `CString`, and `T *` for `Pointer<T>` (`NULL` for an optional pointer). C structs keep their field order; Fa types behind a pointer are opaque. `Integer`, callbacks and generic functions cannot be exported (`FFI014`). An error type becomes an enum named from its nested path, such as `farm_FarmError`; a throwing function's last result pointer may be `NULL`. `farm_last_error_message()` initially returns `""`, retains the last error after a success, and truncates messages after 1023 bytes.

### WebAssembly libraries

With `targets = ["wasm"]`, `fa build` writes `libfarm.wasm`, `farm.h` and the importable loader `libfarm.mjs` into `build/wasm/`. The loader runs on Node.js or Bun:

```js
import open from "./build/wasm/libfarm.mjs";

const library = await open();
try {
	console.log(library.exports.farm_twice(21)); // 42
} finally {
	library.dispose();
}
```

Each call to `open()` creates an independent instance and initializes its module-level values. `dispose()` destroys those values once. Free any objects returned by the API with their exported destruction function before disposing the instance; the instance's functions and pointers must no longer be used afterwards.

`library.exports` contains the C interface. `library.memory` is the instance's `WebAssembly.Memory`: pointers are byte offsets into it, and 64-bit integers cross the JavaScript boundary as `bigint`. Use `library.allocate(size, alignment = 1)` and `library.free(pointer, size, alignment = 1)` for temporary argument and result buffers; free them with the same size and alignment. A memory growth replaces `memory.buffer`, so create a new view after an API call that may allocate.

If the module imports C functions from its host, pass them to `open({ functionName, ... })`, or export them from an `env.mjs` next to the loader. The raw `.wasm` module can also be instantiated by another host: call its `$fa.initialize` export before its API, and `$fa.finalize` once after the last use.

## Targets

| Target | Calling C | Exposing a C library |
| --- | --- | --- |
| `native` | yes | yes |
| `wasm` | yes: a C function is an import of the module, provided by C compiled to WebAssembly and linked with it, or by the host | yes: the functions are exports of the module |
| `bun` | yes, through `bun:ffi` | no |
| `web`, `node` | no: a compile error | no |

To support several targets, branch with [`@if target`](/advanced/metaprogramming) around the code that uses the binding.

A fixed inline `CArray` inherits the ownership category of its items; inline scalar storage alone does not require `copy`. A `CArray<T, n>` is initialized with an array literal of exactly `n` items. It has `length`, supports indexing (negative indices count from the end), writes and iteration. Copying its `CStruct` copies the array.

## Implementation details

### Native

- A call to an `@extern` function is a direct call with the C calling convention of the target. `CStruct` parameters and results are classified like clang does for System V x86-64, AAPCS64 and wasm32, in `fa-llvm`: LLVM doesn't lower C struct arguments by itself.
- A `CStruct` is an LLVM struct with the C layout. It is nominal, so it is interned by declaration, not by shape.
- A temporary C string is built on the stack up to 256 bytes, on the heap beyond. String literals are stored with a final zero byte, which `length` doesn't count.
- `destroy` is pushed on the scope-exit cleanup stack like any destruction. Move-only types are checked by the checker, like `Task`.
- `Pointer.allocate` and `free` use the runtime allocator (`fa_alloc`, `fa_free`).
- A C library includes `fa-runtime`. Its exported functions are thunks: they convert the error union into a status and an out-parameter, store the error message in a thread-local buffer, and start the thread's executor on the first call from a new thread. Module-level values are initialized from `.init_array` (ELF), `__mod_init_func` (Mach-O) or `DllMain` (Windows).
- When a C library is built with clang's ThinLTO and given as bitcode, `lld` optimizes across the two languages, and can inline C functions into Fa code.

- AAPCS64 puts homogeneous aggregates of one to four floats or doubles in floating registers, other structs of at most 16 bytes in integer registers, and larger structs behind a pointer to a copy or `sret`. Under wasm32, a single scalar struct uses that scalar; other structs use `byval`/`sret`.
- C libraries use general-dynamic thread-local storage so `dlopen` works. A version script limits shared exports; static output is one relocatable object (`ld.lld -r`, then `llvm-objcopy --keep-global-symbol`). Error messages use a thread-local 1024-byte buffer. Load/unload functions use `.init_array`/`.fini_array` on ELF.
- `Pointer.allocate(value)`, `read`, `write`, `value` and `free` work natively, on wasm and on Bun. Reads copy Fa values; replacing a value destroys the old one.

### WebAssembly

- `@extern` functions are imports (module `env` by default). `wasm-ld` resolves them against C compiled to WebAssembly; the unresolved ones are left to the host.
- `build.cLibrary` links with no entry point and exports the C interface, memory and four lifecycle/allocation helpers (`$fa.initialize`, `$fa.finalize`, `$fa.allocate`, `$fa.free`). Initialization and finalization are guarded per instance. The `.mjs` loader caches the compiled module, creates the host runtime state per instance and exposes the C functions directly, without a JavaScript wrapper per call. The last-error buffer belongs to the instance rather than a thread. `CString.toString()` measures the zero-terminated input with a generated byte loop, so it needs no host `strlen` import, then validates and decodes it with WHATWG replacement.

### JavaScript

- On `bun`, the libraries of `build.link` are opened with `dlopen` from `bun:ffi`, with one symbol table generated from the `@extern` declarations. A `Pointer` is a number; `read` and `write` go through a `DataView` over `toArrayBuffer`. Callbacks are `JSCallback`s.
- A `CString` argument is encoded with a `TextEncoder`, plus the final zero byte.
- `Pointer.allocate` uses C `malloc`, and `free` uses C `free`. C-compatible values use their C layout in the block. Other Fa values are rooted in a map keyed by the C address until freed; `read` copies them, `write` destroys the previous value, and `value` borrows it. A view of a C struct or fixed array uses getters and setters over its memory, including nested fields. A target that still contains an unresolved generic parameter is not compiled yet.

### State of the implementation

- Analyzer: C declarations, pointers, fixed arrays, resources and C-library APIs are checked. C unions, bit fields and variadic functions are rejected (`FFI007`).
- Native: `@extern` calls, `CStruct` by value under x86-64 System V, AAPCS64 and wasm32 ABIs, `CString`, arrays and addresses, callbacks, resource destruction, `build.link`, and C libraries on Linux and macOS. Windows x64 struct classification and `DllMain` remain unimplemented. Multi-file programs are supported. A temporary C string is currently heap allocated.
- JavaScript: Bun supports C structs passed by value through a shim compiled on first use by `bun:ffi`'s `cc`; generated code lays out the arguments in C memory and the shim applies the platform ABI. Resource destruction runs at scope exit for owning locals and fresh default temporaries; resource parameters borrow and never finalize the caller's value, inside composites and collections, when a value is replaced, and for discarded new values. A resource's destructor is imported when its type is declared in another file. A drop flag tracks moves, including a resource whose bytes are all zero.
- WebAssembly: `@extern` calls are `env` imports unless C objects in `build.link` define them. The loader gets host functions from `env.mjs` next to it, copied from the program or package root; that module can export `attach(exports)` to reach memory. Missing functions are reported by name. C-library exports remain to be implemented.
